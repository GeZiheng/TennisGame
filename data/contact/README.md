# 击球采集样本

真机打球的每一次「球与拍面相遇」落到这里，一行一条 JSONL。**不进版本库**
（`.gitignore` 里忽略 `*.jsonl`），这个 README 和 `.gitkeep` 保留目录本身。

## 怎么产生

```bash
npm run dev:https        # 打真机走这个（手机传感器只在安全上下文里开放）
```

**页面一加载就开始采**，不需要按任何键。HUD 左上角会显示 `采集 s1 · 37 条`。

| 键 | 作用 |
|---|---|
| `L` | 暂停 / 恢复（暂停时会先把攒下的落盘） |
| `K` | 立刻落盘，并把分组读数打到浏览器控制台 |
| `R` | 姿态重标定 + **采集换段**（`s1` → `s2`） |

落盘走 dev server 的 `POST /__contact`（`server/vite-plugin.ts`），边打边追加：

- 攒够 8 条写一次；停手 10 秒也会写一次；关页 / 刷新前用 `sendBeacon` 补一次
- 文件名是**页面打开时刻**的 `YYYYMMDD-HHMMSS.jsonl`，所以刷新一次就是新文件，
  两次会话不会混进同一份
- 服务端不可用时（比如直接开 `dist/`）按 `K` 会退回浏览器下载

## 文件长什么样

一行一条，分三块。**建模时只准 `feat.*` 进 X**：

```json
{"t":1734567890,"session":"s1",
 "label":{"G":[0.1,1.3,1.0],"fc":[0.15,1.19,1.22],"rest":[0,0.6,0],"delta":[0.05,-0.11,0.22]},
 "feat":{"rest":[0,0.6,0],"lag":43,"peakW":21.4,"speed":24,"charge":0.7,
         "face":[0.3,-0.2,-0.93],"ballV":[1.2,-3.1,9.8]},
 "meta":{"hit":true,"swung":true,"serve":false,"offCenter":0.34,
         "rally":3,"sincePrevHit":1840,"driftDeg":4.2,"driftComp":false,
         "at":[0.12,1.35,1.0],
         "planOffset":[0,0.6,0.02],"holdR":0.14,"deadband":0.05,"deadbandY":0.02}}
```

| 块 | 内容 | 能不能进特征 |
|---|---|---|
| `label` | `G` 握点、`fc` 相遇时刻拍面中心、`rest` 站立偏移、`delta` 标签 | 否。`delta` 是**标签**，`G` 是走位的输出 |
| `feat` | 握法、`lag` 挥拍时差、挥拍强度、拍面法线、球速 | 是。白名单 = `FEATURE_KEYS`，测试逐字对表 |
| `meta` | 命中与否、第几拍、漂移读数、球的位置、瞄准点与走位容差 | 否。用于筛选、整段剔除和残差分解 |

`G` 必须记（否则算不出 `delta`）但**绝不能进特征**——喂进去就是闭环自激，模型会
开始拟合自己的输出。这道约束写在字段分组里，不靠记性：`feat` 的字段由
`core/contact-log.ts` 的 `FEATURE_KEYS` 白名单兜住，谁往里加字段没登记，`npm test` 直接红。

**`at`（球的世界坐标）11-16 从 `feat` 挪进了 `meta`。** 它看起来是纯外部条件，实测
与 `label.G` 的 x 分量相关 **0.994**、`|at − G|` 均值 **0.565m** 且差值近乎常数——
因为球是打到你身边才打得到的。喂进模型等于把握点（走位输出）换个名字塞回 X。
诊断还要用它还原漏接几何，所以留着，只是不能当特征。

`meta` 里那三个走位量是**诊断用**，不是特征：

| 字段 | 含义 | 拿它算什么 |
|---|---|---|
| `planOffset` | 相遇前喂给 `planAutoMove` 的瞄准点 | 残差 `= delta − (planOffset − rest)`，即「实际扫出去」减「当时以为会扫出去」 |
| `holdR` | 当时生效的 `TargetHold.holdR` | 残差里「按设计允许不动」的那一截 |
| `deadband` | 当时生效的 `stepAxis` 死区（x / z） | 同上 |
| `deadbandY` | 竖直轴的死区，比 `deadband` 小（0.02） | 同上。**分轴记**，拿 0.05 减 y 会减多 |
| `at` | 球心位置（碰到时是接触点，没碰到是最近点） | 漏接几何、`offCenter` 的来源。**不进特征**，见上 |
| `driftDeg` | 手机认为「传感器已经漂了多少度」，1Hz 上报 | **不是误差**，见下。必须配 `driftComp` 读 |
| `driftComp` | 取上面那个读数时补偿开没开 | 关 = 「观测到的累计漂移」，开 = 「已经替你扣掉多少」 |

`driftDeg` 是相遇前**最后一个报文**，最多滞后 1 秒。手机没接上、或者页面是 11-16
之前的旧版，它是 `null` 表示**不知道**——不是 0。换段（`R` / 重连）之后也会先置
`null`，等新报文到了才有值；4.34 之后手机在重置 / 重连时**立刻补报**一次，所以这个
空窗现在只到毫秒级。

**4.35 起它的含义变了：它随玩法时长单调增长，不代表「这一刻歪了多少」。** ZUPT 之后
`driftDeg = 零偏 × 时间`，打了十分钟就是几百上千度，而这个数越大恰恰说明补偿做得越
到位。所以**不要再用 `|driftDeg| > 20` 之类的阈值剔样本**——那会把正常的长时间会话
整段砍掉。要判断「这批数据可不可信」，看的是手机 HUD 上的 `°/s`（零偏估计）：
0.1–1°/s 是正常 MEMS 零偏；>2°/s 说明这台机器的 yaw 基本靠陀螺积分硬撑，那一段的
姿态本来就不可信。

**11-16 与 11-17 之前那几批的 `driftDeg` 全部作废。** 那时算的是「累计的慢转角」：门限
`0.05 rad/帧`，20–25Hz 下等于 58–72°/s，抬手转身都被当成漂移积了进去——读数中位 90°、
最大 674°，而命中率在漂移分桶上完全平坦（见 `docs/history.md` 4.34）。4.34 把门限按
角速度判（5.7°/s），4.35 换成 ZUPT（静止窗口测零偏、运动外推）。那批样本的
`delta` / `feat` / `planOffset` 不受影响，只是**不能拿 `driftDeg` 做剔除**。

`planOffset` **必须是相遇前的快照**：命中之后 `learnContact` 会原地把它朝这一拍的
`delta` 收敛，取晚一拍记到的就是「学完之后」的瞄准点，残差会凭空变小——正好把要
诊断的偏差自己抹掉。`buildContactSample` 里存的是拷贝，有一条测试专门钉住它
（改成存引用，所有样本都会显示最后一帧的瞄准点，而文件看起来完全正常）。

`holdR` 和两个死区记逐条而不是写进 README 常量表，是为了**参数改过之后老数据
还能解释**：残差里有 14cm + 5cm（y 是 2cm）是设计上就允许的静差，不算走位误差。
混在一起算，会得出「走位一直偏 19cm」的错误结论。

**11-15 那批样本没有这三个字段**（`undefined`）——记录器到 11-15 23:24 才开始记。
分析时按缺省处理：那批数据只能用 `offCenter` 间接推断，不能算残差。

**11-16 之前的样本 `driftDeg` 全是 `null`**（那字段当时写死在 `recorder.ts` 里，从来
没接过线），`at` 还留在 `feat` 里。两批数据可以合并看分布，但**不能混进同一个训练集**。

不能混的硬理由不是 schema，是**两天不是同一个映射**（同一份 `delta ~ rest + lag`，
`rest.y → delta.y` 的系数）：

| 批次 | n | `rest.y → delta.y` | `r(lag, delta.y)` |
|---|---|---|---|
| 11-15（16:21，s3–s4） | 21 | **−1.30 ± 0.17** | −0.13 |
| 11-16（22:14，s1–s5） | 90 | **−0.13 ± 0.09** | **−0.62** |

差值约 1.2（合成标准误 0.19），两天的 `rest` 共线性也相近（`r(rest.x, rest.y)` 都是
−0.45 左右），所以这不是小样本噪声，也不是共线性假象。11-15 那天 `delta.y` 主要由
握法解释，11-16 主要由 `lag` 解释。混起来两条关系会互相抵消（pooled 系数 −0.32，
对哪一天都不对）。**先按天分组，再决定是一天一个模型还是加天级特征。**

## 发球不在训练集里（一条规则，不是「暂时没采到」）

**发球不进校准器。** 抛球点与击球区已经锚在握点上、顶点 3.43m（`docs/history.md` 4.25），
真机反馈位置合适，没有要修的东西；而且发球是举在头上打的，杆向量分布和地面击球完全
不是一回事，混进来只会把地面击球的均值带偏。

现在的实现保证：发球走 `Duel.tickToss` 里独立的 `tossContact` 判定，不经过
`enterContact`，**一个 `contact` 事件都不发**。所以 `meta.serve` 恒为 `false`——
这个字段是留给「万一以后有人把发球接进统一采集」时的护栏，`usableForCalibration()`
会按它整条剔除。两条测试钉在这一层：`usableForCalibration(serve:true) === false`，
以及「发球阶段挥拍能打出去、但一条 contact 都不产生」。

为什么要采、标签是什么、三种相遇（命中 / 碰到没挥 / 没碰到）怎么区分，见
`src/core/contact-log.ts` 的文件头注释。

## 分析

`lag` 分桶的均值是第一层漏斗：三桶几乎一样就说明 `lag` 不是主因，校准器的收益
上限很低；差得明显才值得上回归。在浏览器里按 `K` 就能看到这份读数（控制台）。
