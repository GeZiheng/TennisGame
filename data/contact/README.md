# 击球采集样本

真机打球的每一次「球与拍面相遇」落到这里，一行一条 JSONL。**不进版本库**
（`.gitignore` 里忽略 `*.jsonl`），这个 README 和 `.gitkeep` 保留目录本身。

## 怎么产生

```bash
npm run dev:https        # 打真机走这个（手机传感器只在安全上下文里开放）
```

**页面一加载就开始采**，不需要按任何键。HUD 左上角会显示 `采集 s1 · 37 条`。

| 键 | 作用 |
|---|---|
| `L` | 暂停 / 恢复（暂停时会先把攒下的落盘） |
| `K` | 立刻落盘，并把分组读数打到浏览器控制台 |
| `R` | 姿态重标定 + **采集换段**（`s1` → `s2`） |

落盘走 dev server 的 `POST /__contact`（`server/vite-plugin.ts`），边打边追加：

- 攒够 8 条写一次；停手 10 秒也会写一次；关页 / 刷新前用 `sendBeacon` 补一次
- 文件名是**页面打开时刻**的 `YYYYMMDD-HHMMSS.jsonl`，所以刷新一次就是新文件，
  两次会话不会混进同一份
- 服务端不可用时（比如直接开 `dist/`）按 `K` 会退回浏览器下载

## 文件长什么样

一行一条，分三块。**建模时只准 `feat.*` 进 X**：

```json
{"t":1734567890,"session":"s1",
 "label":{"G":[0.1,1.3,1.0],"fc":[0.15,1.19,1.22],"rest":[0,0.6,0],"delta":[0.05,-0.11,0.22]},
 "feat":{"rest":[0,0.6,0],"lag":43,"peakW":21.4,"speed":24,"charge":0.7,
         "face":[0.3,-0.2,-0.93],"at":[0.12,1.35,1.0],"ballV":[1.2,-3.1,9.8]},
 "meta":{"hit":true,"swung":true,"serve":false,"offCenter":0.34,
         "rally":3,"sincePrevHit":1840,"driftDeg":null,
         "planOffset":[0,0.6,0.02],"holdR":0.14,"deadband":0.05,"deadbandY":0.02}}
```

| 块 | 内容 | 能不能进特征 |
|---|---|---|
| `label` | `G` 握点、`fc` 相遇时刻拍面中心、`rest` 站立偏移、`delta` 标签 | 否。`delta` 是**标签**，`G` 是走位的输出 |
| `feat` | 握法、`lag` 挥拍时差、挥拍强度、来球位置与球速 | 是。只放与走位无关的外部条件 |
| `meta` | 命中与否、第几拍、漂移读数、瞄准点与走位容差 | 否。用于筛选、整段剔除和残差分解 |

`G` 必须记（否则算不出 `delta`）但**绝不能进特征**——喂进去就是闭环自激，模型会
开始拟合自己的输出。这道约束写在字段分组里，不靠记性。

`meta` 里那三个走位量是**诊断用**，不是特征：

| 字段 | 含义 | 拿它算什么 |
|---|---|---|
| `planOffset` | 相遇前喂给 `planAutoMove` 的瞄准点 | 残差 `= delta − (planOffset − rest)`，即「实际扫出去」减「当时以为会扫出去」 |
| `holdR` | 当时生效的 `TargetHold.holdR` | 残差里「按设计允许不动」的那一截 |
| `deadband` | 当时生效的 `stepAxis` 死区（x / z） | 同上 |
| `deadbandY` | 竖直轴的死区，比 `deadband` 小（0.02） | 同上。**分轴记**，拿 0.05 减 y 会减多 |

`planOffset` **必须是相遇前的快照**：命中之后 `learnContact` 会原地把它朝这一拍的
`delta` 收敛，取晚一拍记到的就是「学完之后」的瞄准点，残差会凭空变小——正好把要
诊断的偏差自己抹掉。`buildContactSample` 里存的是拷贝，有一条测试专门钉住它
（改成存引用，所有样本都会显示最后一帧的瞄准点，而文件看起来完全正常）。

`holdR` 和两个死区记逐条而不是写进 README 常量表，是为了**参数改过之后老数据
还能解释**：残差里有 14cm + 5cm（y 是 2cm）是设计上就允许的静差，不算走位误差。
混在一起算，会得出「走位一直偏 19cm」的错误结论。

**11-15 之前的样本没有这三个字段**（`undefined`），分析时按缺省处理：那批数据只能
用 `offCenter` 间接推断，不能算残差。

## 发球不在训练集里（一条规则，不是「暂时没采到」）

**发球不进校准器。** 抛球点与击球区已经锚在握点上、顶点 3.43m（`docs/history.md` 4.25），
真机反馈位置合适，没有要修的东西；而且发球是举在头上打的，杆向量分布和地面击球完全
不是一回事，混进来只会把地面击球的均值带偏。

现在的实现保证：发球走 `Duel.tickToss` 里独立的 `tossContact` 判定，不经过
`enterContact`，**一个 `contact` 事件都不发**。所以 `meta.serve` 恒为 `false`——
这个字段是留给「万一以后有人把发球接进统一采集」时的护栏，`usableForCalibration()`
会按它整条剔除。两条测试钉在这一层：`usableForCalibration(serve:true) === false`，
以及「发球阶段挥拍能打出去、但一条 contact 都不产生」。

为什么要采、标签是什么、三种相遇（命中 / 碰到没挥 / 没碰到）怎么区分，见
`src/core/contact-log.ts` 的文件头注释。

## 分析

`lag` 分桶的均值是第一层漏斗：三桶几乎一样就说明 `lag` 不是主因，校准器的收益
上限很低；差得明显才值得上回归。在浏览器里按 `K` 就能看到这份读数（控制台）。
