## 3.1 姿态链路：手机 → 大屏 → 球拍位姿

```
deviceorientation (alpha/beta/gamma)
  → attitude.deviceEulerToWorldQuat   R = Rz(α)Rx(β)Ry(γ)，再左乘 EARTH_TO_WORLD = Rx(-90°)
  → toOutputQuat                      只归零绕世界 Y 的朝向（yawZero 懒锁存）
  → 网络（60Hz，68 字节包）
  → PlayScene.syncRacket              自适应平滑 + 组装位姿
  → Duel.pushRacket                   每帧必推
  → RacketTrack.at(t)                 400ms 滑窗，按时间戳 slerp
  → sweepFace                         物理子步求交
```

四个不能改的约定：

1. **球拍本地轴 = 手机硬件轴**：拍柄 +Y（手机长边），拍面法线 +Z（垂直屏幕）。设备→球拍是单位矩阵。
2. **屏幕旋转补偿是错的，已删除。** 设备坐标系焊死在硬件上，与 `screen.orientation.angle` 无关。按它补旋转会让横握时球拍整体歪 90°。
3. **姿态用绝对姿态，不积分陀螺仪。** 陀螺仪只给角速度，积分出来是相对启动时的增量，没有重力参考。拿不到方向事件时才退回陀螺仪积分。
4. **平滑是自适应的**（`scene.syncRacket`）：等效角速度 `spin` > 12 rad/s 时 τ=3ms（几乎不平滑，拍子完全跟手），> 4 时 τ=10ms，静止时 τ=22ms。固定 22ms 会让快挥时拍面滞后 44cm。

**渲染与判定必须用同一份 pose。** `syncRacket` 返回的 `RacketPose` 一边喂给 `duel.pushRacket`，一边用来设置 three.js 的 `position/quaternion`。如果渲染和判定各算一份，就会出现「看着碰到、判定说没有」。

## 3.2 挥拍检测：迟滞 + 峰值保持

`src/core/swing.ts` 的 `SwingDetector` 是一个状态机，不是三点峰值比较。

原因是频率对不上：大屏 60Hz 发包，而 `deviceorientation` 常常只有 20–35Hz。走姿态差分兜底时，同一个角速度值会被连发 2–4 次，序列里出现平台段；「严格大于左右邻居」在平台段上恒不成立，整次挥拍被静默丢弃。曾出现「球到面 43 次、挥拍只记到 1 次」。

判据：

```
越过 SWING_THRESHOLD(3.0 rad/s) → armed，跟踪这一路的最大 |ω| 及其时刻
回落到峰值的 FALL_RATIO(0.9)     → 结算，用**峰值那一刻**的姿态建拍
超过 SWING_MAX_MS(450ms) 没回落 → 那是「转」不是「挥」，丢弃
冷却按两个峰的真实间隔算，不受结算延迟影响
```

**`FALL_RATIO` 是整条链路里对手感最贵的参数。** 结算发生在峰值之后，球什么时候被打出去就跟着晚多久：

- 0.75：峰值后 50–90ms，超过人的视触同步阈值（50–80ms），能明显感觉到「球被吸住」
- **0.90：峰值后 1–2 帧（16–33ms），低于感知阈值**
- 不能取 1.0：平台段上 w 恒等于峰值，「跌到峰值以下」永远不成立，一次都不会结算

**抢跑 `liveStroke`**（`Duel` 构造注入）：`takeStroke` 找不到已结算的挥拍时，直接向检测器要一份「正在进行中」的峰。球到面的那一帧就出球，`出球` 诊断恒为 0。配套 `consumeLive()` 后置 `blocked`，要等 w 跌破 `SWING_THRESHOLD*0.7` 才解锁，否则同一次挥拍会被再结算一次。

**角速度双通道**（`controller/sensors.ts`）：`devicemotion.rotationRate` 和「姿态差分」（`gyro.omegaFromQuatDelta`）都记录，双向判定该信谁——rotationRate 出现过大读数就一直信它；一直为 0 而差分在动就切差分。只判一个方向的话，坏机器永远切不过去。

## 3.3 出球模型：`shotFromStroke`

不追求物理正确，追求「玩家意图能被兑现」：

```ts
dir   = normalize(face * 0.72 + headDir * 0.30 + [0, 0.06, 0])
speed = clamp(dot(head, dir) * 0.85 + 3, SPEED_MIN=18, SPEED_MAX=32)
clean = dot(face, FORWARD=[0,0,-1]) > 0.15
```

- **拍面法线 72% + 拍头速度 30%**：纯法线会让「挥拍方向完全不影响结果」，纯挥拍方向又让拍面控制失效。
- **拍面偏角被放大**：出球方向 72% 来自法线，10° 的拍面偏差在 10 米外差 1.24m。这是握持安装角影响大的原因。
- **速度沿出球方向投影**：横挥的能量应该变成旋转，不是凭空加到球速上。
- **拍面完全背对球场时不纠正方向**：球往后飞，玩家立刻看到「打不出去」，比文字提示直接。
- **`SPEED_MIN=18` 是玩法底线，不是防呆**：场地往返 21.6 米，低于它球过不了网前就开始掉，玩家看到的是「打出去了，然后没了」。上限 32 防数据毛刺打出炮弹。
- **高球惩罚 `pen`**（`duel.ts` 的击球分支）：击球点 > 1.35m 时 `pen = max(0.62, 1 - (y-1.35)*0.34)`，打断「连续全力挥 → 击球点一拍比一拍高 0.35m → 五拍后够不着」的正反馈。

旋转：把拍头速度分解到垂直于出球方向的平面上，向上刷 = 上旋（`topComp * 26`，限 ±420 rad/s），向下切 = 下旋，侧向 = 侧旋（`sideComp * 18`，限 ±260）。

## 3.4 弹道积分：`physics.advance` / `substep`

240Hz 定步长、半隐式欧拉（先更新速度，再用新速度走位置）。

```
重力   0.56 N
阻力   1.05 N   ← 30 m/s 平击时比重力还大，这是网球速度衰减极快的原因
马格努斯 0.2 N  ← 够让上旋球提前两米落地
```

- **阻力**：`kd = 0.5·ρ·Cd·A·|v| / m`，加速度 `-kd·v`。`DRAG_CD=0.55`（绒毛表面）。
- **马格努斯**：`F = 0.5·ρ·A·r·Cl·(v × ω)`。**叉乘顺序必须是 `v × ω`**，写成 `ω × v` 上旋会往上飘——看着「也挺像那么回事」，但旋转玩法全废。单测专门钉了一条「上旋必须比平击落得早」。
- **旋转衰减**：`exp(-h/SPIN_TAU)`，`SPIN_TAU=4s`。
- **地面**：`v[1] < -0.6` 才算一次落地。上旋落地「蹿」：水平摩擦 `0.74 + ts*0.18`（夹 0.45–0.95），竖直恢复 `0.76 + ts*0.05`，旋转衰减到 55%。低于阈值走贴地滚动分支，只做阻尼，**不计落地**（否则静止球每秒刷 240 个 ground 事件）。
- **球网**：用「这一步是否跨越 `NET_Z` 平面」判断，不用距离比较。`yCross = p[1] - v[1]·h·(1-tt)`，小于 `NET_H + BALL_R` 就撞网。

`advance` 不把多帧累积到累加器：累加器会让球慢 1–3 步（4–12ms），而击球判定依赖球的位置，这点滞后直接变成「手感黏」。它把一帧拆成不等长子步，最后一步可能只有半拍。

## 3.5 拍面碰撞：`sweepFace`（核心）

**判据是「球心到拍面圆盘的距离 ≤ 球半径」，不是「球心穿过拍面平面」。**

两种判据的差别只在掠射时出现：

- 球正撞拍面（球路与拍面成几十度）：最近点在平面上，两者完全一致。
- 球**顺着拍面掠过**（球路几乎平行于拍面）：球心可能永远不穿过平面，但球体已经压到拍线上了。按「必须穿过平面」判会漏——漏掉的那 16ms 在屏幕上就是「球从拍子中间穿过去」。

实现（`core/racket.ts`）：

```ts
// 世界点 → 拍面局部系（原点在握点，+y 沿拍柄，拍面平面是局部 z=0）
a = toLocal(pose, p0); b = toLocal(pose, p1);

// 候选点：穿过平面处 + 面内离中心最近处 + 两个端点
// 挑垂距 ≤ BALL_R + FACE_MARGIN 且 (u/rx)² + (v/ry)² ≤ 1 的，取最靠中心的一个
R  = BALL_R + FACE_MARGIN
rx = FACE_RX + R;  ry = FACE_RY + R
```

- **必须做线段求交，不能做点判定**：240Hz 子步里球走 8–17cm，是球半径的 3–5 倍。球在两帧之间穿过去时两端都不在椭圆内。
- **椭圆按球半径 + 容差膨胀**：近似 Minkowski 和，中心区域精确，只在长轴端点处多算几毫米。
- **`FACE_MARGIN=0.02` 补的是位姿延迟**：判定用的拍面比玩家手里那把（也比他屏幕上看到的）平均晚 20–60ms，快速挥拍里就是几厘米。1.2cm 时会出现「视觉上明显蹭到框、判定说没有」。
- **等效判定半轴**：横向 `0.15 + 0.0335 + 0.02 = 0.2035`，竖向 `0.19 + 0.0335 + 0.02 = 0.2435`。这两个数决定了喂球散布能有多大（第 3.6 节）。

**位姿必须按时刻插值。** 拍面位姿来自渲染循环（60Hz），物理跑 240Hz，一个子步里拍面最多转 25°。`RacketTrack` 保留 400ms 历史，`at(t)` 按时间戳 slerp（不是帧序号，rAF 不是严格 60Hz）。

**子步回调返回 `false` 必须立刻 break**（`advance` 的 `onStep`）：球被接住后速度为 0，继续推进会让它往下掉一点点，而且后续子步可能重复触发碰撞。

## 3.6 出球反解：`aimIntoCourt`

整条链路上**只有一个**「我要球落在哪儿 → 该用什么速度打」的求解器，就是它：
回球机、发球、探针喂球全都调用它。别再写第二份——两份求解器一起存在时，
「探针量的到底是哪一份物理」会变成一道记忆题（`docs/history.md` 4.27）。

签名（`physics.ts`）：

```ts
aimIntoCourt(from: V3, target: V3, spin = [0,0,0], opts): V3 | null
```

`target` 是**落点**（`[x, BALL_R, z]`），`opts` 是硬约束：

| 选项 | 含义 |
|---|---|
| `minClear` / `maxClear` | 过网时球心离网顶的高度带。松了会擦网，紧了只剩月亮球 |
| `zMin` / `zMax` / `xMax` | 落点范围（默认「对方场内、不贴边线」） |
| `speed` | 出球速度区间，`[8, 26]` 是回球机的档 |
| `arriveZ` / `arriveY` / `arriveTol` | 可选：球**穿过某个 z 平面**时的高度必须落在带内 |

**返回 `null` 是正常结果**，含义是「几何上真没法既落界内、又到这个高度」。
调用方负责退让（换落点、放宽高度带），不能把 `null` 当异常。

**为什么必须用 `advance` 复算而不是解析解**：阻力让射程短 10–15%，马格努斯再改
一遍形状，解析式打出来的落点系统性偏近。求解器内部就是「猜一组速度 → 跑一遍
真实物理 → 按误差修正」，所以它和游戏内是同一套弹道，不存在「解出来的球实际
落不到那儿」。

## 3.7 回球机：三层，且不带任何特权

`core/machine.ts` 的完整设计写在它自己的文件头，这里只留三条给别人看的关键约束。

**它不参与特殊判定。** 每帧产出一个 `RacketPose`，塞进和玩家同一套 `RacketTrack` /
`sweepFace`；球必须真的碰到它的拍面才算回球，够不着一样漏。所以 `Duel` 里没有
`if (side === 'machine')` 的判定分支——以后换成 RL 或另一个真人，状态机不用改。

**到面高度带是硬约束**（`ARRIVE_Y_MIN/MAX` = 1.3 / 1.6，`arriveTol` 0.12）：

| 到面高度带 | `duel-sim` 连续回球 L1 / L2 / L3 |
|---|---|
| **1.3–1.6m（现用）** | **27 / 52 / 81** |
| 1.45–1.75m | 22 / 33 / 75 |
| 1.6–1.9m | 26 / 40 / 69 |

拍面中心只能落在半径 `FACE_CY`=0.6 的球壳上（握点 1.3 → 拍面 1.3–1.9），但可及的
整段不等于该送的高度段：往高调，从 21.6 米外还要「落界内 + 爬那么高」的弹道越少，
机器只能打月亮球。

**落点是候选阶梯，不是一次求解。** 站位越靠前，能打的落点越靠前（从 `z=-21.3`
出发只能打 `-6.0…-2.0`，从 `-14` 出发可以打 `-3.5…-1.0`）。所以 `candidateTargets()`
按站位给一串目标，前面几档全 `null` 才判 `solve` 失败（`lastMiss = 'solve'`）。

三档难度只改四个数：反应延迟、横移速度、站位误差、`cornerProb`（打不打刁角）。
L1 平均回合 1.2 拍、L2 4.3 拍，用于 `npm run duel-sim` 的门禁。

## 3.8 状态机 `Duel`

```
wait --(1.5s / 换分)--> [发球方]
      玩家发球：setup（走到位）→ toss（抛球）→ 等挥拍 → live
      机器发球：直接 live
live --(落地 / 撞网 / 飞出范围)--> point --> wait
      --(发球落点不在发球区)--> fault --> 二发 / 双误
```

要点：

- **一分只在三个时刻判**：落地、撞网、飞出范围。中间不给「漏接」的即时判定——
  否则「打出一条飞向底线的长球、先穿过对手击球面再落在界外」会被判成对手漏接。
  代价是反馈晚半秒，换的是判罚正确（`docs/duel.md` 3.1）。
- **第一落点定局**：球合法落在对方场内之后，弹第二下或滚出边线都不改判。
- **发球两发**：一发失误升二发，二发再失误是双误，这一分归接发方。发球**必须
  落在斜对角发球区**，判据与普通落点共用 `onCollision`，只是区间换成 `serveBox()`。
- **`contact` 不是阶段而是标记**：球穿过击球面时只记「这一拍有人该打了」，
  不暂停物理、不定输赢。

`DuelDiag` 五个数：`swings`（收到挥拍次数）、`reaches`（球到面次数）、
`lastOffCenter`（甜区，1=拍框内沿）、`lastLag`（时差，正=挥晚）、
`lastLatency`（出球延迟）。HUD 那一行还多一个「拍面」偏角，那是渲染层算的。

## 3.9 主循环顺序（不能换）

```ts
updatePlayer(dt);                              // 走位：键盘优先，否则自动
lastPose = scene.syncRacket(now, dt);          // 先平滑球拍并取位姿
duel.pushRacket(lastPose);                     // 每一帧都要推
for (const e of duel.update(dt, now)) handle(e);
scene.setBall(duel.ball.p, duel.ball.spin);
scene.render(dt);
```

先判定再平滑 → 拿到的是上一帧姿态，快速挥拍会偏几十度，越用力越容易空。

### `updatePlayer` 里的两路走位

`src/core/auto-move.ts` 只有三个纯函数（`planAutoMove` / `stepAxis` / `blendCenterOffset`），
决策全在它里面，`app.ts` 只负责调用。输入只有两路，**键盘优先**：

1. **键盘**（`WASD`）——这一帧只要有方向键按下，就整帧走键盘，自动走位让位。
2. **自动**（默认）——`planAutoMove(ball, { x, y, z, center })` 给出握点目标 `(x, y, z)`。

> 11-10 曾加过第三路「摄像头追胸口色块」（`?vision=1`，优先级最高）。11-13 整条删除，
> 见 `docs/history.md` 4.21——走位来源只剩这两路，玩家只负责挥拍。

自动那一路（11-13 两次修正后是**三维**）：

1. `sampleCrossings(ball, minZ + c.z, maxZ + c.z)` 沿弹道每 10cm 采一个穿面点。
   采样在**第二次我方半场落地**处截断——那之后这一球已经判死了（`duel` 的
   「两次落地」），继续往后推出来的是不存在的弹道；
2. 每个点反解出握点 `(p.x - c.x, p.y - c.y, p.z - c.z)`，三轴各自夹到身体范围内：
   横向 ±5.6（**单打边线外 1.5m**）、纵深 -6.5…+1.3（网前 4m 到底线内）、
   **握点高度 0.70–1.65**；
3. 高度夹出来的差值不为零 ⇒ 这个平面**不合格**：站在那儿拍面也罩不住球，再近也没用。
   这是「离球太近却打不到」的直接解药；
4. 剩下的分轴估走到那儿要多久（横移 5.4 / 前后 3.6 / 升降 6 m/s），超过球到面时间就淘汰；
5. 合格解里挑代价最小的：`0.9×姿态偏离 + 0.7×站位偏离 + 1.2×横向出界 + 0.06×耗时`。
   站位的权重高于姿态——宁可屈膝 20cm，也不愿意为了舒服退到底线外一米。

一个都不合格时**不回到中线**，挑「高度差 + 赶得上」综合最好的那个继续追：球已经发出去，
站着看它落地是更差的选择。而球**已经越过拍面所在平面**（`state.z + c.z + 0.15`）时反过来
——原地站住不动，追着球往后跑只会变成「球贴着我飞、拍子够不到」。

五个设计点值得记住：

- **目标是拍面中心，不是握点。** 中心挂在握点沿拍柄 0.6m 处（`pos + R(q)·(0, FACE_CY, 0)`）。
  握法一横，中心就在握点侧方半米，而判定半轴只有 0.24m —— 只把握点对准球，横握时永远打空
  （实测命中率 0/12）。所以 `c` 必须参与运算，`x` 与 `z` 都是 `p - c`。
- **`c` 是两份相加，不是一份**（11-14 晚）。挥拍中段中心会被甩出 0.3–1.1m，所以不能直接用
  实时 `faceCenter`——那是 4.5 已经解决过的「一挥拍人被拽着跑」。但只估「站着不动」的那一份
  也不对：真挥起来拍子转 40–80°，拍面中心在**击球那一刻**已经离瞄准点 40–60cm，比判定盘
  半轴（0.20 / 0.24）还大。于是拆成：

  | | 来源 | 更新方式 | 用途 |
  |---|---|---|---|
  | `restOffset` | 实时 `faceCenter − 基座` | 角速度 < 1.2 rad/s 的帧，τ=0.3s | 握法（横 / 斜 / 竖） |
  | `contactDelta` | 命中那一刻的 `faceCenter − 基座` − `restOffset` | 每命中一球 EMA 0.45，逐帧 τ=0.45 收敛 | 挥拍扫出去的那一段 |

  `planOffset = restOffset + contactDelta`，喂给 `planAutoMove` 的 `center`。
  实测瞄准误差（`scripts/probe-contact.cjs`，球到拍面那一刻的真实拍面 vs 瞄准点）：

  | 握法 | `MODE=rest`（只学握法） | `MODE=contact`（再学挥拍扫出去那段） |
  |---|---|---|
  | 斜握 14° | 0.128m | **0.048m** |
  | 横握 | 0.303m | **0.192m** |
  | 竖握 | 0.406m | **0.278m** |

  `contactDelta` 只在**命中**时学：漏接的姿态不代表「击球那一刻」。竖握/横握收敛不到
  0.05，是因为挥拍扫出去的方向本身随挥拍相位变，一个常量补不平——剩下的缺口由玩家
  自己对准（`docs/known-issues.md` 第 1 条）。
- **预测和回球机共用 `physics` 里的弹道工具**。`predictAtPlane` 给单平面，`sampleCrossings`
  给区间曲线；两边不一致会出现「机器算的点对得上、人算的差半米」。
- **`stepAxis` 是「有多少走多少、到点就停」，不是指数收敛**。指数收敛永远差最后一点点，
  球到面时还差 10cm 就擦框。执行器整体是 `stepAutoMove(cur, plan, tg, dt)`，主循环和
  `probe-jitter` / `probe-contact` 都调它，**不要再在探针里抄一份**（抄的那份一漂，探针量到的
  就不是玩家身上的行为）。
- **高度分两段**（11-14 晚）。`eta > heightLead`（0.45s）时目标只许偏离中立位 `±heightBand`
  （20cm）、速度 `speedYSlow`（1.8 m/s）；随着 `eta` 变小，开闸权重 `w = (lead − eta)/lead`
  把目标连续推向 `tg.y`，到面那一刻是满行程（`speedY`=6 m/s）。硬切会在 `eta === lead`
  那一帧让目标跳一次、人反向一次（探针里 y 反向 0.04 次/球）。为什么要这么绕：老行为全程
  9 m/s，一帧 15cm，抬起来是一瞬间、球一过又弹回 1.3m，看到的一直是回位后的姿势，读起来
  就是「拍子高度永远不变」。
- **目标和步进之间必须有 `TargetHold`**（11-14）。`planAutoMove` 是每帧独立重算的纯函数，
  相邻两个候选平面（采样网格跟着球往前滑）代价常常只差千分之几，排序每帧翻一次：
  `targetZ` 在 0.30 / 0.36 之间跳，`stepAxis` 当成「真的要挪」按满速走 6cm 再走回来 ——
  60Hz 的 ±6cm 方波，人站在那儿前后抖，相机也跟着晃。`TargetHold.resolve(plan, now)`
  只做一件事：新目标离上一次的不到 `holdR` 就当没听见；超过就是真的换落点，一次跳过去
  （由 `stepAxis` 的速度上限拉成几帧）。另外两层：`chasing` 翻 false 之后先保持原地
  250ms（球刚过去那几帧正是随挥，这时候回位就是「击球瞬间拍子猛地一抖」，`speedY` 是单帧
  10cm），回位那一段的 y 也用 `homeSpeed`（3.2）而不是对位的 6。
- **`holdR` 必须严格大于采样步长**（11-15，`holdR` 0.10 → 0.14 = 1.4 × `CROSS_STEP`）。
  这条不是拍数拍的：候选点沿弹道按 `CROSS_STEP`=0.10m 采，**相邻两个候选的距离就是 0.10m**，
  阈值取 0.10 等于「和它要过滤的东西同一个量级」——两个候选交替胜出时每次切换 0.101，
  刚好越过阈值，判据形同虚设。实测横握 741–743 帧连翻两次（`(y1.229,z0.000)` →
  `(1.301,-0.083)` 0.110 换过去 → `(1.235,-0.006)` 0.101 换回来），握点跟着反向一次，
  单帧最大位移 0.113m。改成 1.4 倍后三种握法反向次数全 0。
  取 1.4 而不是 2：z 走一格 0.10、y 沿弹道跟着抬 0.03，合起来 0.104，1.4 倍留 4cm 余量；
  再往上就会把「真的换落点」也开始吞掉。
- **y 轴是「举拍 / 屈膝」，不是「站高站低」**。它只在选点时参与反解：球高 1.5m、竖握
  `c.y`=0.6 ⇒ 握点得在 0.9m。这一维缺了会怎样：握点锁死 1.3m 时竖握拍面恒 1.9m，来球
  1.3–1.6m 全从拍面**下方 20cm** 掠过，实测命中率 0/42（横握 34/38，因为 `c.y`=0）。

纵深范围 `minZ = NET_Z + 4.0`（网前 4m）、`maxZ = HIT_Z + 1.0`（底线内）。前端改过三轮
（-0.55 → -2.7 → -6.5），每一轮都是被同一类球逼的：「机器一记软球落在 z≈-8、弹一下在
z≈-1.4 就二次落地」（vz=13 / vy=5.5 那一条：-8.01 → -1.40），人得往前迎 2–3m 才有球可打；
-2.7 那一档仍然够不到「第二落点还在网前几米」的短球——`sampleCrossings` 在第二次落地处
截断，于是那个范围里**一个候选平面都没有**，`planAutoMove` 直接返回 `home`，人站着看球弹
两下。横向同理：3.9 是按「站在线上不算出界」定的，而那是**球**的规则，卡在场内等于
「边线球必失」，11-15 放到边线外 1.5m（`maxX`=5.6）并把跑速提到 5.4。
后端从 +2.0 收到 +1.0，因为「球高了」现在由 y 轴解决，不再需要退到场外去等球掉下来
（那正是旧版把人拖到 z=1.9 却还是差 28cm 的原因）。

## 3.10 挥拍枢轴：腰 → 肘 → 腰（`core/swing-rig.ts`）

球拍的位姿一直是「握点 × 手机姿态」：握点钉在走位给的那个点上，整支拍子绕着它转。
玩家反馈「像绕拍柄底部转的棍子，不像挥拍」。真网球拍是三段式：

1. **转腰带动**——手跟着肩走一段弧，拍头在更外面；
2. **手肘制动**——击球前一刻大臂减速、肘几乎停住，拍头绕肘甩出去（拍头 20 m/s，手 3 m/s）；
3. **随挥**——又回到绕躯干转，拍子收在身体另一侧。

手机只测得到握点的朝向，测不到躯干和肘在哪。所以这一层不去反解骨架，只给握点补上
它**本来就该有的那段平移**：把整支拍子绕一个虚拟枢轴转同样的角，枢轴按手部角速度在
腰与肘之间切换（`smoothstep(6, 18, spin)`，τ=60ms 平滑）。速度回落就自动回到腰，
「起势 → 击球 → 随挥」不需要状态机。

三个判据决定了它能不能用：

- **用拍柄方向的最小弧，不用姿态增量。** 手腕内外旋（绕拍柄轴自转）在姿态里角度很大，
  但它不该让握点位移——手心转一下只是拍子原地翻面。取拍柄方向 `q·(0,1,0)` 从准备姿态
  到当前姿态的最小弧，自转对它是零，扫拍对它是全额。
- **准备姿态是慢速跟踪出来的**（`spin < 1.2 rad/s` 时 τ=0.5s 跟过去）。换握法、alpha 慢漂、
  按 `R` 重标定都靠它吸收；不跟踪的话，每帧从当前姿态出发，转角恒为 0，等于没做。
- **位移必须限幅（`maxShift` 0.18m）。** 走位瞄的是**挥拍前**那个拍面中心，枢轴把拍面
  搬走多少，就少多少命中余量。下表是墙打时代的模拟器 A/B（`RIG=1` + `sim-e2e`，五档 × 6
  种子）——那套脚本已随模式删除（`docs/history.md` 4.27），但**这几个数依然成立**，
  它们量的是「拍面被搬走多少 → 判定还剩多少余量」这条几何关系，与喂球是谁无关：

| 位移限幅 | 总击球 | 漏接 |
|---|---|---|
| 0（老行为） | 396 | 0 |
| 0.06 / 0.08 / 0.10 / 0.15 / 0.20 | 396 | 1（同一例，28 rad/s、拍柄扫过 149°） |
| 0.35 / 0.60 | 396 | 2（拍面被搬到球下方 0.85m） |

  0.20 以内不比 0.08 差，说明扫掠判定对「拍面被搬走一点」很宽容；取 0.18 是留一半余量
  给喂球自身 ±0.12 的顶点散布。`gain`（0.4）只缩转角不缩半径——缩掉的那部分转动本来就
  发生在手腕和肘上，视觉上是「手走的弧比拍头短」，真实挥拍正是这样。

`RacketPose` 同时喂渲染和 `sweepFace`，所以看到的弧永远等于判定的弧。代价是球到面那一刻
拍面中心偏了一段（40° 转角时约 12cm），这在判定盘半轴（横 0.20 / 竖 0.24）以内。
`G` 键 / `?rig=0` 关掉它回到老行为（真机 A/B 用）。

## 3.11 网络与时钟

- 两条 DataChannel：`ctrl` 可靠有序（时钟同步、控制指令），`imu` **不可靠无序**（60Hz 传感器数据）。不要用 WebSocket 传高频传感器：TCP 队头阻塞，Wi-Fi 抖一下就是几百毫秒。
- 包格式 68 字节（seq / tSend / **tSample** / 四元数 / 角速度 / 加速度 / 峰值），**保留 60 字节旧格式解码**。手机浏览器缓存顽固，改协议后不刷新就「一条包都收不到」。
- 大屏 `ping`，手机必须回 `pong {t0,t1,t2}`。曾经手机端只处理 `recal`、没有 ping 分支，导致 `ClockSync.isValid` 永远 false：延迟全显示 `—`，且 `tLocal` 退化成包到达时刻，挥拍时间窗系统性偏晚一个单向延迟。**这类「有兜底就看不出来坏了」的模块，必须有肉眼可见的指标。**
- `端到端 = now - toLocal(tSample)`，`网络` 只算 Wi-Fi + 排队，两者之差就是手机那一段（采样等待 + 发包排队）。
- NTP 偏移公式 `θ = ½[(t1-t0)+(t2-t3)]` 算出的是「远端比本地快多少」，换算到本地要**减**。符号写反不会报错，只会让延迟变成负数或大得离谱。

## 3.12 计分与发球几何（`core/match.ts` + `core/serve.ts`）

对打的规则层。两块都是**纯函数 / 纯状态机**，一个 DOM 都不碰，所以它们能被单测钉到
很细——11-14 新增的 17 项、11-15 又加的 9 项，全部落在这两个文件（外加走位边界）上。

### 计分：`TennisMatch`

存**原始计数**而不是 0/15/30/40：平分和占先是相对关系（40-40 后领先一分显示 `AD`，
被追平又显示 40），存绝对值就不得不在每一处判断前后关系。判定只有三条：

```
局：points[i] >= 4 && points[i] - points[j] >= 2
盘：games[i]  >= 6 && games[i]  - games[j]  >= 2
抢七：points[i] >= 7 && points[i] - points[j] >= 2   → 直接赢盘（一盘制）
```

显示时换算一次（`pointLabel`）。`serveCourt()` 读 `(points[0]+points[1]) % 2` 的奇偶，
`serveServer()` 在抢七里按 1-2-2 轮转，**不能**直接返回 `server` 字段。

`Duel` 只在「这一分归谁」定下来之后调一次 `awardPoint()`，照返回的 `PointOutcome`
决定播 `game` / `tiebreak` / `matchOver` 哪个事件。**规则层不知道球、不知道场地、
不读时钟**，所以想换成三盘两胜只是改这一层。

### 发球几何：坐标先对齐

玩家在 +z 侧、面朝 −z，右手边是 **+x**；机器在 −z 侧、面朝 +z，右手边是 **−x**。
发球要发到**接发方的右区**，于是玩家的右区发球落点是 `x<0`。这个符号在
`serveBox` / `serveStandX` 里各定义一次，**别在别处再推一遍**——这一层最容易出的错
就是左右搞反，而且错了以后「发球有 50% 的概率直接失误」，看起来像难度设定。

### 发球判定：为什么不是 `sweepFace`

拍面碰撞用的是「球段与椭圆盘的平面穿越」（`sweepFace`）：球必须从平面的一侧穿到
另一侧，`n0` 与 `n1` 异号。但**竖直抛球 + 竖直拍面**时球是**沿着**平面走的，
`n0/n1` 永远同号，一次都判不到。

所以发球改成**球形判定**（`tossContact`）：取球在这一子步内离击球区中心的最近点，
距离小于 `SERVE_REACH`=0.42 就算碰到。0.42 = 拍面竖直半轴 0.19 + 球半径 0.034 + 明显
更宽的余量——发球是一次主动的、抛起来打的动作，不该像接杀那样苛刻（0.34 那一档实测
「等球落进来」的窗口只有 0.2 秒）。

**击球区中心不是拍面中心**，而是 `serveStrike(pose)`：以握点上方的锚点为基准
（上方 0.53m、前方 0.25m），拍面中心离它超过 `SERVE_ANCHOR_R`=0.35m 就朝它收。
这是 11-15 的改动，理由见下面的「抛球锚点」。

额外一条：**只认下落段**（`vy <= 0.5`）。出手点在锚点下方 0.1m，本来就在判定球里，
不卡这一条，抛出那一帧随手一挥就把球打出去了；卡住之后击球点在 2.45m 左右的下落段。

### 抛球锚点：不能锚在拍面中心

拍面中心挂在握点沿拍柄 0.6m 的杆子末端，位置**由手机朝向决定**：竖握在头顶
（2.22m）、横握在胸前 0.6m 外、斜握在斜前方。旧代码 `startToss` 就取
`faceCenter(pose)`，于是同一句「抛球」在三种握法下抛到三个地方——玩家把拍子举到
头顶时球不在那儿，既打不着也发不进区。

现在抛球点、击球区都锚在**握点**上：`SERVE_STRIKE_UP/FWD`（上方 0.53、前方 0.25），
与手机怎么转无关。抛球从 2.05m 以 5.2 m/s 上抛，顶点 3.43m（比举高的拍面高 1.2m），
落回击球区约 0.95 秒。

### 发球落点：左右压灵敏度，纵深映射

```
axis   = aimAxis(face, shaft)        → 双面拍翻正；法线朝天时改用拍柄当准星
pitch  = asin(-axis[1])              → 映射到区内深浅
u      = (pitch - 3°) / (18° - 3°)   夹到 [0,1]
z      = zDeep + (zShort - zDeep)·u  zDeep = 发球线+0.7，zShort = 网-1.0
yawEff = yawBox + (yaw - yawBox)·0.65   yawBox = 指向区中心的偏角
x      = contact.x + tan(yawEff)·(contact.z - z)
```

**纵深为什么不直接取射线与地面的交点**：落点纵深就由俯角唯一决定，而从 2.5m 高、
14m 外的发球区看，能落进区的俯角窗口只有 7.2°–10.8°（宽 3.6°）。手机上这比走钢丝
还难，而它不是技术，只是几何太窄。映射之后整段 15° 都落在区里，玩家只需要控制
左右——那才是网球发球真正的难点。

**左右为什么只压灵敏度、不夹**：按射线求交时，对角发球区从发球位看只张开
**15.6°**（指向左边缘 −20.4°、右边缘 −4.8°），偏 8° 就出区。所以 `YAW_GAIN`=0.65
把「相对区中心的偏角」压缩再用，合法窗口撑到 **23°**，中心仍对准区中心。
转过头仍然出区——「必须发到正确的区」这条规则不能白送，而把偏角直接映射到区宽
就等于把失误抹掉了。

### 双面拍：`frontFace`

网球拍是双面的，正手打正面、反手打背面，几何上完全等价。但设备只给一根 +z 法线，
反手时手机翻了个面，这根法线指着玩家身后。`shotFromStroke` 的
`alignment = dot(face, FORWARD)` 是**有符号**的，于是反手判出 `alignment ≈ -1`、
走「拍面背对球场」那条分支，球飞回自己半场——「反手接不到球」。

`frontFace()` 只在**明确朝后**（`face[2] > 0.12`）时翻面，于是：

- `Stroke.face` 永远是「朝球场那一面」，下游不用再想这件事；
- `clean` 的含义变成「拍框没有正对来球（侧着 90°）」，那才是真实网球里打不出去的那种；
- 拍面接近水平（屏幕朝天）时 z 分量在零附近抖，所以不翻——否则出球方向会在上下之间跳。

判定层（`sweepFace`）本来就不需要它：椭圆盘对法线正负号不敏感，这也是为什么这个 bug
的表现是「碰得到、但接不回去」而不是「碰不到」。

## 附：一局的数据流（从挥拍到出球）

```
[手机] deviceorientation 25–35Hz
   → attitude 四元数（yaw 归零）
   → 60Hz 打包（68B，含 tSample）
   → WebRTC imu 通道（unreliable/unordered）
   ↓
[大屏] 解码 → ImuTracker / 直接绝对姿态
   → SwingDetector.push(omega, q)        迟滞 + 峰值保持
   → 结算出 Stroke（t = 峰值时刻）
   ↓
[大屏] syncRacket(now, dt)
   → 自适应平滑（τ 3/10/22ms）
   → RacketPose { t, pos=握点, q }
   → three.js 渲染 + duel.pushRacket（同一份）
   ↓
[大屏] duel.update(dt, now)
   → 机器侧：machine.update → pickIntercept → moveToward → attemptReturn
   → advance 240Hz 子步
        → sweepFace(pose(t_sub), p0, p1)：玩家拍面、机器拍面各判一次
        → 玩家命中 → 试 takeStroke（已结算或 liveStroke 抢跑）→ 出球
        → 机器命中 → attemptReturn（aimIntoCourt 反解）→ 出球
   → 落地 / 撞网 / 飞出范围：判这一分归谁 → wait → 下一分
   ↓
[大屏] scene.setBall / 音效 / 特效 / HUD
```

关键点：**判定发生在 240Hz 子步里，用的是插值到那一时刻的拍面位姿；出球发生在同一帧，不等网络。** 这两条是「手感不黏」的全部秘密。
