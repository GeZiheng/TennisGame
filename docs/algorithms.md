## 3.1 姿态链路：手机 → 大屏 → 球拍位姿

```
deviceorientation (alpha/beta/gamma)
  → attitude.deviceEulerToWorldQuat   R = Rz(α)Rx(β)Ry(γ)，再左乘 EARTH_TO_WORLD = Rx(-90°)
  → toOutputQuat                      只归零绕世界 Y 的朝向（yawZero 懒锁存）
  → 网络（60Hz，68 字节包）
  → PlayScene.syncRacket              自适应平滑 + 组装位姿
  → Rally.pushRacket                  每帧必推
  → RacketTrack.at(t)                 400ms 滑窗，按时间戳 slerp
  → sweepFace                         物理子步求交
```

四个不能改的约定：

1. **球拍本地轴 = 手机硬件轴**：拍柄 +Y（手机长边），拍面法线 +Z（垂直屏幕）。设备→球拍是单位矩阵。
2. **屏幕旋转补偿是错的，已删除。** 设备坐标系焊死在硬件上，与 `screen.orientation.angle` 无关。按它补旋转会让横握时球拍整体歪 90°。
3. **姿态用绝对姿态，不积分陀螺仪。** 陀螺仪只给角速度，积分出来是相对启动时的增量，没有重力参考。拿不到方向事件时才退回陀螺仪积分。
4. **平滑是自适应的**（`scene.syncRacket`）：等效角速度 `spin` > 12 rad/s 时 τ=3ms（几乎不平滑，拍子完全跟手），> 4 时 τ=10ms，静止时 τ=22ms。固定 22ms 会让快挥时拍面滞后 44cm。

**渲染与判定必须用同一份 pose。** `syncRacket` 返回的 `RacketPose` 一边喂给 `rally.pushRacket`，一边用来设置 three.js 的 `position/quaternion`。如果渲染和判定各算一份，就会出现「看着碰到、判定说没有」。

## 3.2 挥拍检测：迟滞 + 峰值保持

`src/core/swing.ts` 的 `SwingDetector` 是一个状态机，不是三点峰值比较。

原因是频率对不上：大屏 60Hz 发包，而 `deviceorientation` 常常只有 20–35Hz。走姿态差分兜底时，同一个角速度值会被连发 2–4 次，序列里出现平台段；「严格大于左右邻居」在平台段上恒不成立，整次挥拍被静默丢弃。曾出现「球到面 43 次、挥拍只记到 1 次」。

判据：

```
越过 SWING_THRESHOLD(3.0 rad/s) → armed，跟踪这一路的最大 |ω| 及其时刻
回落到峰值的 FALL_RATIO(0.9)     → 结算，用**峰值那一刻**的姿态建拍
超过 SWING_MAX_MS(450ms) 没回落 → 那是「转」不是「挥」，丢弃
冷却按两个峰的真实间隔算，不受结算延迟影响
```

**`FALL_RATIO` 是整条链路里对手感最贵的参数。** 结算发生在峰值之后，球什么时候被打出去就跟着晚多久：

- 0.75：峰值后 50–90ms，超过人的视触同步阈值（50–80ms），能明显感觉到「球被吸住」
- **0.90：峰值后 1–2 帧（16–33ms），低于感知阈值**
- 不能取 1.0：平台段上 w 恒等于峰值，「跌到峰值以下」永远不成立，一次都不会结算

**抢跑 `liveStroke`**（`Rally` 构造注入）：`takeStroke` 找不到已结算的挥拍时，直接向检测器要一份「正在进行中」的峰。球到面的那一帧就出球，`出球` 诊断恒为 0。配套 `consumeLive()` 后置 `blocked`，要等 w 跌破 `SWING_THRESHOLD*0.7` 才解锁，否则同一次挥拍会被再结算一次。

**角速度双通道**（`controller/sensors.ts`）：`devicemotion.rotationRate` 和「姿态差分」（`gyro.omegaFromQuatDelta`）都记录，双向判定该信谁——rotationRate 出现过大读数就一直信它；一直为 0 而差分在动就切差分。只判一个方向的话，坏机器永远切不过去。

## 3.3 出球模型：`shotFromStroke`

不追求物理正确，追求「玩家意图能被兑现」：

```ts
dir   = normalize(face * 0.72 + headDir * 0.30 + [0, 0.06, 0])
speed = clamp(dot(head, dir) * 0.85 + 3, SPEED_MIN=18, SPEED_MAX=32)
clean = dot(face, FORWARD=[0,0,-1]) > 0.15
```

- **拍面法线 72% + 拍头速度 30%**：纯法线会让「挥拍方向完全不影响结果」，纯挥拍方向又让拍面控制失效。
- **拍面偏角被放大**：出球方向 72% 来自法线，10° 的拍面偏差在 10 米外差 1.24m。这是握持安装角影响大的原因。
- **速度沿出球方向投影**：横挥的能量应该变成旋转，不是凭空加到球速上。
- **拍面完全背对球场时不纠正方向**：球往后飞，玩家立刻看到「打不出去」，比文字提示直接。
- **`SPEED_MIN=18` 是物理底线，不是手感偏好**：低于它，回球从墙上弹回来会擦网或在中场趴下（13–16 m/s 实测全挂）。
- **高球惩罚 `pen`**（`rally.launch`）：击球点 > 1.35m 时 `pen = max(0.62, 1 - (y-1.35)*0.34)`，打断「连续全力挥 → 击球点一拍比一拍高 0.35m → 五拍后够不着」的正反馈。

旋转：把拍头速度分解到垂直于出球方向的平面上，向上刷 = 上旋（`topComp * 26`，限 ±420 rad/s），向下切 = 下旋，侧向 = 侧旋（`sideComp * 18`，限 ±260）。

## 3.4 弹道积分：`physics.advance` / `substep`

240Hz 定步长、半隐式欧拉（先更新速度，再用新速度走位置）。

```
重力   0.56 N
阻力   1.05 N   ← 30 m/s 平击时比重力还大，这是网球速度衰减极快的原因
马格努斯 0.2 N  ← 够让上旋球提前两米落地
```

- **阻力**：`kd = 0.5·ρ·Cd·A·|v| / m`，加速度 `-kd·v`。`DRAG_CD=0.55`（绒毛表面）。
- **马格努斯**：`F = 0.5·ρ·A·r·Cl·(v × ω)`。**叉乘顺序必须是 `v × ω`**，写成 `ω × v` 上旋会往上飘——看着「也挺像那么回事」，但旋转玩法全废。单测专门钉了一条「上旋必须比平击落得早」。
- **旋转衰减**：`exp(-h/SPIN_TAU)`，`SPIN_TAU=4s`。
- **地面**：`v[1] < -0.6` 才算一次落地。上旋落地「蹿」：水平摩擦 `0.74 + ts*0.18`（夹 0.45–0.95），竖直恢复 `0.76 + ts*0.05`，旋转衰减到 55%。低于阈值走贴地滚动分支，只做阻尼，**不计落地**（否则静止球每秒刷 240 个 ground 事件）。
- **练习墙**：`v[2] = -v[2] * 0.76`，`v[0]/v[1] *= 0.9`（软垫墙会把斜球「吸」一下）。
- **球网**：用「这一步是否跨越 `NET_Z` 平面」判断，不用距离比较。`yCross = p[1] - v[1]·h·(1-tt)`，小于 `NET_H + BALL_R` 就撞网。

`advance` 不把多帧累积到累加器：累加器会让球慢 1–3 步（4–12ms），而击球判定依赖球的位置，这点滞后直接变成「手感黏」。它把一帧拆成不等长子步，最后一步可能只有半拍。

## 3.5 拍面碰撞：`sweepFace`（核心）

**判据是「球心到拍面圆盘的距离 ≤ 球半径」，不是「球心穿过拍面平面」。**

两种判据的差别只在掠射时出现：

- 球正撞拍面（球路与拍面成几十度）：最近点在平面上，两者完全一致。
- 球**顺着拍面掠过**（球路几乎平行于拍面）：球心可能永远不穿过平面，但球体已经压到拍线上了。按「必须穿过平面」判会漏——漏掉的那 16ms 在屏幕上就是「球从拍子中间穿过去」。

实现（`core/racket.ts`）：

```ts
// 世界点 → 拍面局部系（原点在握点，+y 沿拍柄，拍面平面是局部 z=0）
a = toLocal(pose, p0); b = toLocal(pose, p1);

// 候选点：穿过平面处 + 面内离中心最近处 + 两个端点
// 挑垂距 ≤ BALL_R + FACE_MARGIN 且 (u/rx)² + (v/ry)² ≤ 1 的，取最靠中心的一个
R  = BALL_R + FACE_MARGIN
rx = FACE_RX + R;  ry = FACE_RY + R
```

- **必须做线段求交，不能做点判定**：240Hz 子步里球走 8–17cm，是球半径的 3–5 倍。球在两帧之间穿过去时两端都不在椭圆内。
- **椭圆按球半径 + 容差膨胀**：近似 Minkowski 和，中心区域精确，只在长轴端点处多算几毫米。
- **`FACE_MARGIN=0.02` 补的是位姿延迟**：判定用的拍面比玩家手里那把（也比他屏幕上看到的）平均晚 20–60ms，快速挥拍里就是几厘米。1.2cm 时会出现「视觉上明显蹭到框、判定说没有」。
- **等效判定半轴**：横向 `0.15 + 0.0335 + 0.02 = 0.2035`，竖向 `0.19 + 0.0335 + 0.02 = 0.2435`。这两个数决定了喂球散布能有多大（第 3.6 节）。

**位姿必须按时刻插值。** 拍面位姿来自渲染循环（60Hz），物理跑 240Hz，一个子步里拍面最多转 25°。`RacketTrack` 保留 400ms 历史，`at(t)` 按时间戳 slerp（不是帧序号，rAF 不是严格 60Hz）。

**子步回调返回 `false` 必须立刻 break**（`advance` 的 `onStep`）：球被接住后速度为 0，继续推进会让它往下掉一点点，而且后续子步可能重复触发碰撞。

## 3.6 喂球：弹地 + 只保证顶点在附近

### 为什么是弹地球

早期用 `feedVy` 直接把球送到拍面，有结构性缺陷：玩家退到后场时飞行 12m+、`vz` 只有 10.5，球必然中途落地；而求解器把「提前落地」当成「仰角还不够」，一路加到上限 12，于是每球都变成从墙顶飞过的月亮球——这正是「发球普遍较高、退到后场够不到」这一真机现象的根因。

弹地球把落地变成设计的一部分，同时带来两个收益：

1. **落点是视觉节拍器**：第一次落地 = 计时开始，之后球的高度单调可预测，挥拍时机可以靠看落点学出来。
2. **球速与来球高度解耦**：弹起的竖直速度由入射角决定，水平速度由落点距离决定。

### `feedBounce` 的解法

未知两个（`vy`、`vz`），约束两个（落点 `dropZ`、弹起后过拍面高度 `targetY`）。不做二维搜索，而是参数化成**发球到落地的飞行时间 `t`**：

- `t` 定了、落点定了，速度就定了（`vz ≈ dist/t`，`vy` 由抛体方程反解）
- 「弹起后到拍面的高度」对 `t` **严格单调**（t 越大 → 入射角越陡 → 弹起越高）→ 直接二分
- 二分区间 `[0.4, 1.9]`，16 次；每次 `shoot` 里再用 5 次 `vz` 修正补偿阻力（阻力会让射程缩短 10–15%）
- 一次求解约 60 次模拟，几毫秒

返回值带 `apex`（**真顶点**）：`sim` 在球穿过拍面之后继续跑到 `v[1] < 0` 才算顶点。不能用「球到拍面那一刻」代替——球还在缓升时，顶点在拍面**之后** 0.55–0.85m。

### 落点与散布

```
落点距拍面 = FEED_APEX_LEAD(2.40) − back
back ∈ [FEED_APEX_BACK_MIN 0.55, FEED_APEX_BACK_MAX 0.85]
→ 落点 1.55–1.85m
```

`FEED_APEX_LEAD = 2.40` 是实测值（抛体运动决定：弹起水平速度 3.5–5.0 m/s × 爬升到 1.6m 的 0.5–0.6s ≈ 2.3–2.45m）。**偏 0.1m，顶点就整体前后移 0.1m**，别凭直觉估，改完用 `probe-feed-scan2.cjs` 重测。

每球抽一次顶点偏移（`Rally.aimDx/aimDy`）：

```
横向 ±FEED_APEX_DX(0.12)、高度 ±FEED_APEX_DY(0.10)
```

为什么是 0.12/0.10 而不是贴着判定半轴（0.2035/0.2435）：两轴会**同时**偏，

```
sqrt((0.12/0.2035)² + (0.10/0.2435)²) ≈ 0.72   ← 留三成余量
sqrt((0.16/0.2035)² + (0.14/0.2435)²) ≈ 0.98   ← 几乎贴盘边，偶发判空
```

甜区读数因此落在 0.45–0.75：明显散开，但时机对了就在盘内。

**为什么不再精确送中心**：每球都吸在拍面同一点，玩家两拍之后就不用看球在哪一侧了，接球退化成打地鼠。这来自「不必每球都朝拍面中心喂，只要顶点在拍面附近」的设计要求。

### 落点、散布与一次性重瞄

发球时瞄的是「发球那一刻」的拍面，但球要飞一秒多。这期间玩家会走位、会转手机，而拍面中心挂在 0.6m 杆末端：转 30° 平移 31cm，转 90° 平移 85cm，判定半轴只有 20cm。

**落地重瞄 `aimAfterBounce`**（`physics.ts`）：球在我方半场第一次落地的那一刻，按「此刻的拍面」重瞄一次。落地是整条弹道上唯一不会被察觉的修正点——球本来就要在这里剧烈改向。两个未知量（`vx`、`vy`），两个约束（到 `targetZ` 时命中目标 x/y），`vz` 保持不变；无阻力解析解打底，再用真实物理试算两次。修正量限幅横向 `1.6 m/s`（2 米飞行约 20cm）、纵向 `4.5 m/s`。

**飞行途中不再改方向**（11-10 撤销 `steerToRacket`）。曾经在最后 0.55s 每帧把球带向拍面，那是追踪弹：球会在眼前明显拐弯，发球后走开 1.2m 也照追不误。撤销后球只按自己的弹道飞，「挥拍时拍面中心扫出去」的缺口由玩家自己对准。

代价是真实的，不要当成 bug 去「修」：`probe-swing.cjs` 显示球到面时拍子已转过 30° 以上就会够不着；`probe-feed.cjs` 的「发球后走开 1.2m」现在判 `reach`。sim 在正常挥拍节奏下仍 30/30，因为球到面时转角还小、落地重瞄够用。

**目标 = 拍面中心 + 本球散布，不是拍面中心本身。** 曾经写成「拍面中心 + 本球偏移」的重瞄，玩家跟着球挪半步会形成正反馈，球越推越远，最后判「够不着」。现在发球和重瞄共用「当前拍面 + 固定散布」。

### 没挥拍时：擦框掉下去

`tickContact` 等满 `CONTACT_HOLD_MS=100ms` 还没等到挥拍事件：

```ts
ball.v = [resumeV[0] * 0.12, -1.2, -2.2]   // 横向削到一成，往侧前方掉
```

**不能还原原速让球穿过拍面。** 喂球瞄着拍面中心，所以「没挥」这个结局每球都会演一次；演成「原速穿过」，玩家的结论必然是「碰撞坏了」。擦框掉落和 HUD 那句「漏接」对得上。

## 3.7 回球补偿：`liftOverNet`

目的：保证这一拍打过去以后，球能自己飞回来、回来时在够得着的高度。手机测出来的挥拍速度比真球拍低不少，轻挥可能只有 13 m/s，按这个速度直线打出去必然下网。

流程：

1. **先试玩家自己的弧线**（`probe(p, v, ...)`）。能用就一点都别改——补偿的职责是兜底，不是替你选球路。
2. **扫描仰角** `vy = 0 → 13`，步长 0.4。起点是 0，不是 `max(v[1], 0)`：原来「只许抬高、不许压低」的前提是「压低一定下网」，但球撞的是墙，压平后撞墙更低、回来也更低，照样过网。这个下限卡死过一整档（全力挥出射仰角本身 6 m/s，33 次试探全失败）。
3. **每条候选跑一遍完整往返**（`probe`）：打出去 → 过网 → 网前可落地 → 撞墙 → 弹回 → 穿回拍面。验证用**和游戏内同一套 `sweepFace`**，不是「竖平面高度窗口」。

   `probe` 的几条硬约束：
   - 撞墙/撞网必须用**碰撞事件**判断，不能用「位置是否越过某个 z」——碰撞后位置会被修正回墙外，`p[2] <= WALL_Z` 永远不成立。这个坑让所有轻球被兜成 6 米高吊球。
   - 允许墙前落地（否则慢球只能打墙上空 = 月亮球），第一跳必须过网（落在我方半场 = 没打过去），墙前最多 2 跳。
   - 撞墙后重新计落地次数，≥2 判失败。
   - 盘形判定下「到平面」不算数：越过 `targetZ + 0.8` 还没碰上拍面 = 够不着。
   - 出球腿不检查（球一开始就贴在拍面上，前几个子步必然假命中）。
   - 撞墙高度 > `WALL_H + 0.05` 的弧线不进池子（那是物理在一面不存在的墙上弹了一下，回球会从天上砸下来在脚前大力弹起）。全都超墙高时才退而求其次。

4. **合格池随机挑**：`offCenter <= RETURN_OFF_TOL(0.55)` 且撞墙合规的候选进池，随机挑一条。不再挑「最居中」——每拍都回甜区正中会让玩家只看时间不看球。粗网格 0.4 可能跳过好解（实测同一拍 `vy` 差 0.2，偏离从 0.75 跳到 0.09），**池子空时**才在最优候选附近按 0.1 补一圈。

5. **传进去的位姿要「归一」**（`rally.launch`）：

```ts
q  = 接触时刻的朝向
w  = vrot(q, [0, FACE_CY, 0])
pos = [接触点.x - w.x, aimY - w.y, HIT_Z - w.z]   // aimY = clamp(at.y, 0.9, 1.9)
```

   不能直接传挥拍中的实时 pose：那时拍面中心被甩在半米外，补偿器变成「让回球穿过一个飞在半空的拍面」，所有候选不合格 → 池子空 → 兜底弧线 → 偶发撞网（实测 25 局 1 次）。但**朝向必须保留**——斜拍面能不能兜住球是真实约束，11-04 那个 bug 正是靠它抓住的。

## 3.8 状态机 `Rally`

```
dead --(1.3s)--> incoming --(球碰到拍面)--> contact --(挥拍事件)--> outgoing
                   |                          |  (100ms 超时)            |
                   |(球从身后飞过)             +--> 擦框掉落 + 漏接      |(过网) streak++
                   +--> 够不着 / 死球                                   |(撞网) 死球
                                                                       |(撞墙) --> incoming
```

- `phase === 'contact'` 时 `update` 直接走 `tickContact`，不推进物理。
- `enterContact` 先记诊断（`reaches` / `atY` / `offCenter` / `lastHit`），再判死——就算这一拍没打好，玩家也需要知道球从哪儿过去。
- 进 contact 时**立刻试一次** `takeStroke`：玩家提前挥拍的情况占多数，这条路径不需要任何等待。
- `launch` 里 `lastLatency = now - contactAt`。抢跑生效时接近 0；靠结算会有几十毫秒。
- 连拍**只在球过网那一刻 +1**，撞网/漏接归零。不在击球瞬间加：那样撞网会先涨再归零，看着很怪；也不在 `launch` 里加，因为击球点常常就在网前，球还没过网。
- 「够不着」判定线：取握点 z 与拍面中心 z 的**较大者**，再加 `BEHIND_PAD=0.35`。球跟着拍面中心飞，拍面可能因为倾角落在握点前方几十厘米。
- 撞墙必须把 `phase` 从 `outgoing` 改回 `incoming`。曾经忘了这一步，球都飞到眼前了状态机还以为「我刚打出去」，一球之后所有按阶段判断的逻辑全部停摆。

`RallyDiag` 六个数：`swings`（收到挥拍次数）、`reaches`（球到面次数）、`lastLag`（时差，正=挥晚）、`lastAtY`（到面高度）、`lastOffCenter`（甜区，1=拍框内沿）、`lastLatency`（出球延迟）。HUD 还多一个「拍面」偏角。

## 3.9 主循环顺序（不能换）

```ts
updatePlayer(dt);                              // WASD 走位
lastPose = scene.syncRacket(now, dt);          // 先平滑球拍并取位姿
rally.pushRacket(lastPose);                    // 每一帧都要推
for (const e of rally.update(dt, now)) handle(e);
scene.setBall(rally.ball.p, rally.ball.spin);
scene.render(dt);
```

先判定再平滑 → 拿到的是上一帧姿态，快速挥拍会偏几十度，越用力越容易空。

## 3.10 网络与时钟

- 两条 DataChannel：`ctrl` 可靠有序（时钟同步、控制指令），`imu` **不可靠无序**（60Hz 传感器数据）。不要用 WebSocket 传高频传感器：TCP 队头阻塞，Wi-Fi 抖一下就是几百毫秒。
- 包格式 68 字节（seq / tSend / **tSample** / 四元数 / 角速度 / 加速度 / 峰值），**保留 60 字节旧格式解码**。手机浏览器缓存顽固，改协议后不刷新就「一条包都收不到」。
- 大屏 `ping`，手机必须回 `pong {t0,t1,t2}`。曾经手机端只处理 `recal`、没有 ping 分支，导致 `ClockSync.isValid` 永远 false：延迟全显示 `—`，且 `tLocal` 退化成包到达时刻，挥拍时间窗系统性偏晚一个单向延迟。**这类「有兜底就看不出来坏了」的模块，必须有肉眼可见的指标。**
- `端到端 = now - toLocal(tSample)`，`网络` 只算 Wi-Fi + 排队，两者之差就是手机那一段（采样等待 + 发包排队）。
- NTP 偏移公式 `θ = ½[(t1-t0)+(t2-t3)]` 算出的是「远端比本地快多少」，换算到本地要**减**。符号写反不会报错，只会让延迟变成负数或大得离谱。

## 附：一局的数据流（从挥拍到出球）

```
[手机] deviceorientation 25–35Hz
   → attitude 四元数（yaw 归零）
   → 60Hz 打包（68B，含 tSample）
   → WebRTC imu 通道（unreliable/unordered）
   ↓
[大屏] 解码 → ImuTracker / 直接绝对姿态
   → SwingDetector.push(omega, q)        迟滞 + 峰值保持
   → 结算出 Stroke（t = 峰值时刻）
   ↓
[大屏] syncRacket(now, dt)
   → 自适应平滑（τ 3/10/22ms）
   → RacketPose { t, pos=握点, q }
   → three.js 渲染 + rally.pushRacket（同一份）
   ↓
[大屏] rally.update(dt, now)
   → incoming: 球速不再被改；落地弹起时 aimArrival 重瞄一次
   → advance 240Hz 子步
        → sweepFace(pose(t_sub), p0, p1)
        → 命中 → enterContact：球冻结在命中点，试 takeStroke
             → 有挥拍（已结算或 liveStroke 抢跑）→ launch
             → 没有 → 每帧试，100ms 后擦框掉落 + 漏接
   → launch: shotFromStroke → pen → liftOverNet(归一位姿) → outgoing
   → 过网：streak++；撞网/两次落地/够不着：kill → 1.3s 后 serve
   ↓
[大屏] scene.setBall / 音效 / 特效 / HUD
```

关键点：**判定发生在 240Hz 子步里，用的是插值到那一时刻的拍面位姿；出球发生在同一帧，不等网络。** 这两条是「手感不黏」的全部秘密。
