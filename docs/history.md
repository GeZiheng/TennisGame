# 修改历史

> 原为 `AGENTS.md` 第 4 节，2026-11-09 拆分独立成篇。按时间顺序，每条记录：**现象 → 根因 → 改动 → 验证**。
> 被否决的方案也记下来，避免重走。
>
> 只在两种时候读：① 想知道「现在这段代码为什么长这样」；② 想改某处之前确认有没有人试过。

## 4.1 2026-11-01 · 立项与技术选型

需求：用传感器做体感操作的网球游戏。

确定三条约束（形态 = 大屏 + 手机、硬件 = 只用现有手机 0 成本、范围 = 单人业余时间），选 TypeScript + three.js + WebRTC，双端浏览器。

被否掉的方案：

- **Unity 6.3 LTS**：作为正式发行时的迁移目标保留，不作为 v1 主线。
- **纯 WebXR / VR**：与「大屏 + 手机」形态冲突。
- **摄像头 MediaPipe 作主输入**：30fps 抓不住挥拍关键帧（拍头 >100km/h，运动模糊丢手腕点），只适合站位识别和教学纠偏。

关键判断：延迟红线 100ms；传感器数据必须走局域网，不能过公网；姿态用 6 轴（Madgwick 思路），不用磁力计（室内钢结构/电器干扰会跳变，宁可慢漂）。

## 4.2 2026-11-02 · P0 骨架 + 第一批真 bug

完成：three.js 球场、虚拟球拍、HUD、60 字节二进制协议、IMU、WebRTC 双通道、极简信令、二维码。

真 bug：

1. **时钟同步偏移量符号写反**。NTP 公式算出的是「远端比本地快多少」，换算到本地必须减。写反后延迟变成负数或大得离谱，且不报错。
2. **手机没有 `DeviceMotion`**：两个叠加的坑——微信 WebView 不下发传感器；`http://192.168.x.x` 不是安全上下文，浏览器静默拦截。新增 `controller/env.ts` 环境自检、本地 CA（自签红锁 → 自建 CA）、`/__lanip`。
3. **球拍姿态和手机对不上**：
   - `screenCorrection` 是错的（设备坐标系与屏幕旋转无关），已删除。横握时球拍曾整体歪 90°。
   - 只积分陀螺仪 = 没有重力参考。改成 `deviceorientation` 绝对姿态 → `Rz(α)Rx(β)Ry(γ)` → 左乘 `EARTH_TO_WORLD = Rx(-90°)`，只归零朝向。
   - iOS 上两个 `requestPermission` 必须在**同一手势内同步发起**。
4. **「能看到球、能挥拍，但打不到球」**（第一版）：手机上两条独立通道——`deviceorientation` 给姿态、`devicemotion.rotationRate` 给角速度。部分机型后者恒为 0，而 `sensors.ts` 写的是 `if (!rr || !acc) return;`，把整条事件丢掉。表现是「一切正常，只有击球静默失效」。
   - 新增 `core/gyro.ts`：`omegaFromQuatDelta`，`q_prev⁻¹ ⊗ q_cur` 得 body-frame 增量；**必须取最短弧**（w<0 整体取反），角度用 `2·atan2(|xyz|, w)` 而不是 `acos(w)`。
   - 角速度双通道 + 双向判定；`Rally.diag` 诊断条诞生。

P1 手感闭环：`vec` / `court` / `swing` / `physics` / `rally` / `audio`。三个架构选择：不做轨迹积分只做峰值检测；击球用时间窗 + 冻结；连拍只在过网时 +1。

调参踩出的数：`SPEED_MIN=20`、`WALL_REST=0.76`、`WALL_Z=-11.9`、高球惩罚 `pen`、`liftOverNet` 用扫描而非二分（回球高度对仰角不单调）。

真 bug：落地后每步重复触发 `ground`（加静止冻结 + `v[1] < -0.6`）；`probe()` 用位置跨越判断撞墙永远不成立（改用碰撞事件）；马格努斯写成 `ω × v`（必须 `v × ω`）；连拍加两次。

## 4.3 2026-11-03 · 平台段击穿、延迟、严格碰撞

**1. 「挥拍 1 / 到面 43 / 时差 未挥拍」**

根因：三点峰值检测被平台段整段击穿。大屏 60Hz 发包，`deviceorientation` 只有 20–35Hz；走姿态差分时同一个值被连发 2–4 次，`w[i] > w[i-1] && w[i] > w[i+1]` 恒不成立，整次挥拍被静默丢弃。

改法：`SwingDetector` 重写为迟滞 + 峰值保持；`SWING_THRESHOLD` 3.6 → 3.0（差分会把峰值削 15–25%）；删除 `SWING_RISE`，新增 `SWING_MAX_MS`。

顺带修：`onCollision` 的 wall 分支只推事件、不改 `phase`，导致 `phase` 永远卡在 `outgoing`，一球之后状态机停摆。

**2. 「球弹回的点明显比球拍接触的点晚」**

根因：`FALL_RATIO=0.75` 要等角速度跌到峰值 75% 才结算，峰值后 50–90ms；判定用峰值时刻（正确），但 `launch` 发生在结算时刻。

改法两层：`FALL_RATIO` 0.75 → **0.9**（峰值后 1–2 帧）；**抢跑 `liveStroke` / `consumeLive`**，球到面那一帧直接出球。新增 `出球` 诊断（抢跑生效时恒为 0）。

**3. 「p50 一直显示 —」**

根因：大屏发 `ping`，手机端 `onCtrl` 只处理 `recal`，从不回 `pong`。`ClockSync.isValid` 永远 false → 延迟窗口空 + `tLocal` 退化成包到达时刻（挥拍时间窗系统性偏晚）。

改法：加 `pong`；协议加 `tSample`（60 → 68 字节）并保留 60 字节兼容；手机端加「姿态 xx Hz」；面板「端到端」与「网络」分开。

**4. 球拍建模：羽毛球拍 → 网球拍**

拍面 25×33 → 30×38cm，框管 Ø2.2 → Ø2.6cm，加拍喉三角、14×16 拍线、握把尾盖。

两个实现坑：不能用 Torus + scale 做椭圆框（会压扁管截面），要沿椭圆采样 → `CatmullRomCurve3` → `TubeGeometry`；拍线不能用浅色（浅背景上会消失）。

**5. 拍面严格碰撞 + 走位（方案 A）**

计算量可忽略（≈60 flops/子步，占球物理 5%）。真正的难点是隧穿，不是算力。

新增 `core/racket.ts`：`sweepFace`、`faceCovers`、`RacketTrack`（400ms 滑窗 + 时间戳 slerp）、`faceCenter`。

连带改动（每个都是被严格碰撞逼出来的）：

- `RACKET_POS` 从 `(0, 1.02, 0)` 改 `(0, 0.85, HIT_Z)`。原来拍面中心在 1.62m（头顶），而且 z=0 而判定面在 0.3——球在拍子前方 30cm 被打中。
- 发球参数重做（旧参数弹到击球面只有 0.73m，正好从拍子底下钻过）。
- `liftOverNet` 增加 `targetZ/targetY`；仰角扫描起点 `max(v[1],0)` → 0。
- `CONTACT_HOLD_MS` 190 → 60。
- 走位 `WASD`，速度 4.2 m/s，`x ∈ ±3`，`z ∈ [HIT_Z-0.55, HIT_Z+1.35]`。
- 诊断「高度」改成「甜区」（`offCenter`）。

主循环顺序固定为「平滑球拍 → 判定 → 渲染」。

## 4.4 2026-11-04 · 真机三问题 + glb + 移动后打不到

**反馈（三点）**：看上去打到时球没有回弹，怀疑碰撞检测；拍面位置偏低、来球偏高，多数球接不到；球速过快，希望落点更靠近球网。

**1. 「打到了却不回弹」= 回球补偿的模型错误（核心 bug）**

`liftOverNet` 旧判据：球穿过 `z=targetZ` **竖平面**时高度在拍面中心 ±12cm。拍面一倾斜这个模型就错了——倾斜拍面是**斜的盘**，上升中的球穿过盘平面的点比穿过竖平面低 15cm（18° 实测）。补偿器因此选中 7.6–7.9m 的高吊，回球在玩家脚前以 8.4 m/s 大力弹起，从拍面下沿下 2cm 掠过 → `reach`。

修复：`liftOverNet` 加 `pose` 参数，回球腿逐个物理子步用**游戏内同一套 `sweepFace`** 验证；只在撞墙 ≤ `WALL_H` 的弧线里选；粗网格 0.4 + 0.1 细化。

**2. 拍子太低**：`RACKET_POS.y` 0.85 → 1.0，喂球高度自适应拍面中心。

**3. 球速太快**：`SPEED_MIN/MAX` 20/42 → 18/32，喂球 `vz` 15.2 → 10.5。

另外：`CONTACT_HOLD_MS` 60 → 100（挥拍事件路途 = 结算 16–33ms + 网络 20–60ms，最晚 90ms）；`FACE_MARGIN` 0.012 → 0.02（补位姿延迟）。

**4. 换 glb 球拍模型**

**需求**：用外部工具重做的网球拍模型替换现有模型（放在 `assets/` 目录下），碰撞检测仍沿用椭圆盘。

模型约定与游戏一致：柄底原点、拍头 +Y、法线 +Z、单位米。按 `FACE_RX/0.128 ≈ 1.172` 与 `FACE_CY/0.515 ≈ 1.165` 双轴缩放对齐；PMREM + `RoomEnvironment` 提亮金属材质；加载失败回退程序化球拍。运行时用 `public/models/racket.glb`（ASCII 名）。

**5. 「移动起来就打不到球」**

根因不在碰撞，在喂球：`serve` 从场地正中 `(0, 1.4, -11)` 发球，落点铺开 ±1.3m，而拍面可及半宽只有 20.35cm，差 6 倍。而且站着不动也会漏（实测球偏 0.66m 就够不着），「不动时打得到」只是运气好。

改法：发球点横向对准拍面 x ±8cm，`vx` ±10cm，`targetZ` 用 `face[2]`；`feedVy` 增加 `targetZ` 参数。

## 4.5 2026-11-08 · 弹地喂球 + 姿态精度

**反馈（两点）**：发球普遍偏高、退到后场也够不到，希望把落点控制在拍面前方一定范围，让球弹起后再接；挥拍手感仍偏怪，质疑仅靠手机姿态判断拍面朝向与拍子角度是否够准，是否需要第二个传感器（例如手臂上）以及如何实现。

**1. 弹地喂球 `feedBounce`**

根因：`feedVy` 要求球一口气飞到拍面、中途不许落地。退到后场时飞行 12m+、`vz` 只有 10.5，球必然中途落地；`heightAt` 把「提前落地」返回 -1，二分认为「仰角还不够」，一路加到上限 12 → 每球都是月亮球。

新方案：球在玩家前方 2.5–2.9m 落地（当时的值，后来拉近），弹起后穿过拍面，高度 = 拍面中心。求解参数化成单参数「飞行时间 t」，严格单调 → 二分。

连带：发球点横向收窄；测试窗口 150 → 260 帧；`probe-move` WARMUP 2s → 4s；新增「发球是弹地喂球」测试。

**2. 姿态精度分析（`docs/motion-accuracy.md`）**

结论：**传感器精度不是瓶颈**。六项误差按影响排序：

1. **握持安装角没标定** 5–20° → 出球方向放大 0.71 倍（10m 偏 0.6–2.5m）。最大的一项。
2. **姿态采样率 25–35Hz**：挥拍中段 12–20 rad/s，相邻样本差 28–38°，取最近样本误差 ±14–19°。
3. **只测角速度不测位置**：拍面只能绕握点画弧，伸拍够球做不到——只有这项必须上硬件。
4. yaw 漂移 / 磁跳变（Android 室内 5–15°）。
5. 网络延迟（不影响精度，只影响延迟感，已被 liveStroke 覆盖）。
6. 平滑滞后（快速挥拍已降到 τ=3ms，不是主要矛盾）。

建议顺序：先量（HUD 拍面偏角）→ 握持标定 → 60Hz 陀螺插值 → yaw 改陀螺积分 → 再评估硬件。第二传感器（`?role=arm`，肘→腕→拍面）约 2 周工作量，主要价值是**位置**。

已落地：HUD 加「拍面」读数（球拍法线相对正对球场的偏角）。

## 4.6 2026-11-09 · 落点、散布、锚定弯路

这一天的反馈密度最高，也走了最大的一段弯路，完整记录。

### (1) 落点太远 + 看着够到却没打到

**反馈**：落点离玩家的水平距离太远，多数球够不到；看上去够到了，实际也没打到。

三个独立问题叠在一起：

1. **落点确实太远**：`feedBounce` 写死 2.5–2.9m（从拍面算），玩家脚下就是 2.8–3.2m。
2. **球发出去之后玩家位置变了**：喂球只瞄「发球那一刻」的拍面。
3. **没挥拍时球按原速穿过拍面**：`tickContact` 等满后还原 `resumeV`。喂球瞄着拍面中心，所以每球都演一遍「球从拍子里穿过去」。

改动：

- 落点 2.5–2.9 → **1.55–1.8m**（后来定为 1.55–1.85）
- 新增 `aimAfterBounce`（落地重瞄）与 `steerToRacket`（飞行途中限 1.2 m/s 横向）
- 没挥拍时改为「擦框掉落」
- `sim-e2e` / `probe-move` 的挥拍时机从「线性外推」改成 `predictReach()` 物理前推，目标平面用拍面实际平面（倾斜 18° 差 18cm / 40ms）

### (2) 22:40「一挥拍就打不到」→ 锚定拍面中心（弯路，已撤销）

**反馈**：静止持拍时能打到，一挥拍球就从拍面中间穿过。

诊断（`scripts/probe-swing.cjs` 前身）：握点固定 + 绕握点旋转，拍面中心挂在 0.6m 杆末：

| 转角 | 拍面中心平移 | 判定半轴 |
|---|---|---|
| 30° | 0.31m | 0.20m |
| 60° | 0.60m | 0.20m |
| 90° | 0.85m | 0.20m |

球却是照着**静止时的拍面中心**喂的，于是「挥得越准（峰值正落在球到面那一刻 = 转角最大）偏得越狠」。

当时的修法分三块，**后来只有第一块被撤销**：

- `HIT_ANCHOR` + `poseFromAnchor`：位置由锚点、朝向由手机，等于把旋转轴从握点挪到拍面中心。**已全部删除。**
- `sweepFace` 改成候选点盘形判据（「球心到圆盘距离 ≤ 球半径」）。**保留**——这是真 bug 修复，掠射不再漏判。
- `rally` 里三处「拍面在哪」改用 `faceCenter`。**保留**——握点到拍面中心差 0.6m，这个区分永远成立。

验证：77 项 ×3、sim 30/30、build 通过。**但模拟器里球拍是绕拍面法线转的——法线不变，拍面中心不动，等于没测到真路径。**

### (3) 23:20「放宽喂球约束：顶点在拍面附近」

**反馈**：不必每球都朝拍面中心喂，只要弹起后的最高点落在拍面附近一定范围、玩家够得到即可。

这是放宽约束，不是修 bug。原实现有两处「强迫症」：

1. `feedBounce` 精确控制「过拍面高度 = 拍面中心」，横向只留 ±3cm。
2. `liftOverNet` 在可行弧线里挑 `offCenter` 最小的，还按 0.1 细化一圈。

改动：新增 `FEED_APEX_DX/DY`（当时 0.16/0.14）、`FEED_APEX_BACK_MIN/MAX`、`FEED_APEX_LEAD`、`RETURN_OFF_TOL`；每球抽一次 `aimDx/aimDy`；`liftOverNet` 改为合格池随机挑；`feedBounce` 返回真 `apex`。

踩坑：

- **正反馈**：重瞄目标写成「拍面中心 + 本球偏移」，玩家跟着球挪半步 → 拍面移到球的位置 → 再按「拍面 + 偏移」算 → 球又被推一份 → 越推越远。改成「只修超出容差的部分」后收敛。
- `FEED_APEX_LEAD` 第一次估 2.15（错），实测 **2.40**。
- 「时差符号」测试偶发 `lastLag=null`（散布下这一球可能没接触）→ 该测试固定 `Math.random=0.5`。

### (4) 23:50「恢复自由挥拍」→ 撤销锚定

**关键澄清**：锚死拍面中心后无法正常挥拍，要求恢复自由挥拍；并明确「打不到」是指碰到后没有回弹、球从拍面中间穿过，属于碰撞判定问题，而非拍面没碰到球。

这是整个项目最重要的一次澄清：**症状是「碰到没回弹」，不是「没碰到」。**

撤销与重做：

- 删除 `HIT_ANCHOR` / `FACE_DRIFT_MAX` / `poseFromAnchor`；`syncRacket` 回归「握点 + 姿态」；`setRacketBase` 搬握点。
- `steerToRacket` 重写为**改方向不改速率**（`want = to/t`，`t = dist/speed` ⇒ `|want| ≡ speed`），三维一次修完，只在 `bounces >= 1` 后介入。
- `aimArrival` 删掉「拍面中心 120ms 位移外推」（那速度混着挥拍旋转，手腕一转 4 m/s，会把球瞄到半米外）。
- `rally.launch` 传**归一位姿**给 `liftOverNet`（位置固定在 `HIT_Z` + 击球高度，朝向保留）。直接传挥拍中的实时 pose → 候选全不合格 → 兜底弧线 → 偶发撞网（25 局 1 次）；归一后 25/25。
- `FEED_APEX_DX/DY` 0.16/0.14 → **0.12/0.10**（合成偏离 0.98 → 0.72）。
- `STEER_LEAD_S=0.55`、`STEER_VMAX=12`、`STEER_ACC=150`。

模拟器终于测到真路径：

- 转角从「绕拍面法线」改成**绕局部 x 轴**（拍面横轴），拍面中心扫出 0.3–1.1m。
- 挥拍时机：`tta = (HIT_Z - z)/vz` 落到 75ms 内就起势。整条弹道外推会被跟随改方向带偏。
- 走位：朝球**当前**横向（不做弹道外推），且限速 5.5 m/s。两个完美跟随系统会互相带偏。

验证：77 项 ×10 连跑零失败、sim 3 × 30/30、build 通过；`probe-swing` 显示跟随关时竖挥 30°/60°/90° 全部「未接触」，跟随开后全部「打中」。

**但没有真机验证。** 见 `AGENTS.md` 第 0 节。

- `SwingDetector` 的 armed 峰、`Rally.pending` 里时间轴已错的旧挥拍也留着。

## 4.13 2026-11-10 深夜 · 位姿慢漂确证与「不重定义正前方」的补偿

**现象与关键澄清**：真机（只跑 `dev:https`、未开视觉）补到三条读数：

1. 偏差**随时间慢慢变大**，约半分钟到一分钟歪到打不到球；按 `R` 可回正，回正后重新累积；
2. **只有反手位按 `R` 才回正**，正手位按 `R` 依然歪；
3. 回正之后就能打到球，重连之后也可以。

第 3 条推翻了 4.12 里「重连后打不到不是姿态漂移的后果」这句过强的断言。`R` 的实现是大屏清统计 + 发 `recal`，手机端只做 `yawZero = null`（下一帧重锁）和清连续性状态；**`ClockSync` / `lastImuSeq` / `SwingDetector` / `Rally` 一个都没动**。只重锁朝向基准就恢复命中 ⇒「打不到」的主因是位姿：alpha 慢漂让拍面法线绕竖直轴侧过去，`sweepFace` 的盘形判定判空，球从拍面位置穿过去。4.12 的时钟 / seq 残留是重连那次的**独立叠加项**，修好之后重连时 `start()` 里的 `yawZero = null` 顺带把姿态也回正，两条一起恢复。

第 2 条说明**旧 `recal` 的语义本身就是错的**：`yawZero = qYaw(当前绝对姿态)` 等于把「此刻手机朝哪」重新定义成正前方。而 `absolute = Ry(α)·Rx(β−90°)·Ry(γ)`，手机近竖直持握时 β≈90°、`Rx(0)` 退化成单位阵，`absolute ≈ Ry(α+γ)` —— **gamma 与 alpha 同轴**，正手 / 反手换握会让 `qYaw` 差出几十上百度，重锁结果必然依赖握位。所以「自动按 R」这条路直接否决：正手位只会更糟。

**改动**（只碰姿态输出，不碰判定 / 弹道 / 喂球 / 协议 / 时钟；`MAX_POSE_JUMP` 一行没动）：

- `src/core/attitude.ts`：新增 `worldYawDelta`（世界系增量四元数 `next·conj(prev)` 读出绕 Y 转角，避开 `qYaw` 的万向锁换分支）、`isYawGimbal`、`YawDriftObserver`。观测器按**相邻帧转角幅度**分离慢漂与真实动作：`< MAX_DRIFT_STEP = 0.05 rad`（≈2.9°/帧）才积分。真机慢漂约 1–2°/s，30–60Hz 下每帧 <0.1°；挥拍中段是十几到几十度，差两个数量级。**刻意不用「静止门控」**——挥拍那几百毫秒里 alpha 一样在漂，只积分静止帧会永久漏掉那部分。
- `src/controller/main.ts`：`advancePose` 里 `effZero = yawZero + (driftOn ? drift.radians : 0)`，`toOutputQuat(abs, effZero)`。只扣「传感器多转的量」，**不重定义正前方**，因此与握位无关。补偿开启时 `recal` 不再是重锁，而是「先 `yawZero += drift.radians` 固化已扣的补偿，再 `drift.reset()`」；关掉 HUD 开关时同理。**只 reset 不固化会让拍子在这一刻突然歪回累积的漂移量**——这是状态转换的坑，别简化掉。`start()` 新会话是 `yawZero = null` + `drift.reset()`，两者一起归零所以没问题。HUD 新增可点击的「漂移 ±x°」按钮做现场 A/B，含「万向锁」标记；扫码 URL 末尾追加 `&drift=1` 可直接以开启状态接入（二维码 URL 已带 `?room=XXXX`，不是再写一个 `?`）。**默认关**：照 `?vision=1` 的先例，未真机验证的能力不默认接管输出。
- `controller.html` / `src/style.css`：HUD 元素与按钮样式。
- `tests/core.test.cjs`：新增 8 条（当时共 **97 项**、15 个分组）。其中「竖直持握时 gamma 混进世界 Y 转角」是握位依赖的数学反证；「扣掉观测漂移后输出回到启动姿态」是「不重定义正前方」的端到端反证。

**明确没做**：没有改 `qYaw` 的分解或万向锁回退分支（HUD 只做标记）；没有改握持安装角标定；没有改大屏侧任何东西；没有把补偿默认打开。

验证：`npm run verify` 全套通过（当时 **97 项 ×3**、sim 30/30 零漏接零撞网、build）。**浏览器 DOM 接入与真机效果门禁覆盖不到，补偿尚未真机验证**；取证四条见 `AGENTS.md` 0.4，重点是静置时 HUD 漂移读数是否单向增长、以及正手位打开补偿后能否打到球。

## 4.14 2026-11-11 · 快挥拍打不到 + 拍子疯狂抖：姿态跳变门限误伤真实旋转

**现象**（真机，只跑 `dev:https`、未开视觉）：挥拍速度一快就打不到球；打了一会儿之后球拍开始**疯狂抖动**。两条和 4.13 的 alpha 慢漂不同：慢漂是几十秒尺度、按 `R` 回正、偏差渐增；这条和「挥得多快 / 挥了多久」直接相关。

**根因**：两个坑嵌在 11-10 上午加的「跳变拒绝」里，都在 `controller/main.ts` 的 `advancePose`：

1. **判据只看角度、不看有没有真实运动**。`MAX_POSE_JUMP = 1.2 rad` 是按「方向事件 25–35Hz、挥拍 20 rad/s、相邻帧最多 0.8 rad」估的。但不少机型方向事件只有 20–25Hz，一次 20–35 rad/s 的挥拍相邻帧就是 **1.0–1.75 rad**，和门限重叠。于是真实快挥拍被当成「万向锁换欧拉解分支」，改用陀螺增量外推；而陀螺在挥拍峰值常被 2000°/s 量程削顶，积分出来的姿态会明显偏离手机。球到拍面那 100–200ms 用的是错姿态，`sweepFace` 判空 ⇒ **打不到**。
2. **比较基准冻结在跳变前**。`lastGoodAbs` 只在「采信绝对姿态」时更新，跳变帧不更新它。于是挥拍期间每一帧都在跟**挥拍前**的姿态比，整段挥拍乃至挥完之后都被判成跳变，卡在外推里，直到 `MAX_EXTRAP_MS = 500` 到期才强制重新接受绝对姿态 —— 这一刻又是一次大跳。大屏 `syncRacket` 在角速度大时把 τ 降到 3ms、几乎不平滑，这些跳被原样显示 ⇒ **疯狂抖动**。此外 `extrapMs += dtMs` 的两个入口（`onSample` 传真实间隔、`sendFrame` 写死 16.7）会把 500ms 兜底提前到约 250ms。

`scripts/probe-pose.cjs`（先跑 `npm test`）在纯计算层复刻旧判据并做 A/B，方向事件 25Hz、30 秒每 2.5s 一拍：

| 每帧转角 | 等效角速度 | 旧判据（挥完回原位） | 旧判据（挥完停在新朝向） | 新判据 |
|---|---|---|---|---|
| 0.4 / 0.8 rad | 10 / 20 rad/s | 0 外推帧 | 0 外推帧 | 0 |
| 1.2 rad | 30 rad/s | 51 帧 / 最长 280ms / 24 次切换 | 57 帧 / 520ms / 24 次 | 0 |
| 1.6 rad | 40 rad/s | 96 帧 / 520ms / 72 次 | 179 帧 / 520ms / 46 次 | 0 |

「切换次数」就是拍子在绝对姿态与陀螺外推之间来回跳的次数。30–60 秒里几十次大跳，正好对上「打了一会儿之后开始疯狂抖动」。

**改动**（只碰姿态连续性，不碰判定几何 / 弹道 / 喂球 / 协议 / 时钟 / 慢漂补偿的语义）：

- `src/core/attitude.ts`：新增纯计算 `PoseContinuityGate`（连同 `MAX_POSE_JUMP` / `MAX_EXTRAP_MS` 从 controller 搬进 core）。判据用**相邻两帧**的差，`prevRaw` **每帧都更新**，所以跳变只影响这一帧、不会冻结到超时；新增 `moving` —— 传感器角速度越过 `SWING_THRESHOLD` 时无条件采信绝对姿态。解分支跳变一般发生在静止 / 微动时，仍会被拦。另给 `YawDriftObserver` 加**非 Y 轴纯度判据**：增量四元数的 x/z 分量超过 0.01 就不积分，避免挥拍起收势的俯仰 / 横滚让 `effZero` 变成随机游走（补偿开启时会表现为拍子慢慢乱晃）。
- `src/controller/main.ts`：`advancePose` 只负责传 `moving` 与外推增量；`elapsed` 改用真实墙钟间隔（修掉双入口计时翻倍）；删掉 `lastGoodAbs` / `extrapMs` 两个局部状态；`recal` 与 `start()` 改调 `poseGate.reset()`。
- `tests/core.test.cjs`：新增 8 条（共 **105 项**、16 个分组），含「25Hz + 35rad/s 全程零外推」「跳变只拦一帧」两条直接反证。
- `scripts/probe-pose.cjs`：新增量化探针，固化修复前后的对照数字。

**明确没做**：没有调 `MAX_POSE_JUMP` 的数值（仍是 1.2 rad，调小会误伤真实挥拍）；没有把球追拍面 / 拍面锚定加回来；没有改大屏 `syncRacket` 的自适应平滑（修好输入后 targetQ 不再跳，改它会引入快挥拍滞后）；没有改慢漂补偿的默认关状态。

## 4.16 2026-11-12 · 对打模式：脚本回球机 + 独立服务

**需求**：在做 RL 之前先要一个脚本回球机，游戏分两种模式（对墙打 / 与回球机对打），分别启动不同的服务。墙打模式一行不改。

### (1) 为什么不换物理引擎

自研弹道积分器（半隐式欧拉、240Hz 定步长、子步轨迹回调）是为这台机器量身定的：球拍是**零厚度的椭圆盘**、不是刚体，任何通用引擎都没有对应 collider；击球判定要「线段 vs 椭圆盘」的精确求交，还需要反解「球要落在哪」时能**重放**同一套积分。换成 cannon / rapier 会得到「球拍要建成一个几何体」这个错误的抽象。对打新增的 `aimIntoCourt` 也是同一套积分的正用：粗扫 + 3 轮细化，一次求解约 0.4ms，不进 60Hz 主循环。「要不要换引擎」的结论与做 RL 无关——真要训练策略，这个积分器单核 1072–1401x 实时，够用。

### (2) 为什么必须是「对打」环境而不是复用墙打

墙打的后墙在 `z=-11.9`，网后 1.4 米。那个位置不是场地，是「球必须自己飞回来」这个前提逼出来的。要在后面站一个对手、要让球落在对方场内、要判「两次落地」，墙必须先关掉（`setWallActive`），而且对手侧要按球网镜像出完整半场（`OPP_HIT_Z = 2·NET_Z − HIT_Z`）。

### (3) 三个几何死结，全是实测撞出来的

1. **到面高度是硬约束**。玩家握点恒等于 `RACKET_POS[1]`=1.0，拍面中心只能在半径 0.6 的球壳上 ⇒ 最高 1.6m。第一版只约束落点，实测发球到面高度 **0.17m**，玩家一帧都接不到。给 `aimIntoCourt` 加 `arriveZ`/`arriveY` 之后才成立。
2. **到面高度的量测时机**。加了约束后求解器对任何目标都返回 null，因为试射在**第一次落地**就 break，而到面高度要在落地**之后**才测得到；改成「两个量都拿到才停」之后又漏了另一类合法球（球在落地前就穿过到面平面 = 玩家凌空打）。最终统一为「`land` 与 `planeY` 都拿到才停」。
3. **玩家的可及高度决定回球落点带**。球落得越靠近玩家，弹起来到击球面时就越低。要让它同时还有 1.3m 高，落点只能夹在 `z ≈ -6 … -1.5` 这一段。这条直接写进了 `ARRIVE_TARGET_Z_MAX` 与 `candidateTargets()`。

### (4) 回球机：不钉在底线

第一版把 `z` 钉在 `OPP_HIT_Z`。从底线到玩家拍面有 21.6 米，能让球「落在界内 + 到面 1.3m 高」的弹道几乎只剩月亮球。这不是求解器不行，是几何——真实球员遇到短球会往前迎。改成在全场找「最舒服的迎击点」（`pickIntercept`）之后，快球也有解，回合长度从 0.7 拍涨到 4.8 拍。

**竖直可及也必须放开**：回球机的握点给到 0.15–2.0（拍心 0.75–2.6），而玩家是 0.4–1.6。这不是放水，是对称性的必需——玩家打出来的球弹起顶点只有 1.0m 上下，拍面最低 1.22 的话它每一个球都够不着。修之前「够不着」几乎全部来自竖直方向，不是走位没跑到位。

### (5) 判分：第一落点定局

`onCollision` 原来的顺序是「先判出界、再判两次落地」。于是球合法落在对方场内、对手没接到、球继续滚出边线时，被判成**击球方出界**，得分反给了对手。`scripts/duel-sim.cjs` 的对打模拟把这个 bug 抓出来了。改成「已经合法弹过一次就不再改判」之后正常。

### (6) 前端：一份代码，两个入口

`src/play/app.ts` 是唯一实现，`main.ts` / `duel-main.ts` 各只有 `startPlay('wall')` / `startPlay('duel')` 两行。**没有复制成两份**——网络那一段（时钟同步、重连复位 `resetSession`、姿态连续性）是这个项目里最贵也最容易出错的代码，只能有一份。差异只有三处：`PlayScene` 的 mode（整场线条 + 对手球拍 vs 半场 + 练习墙）、规则对象、HUD 主数字（比分 vs 连拍）。

端口：5173/5174 墙打，5183/5184 对打。分端口不是洁癖——信令房间按房间号配对，共用端口时两个大屏窗口会互相抢手机。对打服务的 `/` 会被中间件改写到 `duel.html`，否则打开根地址会进到墙打。

### (7) 模拟脚本自己踩的坑（写在这里免得下次重踩）

- **探针必须关练习墙**。`advance` 的墙判据是「位置在墙平面**之后**」，从 `z=-21.3` 生成的球一出生就被抓到 `-11.9`。曾经据一张「没关墙」的网格图得出「只有 9–11 m/s 月亮球可用」的错误结论，那次调参全部作废。

## 4.17 2026-11-12 · 自动走位：只要挥拍，不用按键盘

### (1) 现场：为什么「够不到」

严格碰撞上线后拍面是真实的 30×38cm 椭圆，球心偏出 20cm 就打空。球的横向瞄准只发生在
**发球那一刻**（+ 落地重瞄那次 20cm 的微调），因为 4.5 撤销了「球追拍面」。于是形成
一个反直觉的结论：**站着别动几乎每球都接得到，中途按错方向跑开就够不到**。

`MOVE=off` 的实测先印证了前半句：五档力度 × 6 种子全绿，只 1 例漏接。既然球本来就来
找人，键盘走位在这套物理下**是负资产**——它最容易造成的结果是「玩家把自己从球的落点上
挪走了」。这条观察决定了功能形态：不是「加一个更强的走位」，而是「把玩家搬回球会经过
的位置」。

### (2) 只做左右，不做前后

前后（`z`）也能用：挪 z 会改「球到面时的高度」，理论上能接到更低/更高的球。但喂球和
回球机都把到面高度夹在拍面覆盖区间里（墙打瞄 `RACKET_POS[1]+FACE_CY`=1.6m，对打
`arriveY` 1.3–1.6m），这个轴上的缺口远小于横向；而自动前后走会让人在场上无意义地
进进退退，反而是负手感。先只解一维，模块形状留着（`planAutoMove` 返回 `eta`，将来
加 z 只多一个函数）。

### (3) 预测和回球机共用一份

`predictAtPlane` 原来住在 `machine.ts`，是回球机的私有工具。自动走位也要「球会从哪来」，
但两边必须给同一个答案：如果各自实现，会出现「机器算出来的点对得上、人算的差半米」这种
只在真机上才看得出的症状。所以把它提到 `physics.ts`，`machine.ts` 留一行转发导出，
`scripts/duel-sim.cjs` 一行没改。

一个容易忘的细节：**预测平面要用玩家当前的 `PLAYER.z`，不是常量 `HIT_Z`**。玩家按 W/S
前后走过之后击球面跟着走，写死常量会按旧平面算出一个偏掉的 x。

### (4) `stepAxis` 刻意不做指数收敛

「每秒最多 4.8m」+「差 5cm 以内不动」+「一步够得到就停在目标上」。不写指数收敛有两个理由：
指数收敛永远差最后一点点（球到面时还差 10cm 就是擦框）；死区不能省，否则玩家会贴着球的
正下方左右抖一帧一次。

### (5) 三路输入的优先级

> 11-13 之后只剩两路（视觉那条已删，见 4.21）：键盘 > 自动。下面这段是当时的记录。

视觉（`?vision=1`）> 键盘（`WASD`）> 自动。实现上就三条 `return`，没有状态机：视觉接管时
整帧返回；这一帧只要有一个方向键按下就走键盘、不碰自动；两者都没有才走自动。**不做
「按键后暂停 N 毫秒」的计时器**——松手瞬间接回来手感最直接。

### (6) 取证方式：给 `sim-e2e.cjs` 加 `MOVE` 开关，而不是另写一个脚本

`scripts/sim-e2e.cjs` 的走位原来是「朝球的当前横向位置跑」，本身就是个能到位的走位，
换成自动走位也是 30/30 —— 看不出差别。所以加了 `MOVE=naive|auto|off` 三档：

- `naive`（默认）历史行为，门禁按它判，**一行没改**；
- `auto` 走 `planAutoMove`，和 `app.ts` 同一份代码；
- `off` 站着不动。

`off` 的结论是「站着不动也能连打」（球瞄站位），于是真正的差别只能靠**主动制造失误**才
显出来：第 40 帧把玩家瞬移到 x=2.2，之后完全撒手。

| | 到面横向偏差中位 | 最差 | 进球心判定位 |
|---|---|---|---|
| 不动 | 0.07m | **1.60m** | 9/10 |
| 自动走位 | 0.01m | **0.05m** | 10/10 |

这条也正是写进单测的那条（`tests/core.test.cjs` 的「中途跑开 2.2m」）。

### (7) 单测：9 条，其中最值得留的是「判据自己做主」

`planAutoMove` 的早期版本靠 `predictAtPlane` 返回 `null` 来兜住「球不朝我飞」——看起来
也对，因为飞向墙的球在 3 秒窗口内穿不过击球面。但它兜不住「球就在身边横向飘」：那种球
`v[2]` 只有 0.4 m/s，照样能在 0.25 秒后穿过击球面，预测器给得出点，于是玩家会跟着一个
几乎没有前进速度的球跑。这条用例断言的是**预测器确实给得出点、而 `planAutoMove` 仍然
不追**，变异检验（把 `v[2] <= incomingVz` 改成 `if (false)`）立刻变红。

另外三条变异也验证过：去掉死区 →「死区内不动」红；去掉限速 →「一帧只挪 speed×dt」
和「左右对称」红。

## 4.18 2026-11-13 · 自动走位改成「拍面中心 + 二维」

### (1) 现场：两条反馈

4.17 的走位上线后真机试了一轮，反馈两条：

- 走位瞄的是「拍子竖直能碰到球」，但实际打球时拍子是横着的，应该按横着的来瞄；
- 只有左右走位还是够不到所有球，要加前后。

两条指向同一个被 4.17 刻意绕过的缺口：**走位的目标是握点，不是拍面中心**。

### (2) 根因：握点不是拍面中心

拍面中心在握点沿拍柄 0.6m 处（`pos + R(q)·(0, FACE_CY, 0)`）。4.17 的 `planAutoMove`
把球穿面时的 x 直接当成握点目标 x，这只在**拍柄竖直**时成立——那时中心在握点正上方，
x 与握点相同。握法一横，这根 0.6m 的杆子横过去，中心落在握点侧方半米，而判定半轴只有
0.24m。于是「人站对了、拍面在半米外」，表现就是「明明够得到却打空」。

4.17 当时不补偿，理由是「挥拍会把中心甩出 0.3–1.1m，拿实时中心当目标，玩家一挥拍人就
被拽走」（4.5 的老问题）。这个理由本身没错，但结论下错了：不能用**实时**中心，不代表
不能用**静态**中心。区别在于「挥拍甩出去的位移」和「握法造成的固定偏移」是两件事。

所以这一版的做法是：**只估计握法偏移，挥拍期间冻结**。

```ts
// 中心偏移 c = faceCenter(pose) - pose.pos，长度恒 0.6
blendCenterOffset(prevQ, q, dt, want, c, maxSpin = 0.6, tau = 0.4)
```

角速度 > 0.6 rad/s（34°/s）的帧整帧拒绝。取这个门槛的依据：静止持拍的传感器抖动是个位数
°/s，慢速调整握持 10–30°/s，而慢挥也有 100°/s 以上 —— 留一档余量，宁可少采几帧
（τ=0.4s 会补回来），也别把挥拍的甩动算进「握法」。实测这个判据的效果：换手后约 2 秒收敛，
挥拍中偏移完全不动。

### (3) 为什么必须加 z，而不是「顺便加」

站位的纵深决定「球到面时的高度」。同一个球，站前 30cm 就高 20cm 左右；而拍面竖直半轴只有
0.23m（`FACE_RY + BALL_R`）。所以高度差了，横向再准也是擦框。

4.17 不做 z 的理由是「喂球和回球机都把到面高度夹在拍面覆盖范围内」。这个理由只在**拍柄
竖直**时成立：那时中心高 1.6m，正好是喂球瞄准的高度。握法一横，中心掉到 1.0m，球还在
1.3m —— 差 0.3m，超出半轴，横向怎么走都没用。**所以「要不要做 z」和「要不要补偿 c」是
同一个问题的两面**，不能只解一半。

### (4) 选点：先筛来得及，再挑高度

沿弹道在我方可站区间每 10cm 采一个穿面点（`physics.sampleCrossings`），每个点换成握点
`(p.x - c.x, p.z - c.z)`，然后：

1. 横向超出站位范围就钳位并按半价计惩罚（球飘到边线外也要尽量靠近，不能干脆不追）；
2. 分轴估走到那儿要多久（横移 4.8 / 后退 3.6 m/s，真人倒退还更慢），超过球到面时间就淘汰；
3. 剩下的按 `|球高 - 拍面中心高|` 排序，加 `0.06×耗时` 的微弱惩罚让目标在两帧之间连续。

一个都来不及的时候**不回到中线**，挑「最赶得上」的那个继续追——球已经发出去了，站着看它
落地是更差的选择。

### (5) 纵深从 +1.35 放宽到 +2.0

第一版只把 z 加到 +1.35（底线外 0.15m），横握命中率只有 25%。查下来是：球在可站区间里
最低只降到 1.15m，而横握中心在 1.0m —— 退到头也差 0.15m。放宽到 +2.0（底线外 0.8m）后
球能降到 1.0m 附近，横握从 25% 到 42%。竖握不受影响（它本来就选靠前的位置）。

顺带一个反直觉的实测：**把目标高度抬高反而更差**。试过「wantY 钳到 1.3–1.75」「wantY+0.25」
「wantY 固定 1.45」，横握全部掉到 0–1/12。原因是几何是诚实的：拍面中心真的在 1.0m，球在
1.3m 就是接不到。想让横握接高球只能靠挥拍把拍子抬起来，站位帮不上。**不要为了「看起来
合理」去改目标高度**。

### (6) 实测（改前 vs 改后）

12 条真实来球（回球机求解器生成，三档到面高度 1.30/1.44/1.56 × 横向散布 -2.6…2.6），
球拍**静止不挥**，用真实 `sweepFace` 判这一球撞没撞上：

| 站位策略 | 竖着持拍 | 横着持拍 |
|---|---|---|
| 只走左右（4.17） | 8/12 | **0/12** |
| 左右 + 前后（4.18） | **11/12** | 5/12 |

横握改前是零 —— 拍面中心偏在握点侧方半米，永远不在球上。这条最能说明「瞄准中心」不是
优化项而是正确性问题。横握改后仍只有 42% 是物理上限：拍面中心 1.0m、球 1.3m 以上，
得靠挥拍抬起来。

### (7) 单测：+4 条，加的都是能复现反馈的断言

- **横握时握点要站到球的侧边 0.6m**：断言 `target + 0.6` 落在球心上，竖握作对照。
- **拍面中心低时要后退**：同一条球，横握的 `targetZ` 必须比竖握深 0.5m 以上；
- **弹道采样等距、时间递增、与精确穿面点吻合**（10cm 网格 vs `predictAtPlane`，时间差
  ≤ 一个物理帧）；
- **握法偏移只在没挥拍的帧采信**：静止 2 秒收敛到 ±2cm，30 rad/s 的挥拍帧整帧拒绝且
  偏移值一个字节都不许变。

`planAutoMove` 的签名从 `(ball, planeZ, cfg, homeX)` 改成 `(ball, { x, z, center }, cfg)`。
改动波及 `scripts/sim-e2e.cjs` 的 `MOVE=auto` 分支：那里**仍然只吃 x**，因为该脚本的挥拍
时机是按「球到 HIT_Z」算的，站位跟着 z 变会把时机判据一起改掉，A/B 就不可比了。

### (8) 性能

`planAutoMove` 单次 0.022ms（60fps 下 0.1% 单帧预算，近球 0.007ms）。采样器越过区间上界
即停，多数调用省掉一半以上步进。可以每帧算。

### (9) 验证与未验证

`npm run verify` 全绿：**132 项 ×3、sim 30/30（naive）、duel-sim 三档门禁、build**。
无头 Edge 看过墙打入口页：无异常，画面正常（场地、网、墙、拍子、球都在），底部键位提示
已更新。

**真机仍未验**。特别是有两件事只有真机能回答：

1. 真机的握法偏移是否和模拟里假设的一致（横 0.6 / 竖 0.6，中间值靠姿态算）；
2. 前后走位会不会让人觉得「被拖着走」。限速 3.6 m/s 和 5cm 死区是按体感拍的，没上过机。

## 4.19 2026-11-13 · 握点抬到 1.3m：横握的拍面终于和来球同高

### (1) 反馈

真机上「拍面高度不止 1 米，应该有 1.3 米左右」。这不是视觉问题：`RACKET_POS[1]` 是**握点**
（虎口）高度，横握时拍柄横过去、`faceCenter` 只加 0.6m 的杆长在竖直方向的分量（=0），
所以**横握的拍面中心就等于握点高度**。1.0 就是「球总在我腰上飞过去」的全部原因。

### (2) 改了什么

`court.ts` 的 `RACKET_POS` 从 `(0, 1.0, 0.3)` 改 `(0, 1.3, 0.3)`（胸口中线）。连带：

| 位置 | 之前 | 现在 |
|---|---|---|
| 横握拍面中心 | 1.0m | **1.3m** = 来球高度 |
| 竖握拍面中心 | 1.6m | **1.9m** |
| 墙打喂球目标（瞄当时拍面） | 自适应 1.0–1.9 | 自适应 1.3–1.9，代码没改 |
| 回球机到面高度带 | 1.3–1.6 写死 | `RACKET_POS[1] + 0…+0.3` |
| 机器发球到面高度带（`duel.ts`） | 1.22–1.6 写死 | 同一条带 |

喂球、落地重瞄、回球补偿全都瞄「当时拍面中心」，所以它们**一行没改**就自动跟着上移了——
这是 11-09 把「归一化位姿 + faceCenter」这套定下来之后第一次吃到红利。
`probe-feed.cjs` 实测：竖握到面 1.90m（vy≈1.9，仍在上升）、横握 1.30m，
落点离拍面 1.62–1.71m（还在设计区间 1.55–1.85 内）。

### (3) 到面高度带为什么不跟着整段上移

玩家能到的球壳从 1.0–1.6 变成 1.3–1.9，直觉是「球也该高 0.3m」。实测否掉了：

| `ARRIVE_Y` | 回球 L1 / L2 / L3 |
|---|---|
| **1.3–1.6（选它）** | **27 / 52 / 81** |
| 1.45–1.75 | 22 / 33 / 75 |
| 1.6–1.9 | 26 / 40 / 69 |

到面高度越高，从对手底线（21.6m 外）既要落界内、又要在到面时爬那么高的弹道越少，
回球机只能打月亮球，玩家反而更接不到。所以只取**握点 +0…+0.3**（= 拍面从水平到前倾 60°），
区间宽度保持 0.3m，不跟着放大。

### (4) 代价与它是不是真问题

拍面最低只能到握点高度 ⇒ **低球变难**。`duel-sim` 的 L2 从 59 掉到 52（L1 27、L3 79 基本不动）。
但这是**测试玩家模型**的限制：它对球的倾角固定 14°、只会屈膝到握点下 0.38m，够不到 1.3–1.6
的球就记一次「握点被夹」；真人遇到低球会把拍面压平（这正是游戏里手机姿态的用途）。
所以门禁保留「不回退」的判定，数字下降记录在此，不当回归处理。

### (5) 两条单测被这次改动打回原形

- `补偿瞄的是拍面本身`：触球点写死 `y=1.59`（那是握点 1.0 时的拍面）。改成 `face[1] - 0.01`。
- `回球补偿：竖直拍面…`：原来拿 `RACKET_POS` 那个真实握点当位姿、却要求回球回到 1.6m——
  等于「从腰高出手、回到头顶」，握点一抬高就必然撞墙 5.9m > `WALL_H` 5.2。
  改成按 `Rally.launch` 的真实做法**归一化位姿**（拍面中心平移到 `aimY = 触球高度`）。
  这条错误在 11-09 就埋下了，只是当时握点恰好等于 `RACKET_POS[1]` 才没暴露。

### (6) 验证

`npm test` **132 项**、`npm run sim` 30/30（漏接 0 / 撞网 0）、`npm run duel-sim` 三档门禁、
`npm run build` 全绿。**真机未验**：如果觉得「球整体变高了」，改 `ARRIVE_Y` 或握点，
别去改 `FEED_APEX_*`——那套散布是按判定半轴算的，和高度无关。

## 4.20 2026-11-13 · 握点变成第三个自由度：走位从二维升到三维

### (1) 反馈：三条，其实是两件事

4.19 上线后真机试了一轮，反馈三条：

- 离球太近，经常打不到；
- 网前的球完全移动不过去；
- 击球动力学不好：很多球「看着打上了但实际没打上」，有时打到了但球回弹很慢。

前两条是走位，第三条是触球质量。查下来**第三条是第一条的下游症状**——不是判定或出球公式的问题。

### (2) 用归一化判定坐标把「看着打上了」量化

先要一把尺子。`sweepFace` 的判据是球心到拍面椭圆盘的距离，所以把触球点换算成盘内归一化坐标
`(u, v, n)`（`u` 横向 / `v` 纵向 / `n` 法向，各除以对应半轴），`max(|u|,|v|,|n|) <= 1` 才算真进拍面。
写了个临时探针（`.tmp-bench/duel-probe.cjs`，未纳入版本库）逐球记录它，一档 42 球：

| 握法 | 真进拍面 |
|---|---|
| 斜握 14° | **2 / 42** |
| 竖握 | **0 / 42** |
| 横握 | 34 / 38 |

「看着打上了」的来源清楚了：球从拍面**下方 10–25cm** 掠过，`v ≈ -1.1`。

### (3) 根因：拍面中心被锁在一段球壳上

`faceCenter(pose) = pos + R(q)·(0, FACE_CY, 0)`，而 4.19 把握点 `y` 写死在 `RACKET_POS[1] = 1.3`。
于是拍面中心只能在这段球壳上：

| 握法 | `c.y` | 拍面中心高度 |
|---|---|---|
| 竖握 | 0.60 | **1.90m 固定** |
| 斜握 14° | 0.53 | **1.88m 固定** |
| 横握 | 0.00 | 1.30m 固定 |

回球机的到面高度带是 `[1.3, 1.6]`。竖握/斜握的拍面恒在 1.88–1.90m，**比球高 0.3–0.6m**——
几何上根本没进椭圆，怎么挥都没用。而 4.18 加 `z` 的思路是「站远一点让球掉下来」，可是：

- 顶多能把球降到 1.63m，还是够不着 1.88；
- 为了找「`|p.y - wantY|` 最小」的平面，选点循环会把玩家拖到底线外 2m（`planZ` 一直是 0.30，
  人却在 z=1.8）。这就是「离球太近打不到」的机制——**高度差不是站位能补的**。

### (4) 改法：`y` 是第三个自由度，不是补丁

`planAutoMove` 的返回值加 `targetY`，`AUTO_MOVE_DEFAULTS` 加 `speedY / minGripY / maxGripY`，
`app.ts` 的 `PLAYER` 加 `y`。三个轴各有自己的限速和钳位：

| 轴 | 范围 | 限速 | 含义 |
|---|---|---|---|
| `x` | ±3.9 | 4.8 m/s | 横向跑。原来 3.0，够不着小斜线 |
| `z` | HIT_Z−3.0 … HIT_Z+1.0 | 3.6 m/s | 纵深。前端放到网前 3m，后端只到底线内 |
| `y` | **0.70 … 1.65** | 9.0 m/s | 深屈膝 ⇄ 举拍 |

于是「球高了」的答案从「退到球掉下来」变成「把拍子沉下去」。选点循环里高度变成**硬约束**：
`overY > 0.01` 的平面直接淘汰（够不着就是够不着，不该靠代价函数软性折中），代价函数才是
`0.9×|姿态| + 0.7×|站位| + 1.2×横向超出 + 0.06×耗时`。

### (5) 网前球：两处都要改

短球的失败有两个独立原因，只修一个都还会漏：

1. 旧 `minZ = HIT_Z - 0.55`，人根本走不到网前；
2. **`sampleCrossings` 不知道「两次落地判死」**，会推出一条不存在的「二次弹起后飘到击球面」的
   弹道，规划器就把人放在终点等着。实测短球落在 z≈−8，弹一下在 z≈−1.4 就死（-22.05 起手扫 vy/vz，vz=13/vy=5.5 那一条：−8.01 → −1.40），那条弹道压根不存在。

第 2 条先写错过一次：初版判据是 `ourBounces >= 2`（只数「从现在起」），横握失败只从 35 降到 7。
原因是**来球往往已经弹过一次**，得从 `ball.bounces` 起算，并且判据要和 `rally`/`duel` 的
`bounces >= 2 && at[2] > NET_Z` 完全同源。改对之后横握 39/39。

### (6) A/B：改前 vs 改后

### (7) 「打不实」是同一个根因的下游

改完之后击球点从 1.9m 一带回到 1.4m 一带（探针统计触球高度 p10 1.34 / p50 1.48 / p90 1.60），
高球发力折扣从 0.82 回到 0.91–1.0。**不需要动出球公式**：球慢是因为打在拍沿、力度被高球折扣
吃掉，不是 `SPEED_GAIN` 不对。`duel-sim` 三档的回球数与 4.19 之后基本一致（27 / 52 / 79），
说明这次改动没有把机器那一侧的手感带坏。

### (8) 一个被否掉的实验：发力折扣跟随握点

直觉上「拍子举高了就该少打折」，于是试了把 `swing.ts` 里写死的阈值 1.35 改成跟随握点
（`HIGH_BALL_Y = RACKET_POS[1] + 0.4 = 1.7`，折扣下限 0.62→0.72、斜率 0.34→0.2）。`npm run sim`
在「大力」档挂 5 个种子的结论和证据相反：回球变快之后墙打脚本的挥拍模型跟不上。

先怀疑是同批改的 `aimY` 上限（1.9→1.7），单独回退只挂 1 个——说明**两件事都在往下压**，
但新折扣本身确实有问题。全部回滚（`swing.ts` 恢复原样、`rally.ts`/`duel.ts` 恢复
`pen = at[1] > 1.35 ? …`、`aimY` 恢复 `Math.min(1.9, Math.max(0.9, at[1]))`），并在 `rally.ts`
留注释记录这次否证，免得下一个人再试一遍。

### (9) 两条单测随语义变更改写

- 旧「前后走位：拍面中心低（横握）时往后退」→ 新「高低差靠举拍/屈膝解决，不再靠前后跑」：
  断言 `|targetY + FACE_CY - hitY| < 0.03`（竖握）、`|targetY - hitY| < 0.03`（横握），
  且站位不离 `homeZ` 超 0.4m。
- 旧「已经从我身边过去的球不追（`maxZ` 判据）」→ 新「球越过拍面所在平面就站住」：
  `HIT_Z + 0.4` 不追且 `target/targetZ` 保持原位，`HIT_Z - 1.0` 要追。
- 新增「网前的短球要往前迎，不是站在击球面等它二次落地」。
