# 修改历史

> 原为 `AGENTS.md` 第 4 节，2026-11-09 拆分独立成篇。按时间顺序，每条记录：**现象 → 根因 → 改动 → 验证**。
> 被否决的方案也记下来，避免重走。
>
> 只在两种时候读：① 想知道「现在这段代码为什么长这样」；② 想改某处之前确认有没有人试过。

## 4.1 2026-11-01 · 立项与技术选型

需求：用传感器做体感操作的网球游戏。

确定三条约束（形态 = 大屏 + 手机、硬件 = 只用现有手机 0 成本、范围 = 单人业余时间），选 TypeScript + three.js + WebRTC，双端浏览器。

被否掉的方案：

- **Unity 6.3 LTS**：作为正式发行时的迁移目标保留，不作为 v1 主线。
- **纯 WebXR / VR**：与「大屏 + 手机」形态冲突。
- **摄像头 MediaPipe 作主输入**：30fps 抓不住挥拍关键帧（拍头 >100km/h，运动模糊丢手腕点），只适合站位识别和教学纠偏。

关键判断：延迟红线 100ms；传感器数据必须走局域网，不能过公网；姿态用 6 轴（Madgwick 思路），不用磁力计（室内钢结构/电器干扰会跳变，宁可慢漂）。

## 4.2 2026-11-02 · P0 骨架 + 第一批真 bug

完成：three.js 球场、虚拟球拍、HUD、60 字节二进制协议、IMU、WebRTC 双通道、极简信令、二维码。

真 bug：

1. **时钟同步偏移量符号写反**。NTP 公式算出的是「远端比本地快多少」，换算到本地必须减。写反后延迟变成负数或大得离谱，且不报错。
2. **手机没有 `DeviceMotion`**：两个叠加的坑——微信 WebView 不下发传感器；`http://192.168.x.x` 不是安全上下文，浏览器静默拦截。新增 `controller/env.ts` 环境自检、本地 CA（自签红锁 → 自建 CA）、`/__lanip`。
3. **球拍姿态和手机对不上**：
   - `screenCorrection` 是错的（设备坐标系与屏幕旋转无关），已删除。横握时球拍曾整体歪 90°。
   - 只积分陀螺仪 = 没有重力参考。改成 `deviceorientation` 绝对姿态 → `Rz(α)Rx(β)Ry(γ)` → 左乘 `EARTH_TO_WORLD = Rx(-90°)`，只归零朝向。
   - iOS 上两个 `requestPermission` 必须在**同一手势内同步发起**。
4. **「能看到球、能挥拍，但打不到球」**（第一版）：手机上两条独立通道——`deviceorientation` 给姿态、`devicemotion.rotationRate` 给角速度。部分机型后者恒为 0，而 `sensors.ts` 写的是 `if (!rr || !acc) return;`，把整条事件丢掉。表现是「一切正常，只有击球静默失效」。
   - 新增 `core/gyro.ts`：`omegaFromQuatDelta`，`q_prev⁻¹ ⊗ q_cur` 得 body-frame 增量；**必须取最短弧**（w<0 整体取反），角度用 `2·atan2(|xyz|, w)` 而不是 `acos(w)`。
   - 角速度双通道 + 双向判定；`Rally.diag` 诊断条诞生。

P1 手感闭环：`vec` / `court` / `swing` / `physics` / `rally` / `audio`。三个架构选择：不做轨迹积分只做峰值检测；击球用时间窗 + 冻结；连拍只在过网时 +1。

调参踩出的数：`SPEED_MIN=20`、`WALL_REST=0.76`、`WALL_Z=-11.9`、高球惩罚 `pen`、`liftOverNet` 用扫描而非二分（回球高度对仰角不单调）。

真 bug：落地后每步重复触发 `ground`（加静止冻结 + `v[1] < -0.6`）；`probe()` 用位置跨越判断撞墙永远不成立（改用碰撞事件）；马格努斯写成 `ω × v`（必须 `v × ω`）；连拍加两次。

## 4.3 2026-11-03 · 平台段击穿、延迟、严格碰撞

**1. 「挥拍 1 / 到面 43 / 时差 未挥拍」**

根因：三点峰值检测被平台段整段击穿。大屏 60Hz 发包，`deviceorientation` 只有 20–35Hz；走姿态差分时同一个值被连发 2–4 次，`w[i] > w[i-1] && w[i] > w[i+1]` 恒不成立，整次挥拍被静默丢弃。

改法：`SwingDetector` 重写为迟滞 + 峰值保持；`SWING_THRESHOLD` 3.6 → 3.0（差分会把峰值削 15–25%）；删除 `SWING_RISE`，新增 `SWING_MAX_MS`。

顺带修：`onCollision` 的 wall 分支只推事件、不改 `phase`，导致 `phase` 永远卡在 `outgoing`，一球之后状态机停摆。

**2. 「球弹回的点明显比球拍接触的点晚」**

根因：`FALL_RATIO=0.75` 要等角速度跌到峰值 75% 才结算，峰值后 50–90ms；判定用峰值时刻（正确），但 `launch` 发生在结算时刻。

改法两层：`FALL_RATIO` 0.75 → **0.9**（峰值后 1–2 帧）；**抢跑 `liveStroke` / `consumeLive`**，球到面那一帧直接出球。新增 `出球` 诊断（抢跑生效时恒为 0）。

**3. 「p50 一直显示 —」**

根因：大屏发 `ping`，手机端 `onCtrl` 只处理 `recal`，从不回 `pong`。`ClockSync.isValid` 永远 false → 延迟窗口空 + `tLocal` 退化成包到达时刻（挥拍时间窗系统性偏晚）。

改法：加 `pong`；协议加 `tSample`（60 → 68 字节）并保留 60 字节兼容；手机端加「姿态 xx Hz」；面板「端到端」与「网络」分开。

**4. 球拍建模：羽毛球拍 → 网球拍**

拍面 25×33 → 30×38cm，框管 Ø2.2 → Ø2.6cm，加拍喉三角、14×16 拍线、握把尾盖。

两个实现坑：不能用 Torus + scale 做椭圆框（会压扁管截面），要沿椭圆采样 → `CatmullRomCurve3` → `TubeGeometry`；拍线不能用浅色（浅背景上会消失）。

**5. 拍面严格碰撞 + 走位（方案 A）**

计算量可忽略（≈60 flops/子步，占球物理 5%）。真正的难点是隧穿，不是算力。

新增 `core/racket.ts`：`sweepFace`、`faceCovers`、`RacketTrack`（400ms 滑窗 + 时间戳 slerp）、`faceCenter`。

连带改动（每个都是被严格碰撞逼出来的）：

- `RACKET_POS` 从 `(0, 1.02, 0)` 改 `(0, 0.85, HIT_Z)`。原来拍面中心在 1.62m（头顶），而且 z=0 而判定面在 0.3——球在拍子前方 30cm 被打中。
- 发球参数重做（旧参数弹到击球面只有 0.73m，正好从拍子底下钻过）。
- `liftOverNet` 增加 `targetZ/targetY`；仰角扫描起点 `max(v[1],0)` → 0。
- `CONTACT_HOLD_MS` 190 → 60。
- 走位 `WASD`，速度 4.2 m/s，`x ∈ ±3`，`z ∈ [HIT_Z-0.55, HIT_Z+1.35]`。
- 诊断「高度」改成「甜区」（`offCenter`）。

主循环顺序固定为「平滑球拍 → 判定 → 渲染」。

## 4.4 2026-11-04 · 真机三问题 + glb + 移动后打不到

**反馈（三点）**：看上去打到时球没有回弹，怀疑碰撞检测；拍面位置偏低、来球偏高，多数球接不到；球速过快，希望落点更靠近球网。

**1. 「打到了却不回弹」= 回球补偿的模型错误（核心 bug）**

`liftOverNet` 旧判据：球穿过 `z=targetZ` **竖平面**时高度在拍面中心 ±12cm。拍面一倾斜这个模型就错了——倾斜拍面是**斜的盘**，上升中的球穿过盘平面的点比穿过竖平面低 15cm（18° 实测）。补偿器因此选中 7.6–7.9m 的高吊，回球在玩家脚前以 8.4 m/s 大力弹起，从拍面下沿下 2cm 掠过 → `reach`。

修复：`liftOverNet` 加 `pose` 参数，回球腿逐个物理子步用**游戏内同一套 `sweepFace`** 验证；只在撞墙 ≤ `WALL_H` 的弧线里选；粗网格 0.4 + 0.1 细化。

**2. 拍子太低**：`RACKET_POS.y` 0.85 → 1.0，喂球高度自适应拍面中心。

**3. 球速太快**：`SPEED_MIN/MAX` 20/42 → 18/32，喂球 `vz` 15.2 → 10.5。

另外：`CONTACT_HOLD_MS` 60 → 100（挥拍事件路途 = 结算 16–33ms + 网络 20–60ms，最晚 90ms）；`FACE_MARGIN` 0.012 → 0.02（补位姿延迟）。

**4. 换 glb 球拍模型**

**需求**：用外部工具重做的网球拍模型替换现有模型（放在 `assets/` 目录下），碰撞检测仍沿用椭圆盘。

模型约定与游戏一致：柄底原点、拍头 +Y、法线 +Z、单位米。按 `FACE_RX/0.128 ≈ 1.172` 与 `FACE_CY/0.515 ≈ 1.165` 双轴缩放对齐；PMREM + `RoomEnvironment` 提亮金属材质；加载失败回退程序化球拍。运行时用 `public/models/racket.glb`（ASCII 名）。

**5. 「移动起来就打不到球」**

根因不在碰撞，在喂球：`serve` 从场地正中 `(0, 1.4, -11)` 发球，落点铺开 ±1.3m，而拍面可及半宽只有 20.35cm，差 6 倍。而且站着不动也会漏（实测球偏 0.66m 就够不着），「不动时打得到」只是运气好。

改法：发球点横向对准拍面 x ±8cm，`vx` ±10cm，`targetZ` 用 `face[2]`；`feedVy` 增加 `targetZ` 参数。

## 4.5 2026-11-08 · 弹地喂球 + 姿态精度

**反馈（两点）**：发球普遍偏高、退到后场也够不到，希望把落点控制在拍面前方一定范围，让球弹起后再接；挥拍手感仍偏怪，质疑仅靠手机姿态判断拍面朝向与拍子角度是否够准，是否需要第二个传感器（例如手臂上）以及如何实现。

**1. 弹地喂球 `feedBounce`**

根因：`feedVy` 要求球一口气飞到拍面、中途不许落地。退到后场时飞行 12m+、`vz` 只有 10.5，球必然中途落地；`heightAt` 把「提前落地」返回 -1，二分认为「仰角还不够」，一路加到上限 12 → 每球都是月亮球。

新方案：球在玩家前方 2.5–2.9m 落地（当时的值，后来拉近），弹起后穿过拍面，高度 = 拍面中心。求解参数化成单参数「飞行时间 t」，严格单调 → 二分。

连带：发球点横向收窄；测试窗口 150 → 260 帧；`probe-move` WARMUP 2s → 4s；新增「发球是弹地喂球」测试。

**2. 姿态精度分析（`docs/motion-accuracy.md`）**

结论：**传感器精度不是瓶颈**。六项误差按影响排序：

1. **握持安装角没标定** 5–20° → 出球方向放大 0.71 倍（10m 偏 0.6–2.5m）。最大的一项。
2. **姿态采样率 25–35Hz**：挥拍中段 12–20 rad/s，相邻样本差 28–38°，取最近样本误差 ±14–19°。
3. **只测角速度不测位置**：拍面只能绕握点画弧，伸拍够球做不到——只有这项必须上硬件。
4. yaw 漂移 / 磁跳变（Android 室内 5–15°）。
5. 网络延迟（不影响精度，只影响延迟感，已被 liveStroke 覆盖）。
6. 平滑滞后（快速挥拍已降到 τ=3ms，不是主要矛盾）。

建议顺序：先量（HUD 拍面偏角）→ 握持标定 → 60Hz 陀螺插值 → yaw 改陀螺积分 → 再评估硬件。第二传感器（`?role=arm`，肘→腕→拍面）约 2 周工作量，主要价值是**位置**。

已落地：HUD 加「拍面」读数（球拍法线相对正对球场的偏角）。

## 4.6 2026-11-09 · 落点、散布、锚定弯路

这一天的反馈密度最高，也走了最大的一段弯路，完整记录。

### (1) 落点太远 + 看着够到却没打到

**反馈**：落点离玩家的水平距离太远，多数球够不到；看上去够到了，实际也没打到。

三个独立问题叠在一起：

1. **落点确实太远**：`feedBounce` 写死 2.5–2.9m（从拍面算），玩家脚下就是 2.8–3.2m。
2. **球发出去之后玩家位置变了**：喂球只瞄「发球那一刻」的拍面。
3. **没挥拍时球按原速穿过拍面**：`tickContact` 等满后还原 `resumeV`。喂球瞄着拍面中心，所以每球都演一遍「球从拍子里穿过去」。

改动：

- 落点 2.5–2.9 → **1.55–1.8m**（后来定为 1.55–1.85）
- 新增 `aimAfterBounce`（落地重瞄）与 `steerToRacket`（飞行途中限 1.2 m/s 横向）
- 没挥拍时改为「擦框掉落」
- `sim-e2e` / `probe-move` 的挥拍时机从「线性外推」改成 `predictReach()` 物理前推，目标平面用拍面实际平面（倾斜 18° 差 18cm / 40ms）

### (2) 22:40「一挥拍就打不到」→ 锚定拍面中心（弯路，已撤销）

**反馈**：静止持拍时能打到，一挥拍球就从拍面中间穿过。

诊断（`scripts/probe-swing.cjs` 前身）：握点固定 + 绕握点旋转，拍面中心挂在 0.6m 杆末：

| 转角 | 拍面中心平移 | 判定半轴 |
|---|---|---|
| 30° | 0.31m | 0.20m |
| 60° | 0.60m | 0.20m |
| 90° | 0.85m | 0.20m |

球却是照着**静止时的拍面中心**喂的，于是「挥得越准（峰值正落在球到面那一刻 = 转角最大）偏得越狠」。

当时的修法分三块，**后来只有第一块被撤销**：

- `HIT_ANCHOR` + `poseFromAnchor`：位置由锚点、朝向由手机，等于把旋转轴从握点挪到拍面中心。**已全部删除。**
- `sweepFace` 改成候选点盘形判据（「球心到圆盘距离 ≤ 球半径」）。**保留**——这是真 bug 修复，掠射不再漏判。
- `rally` 里三处「拍面在哪」改用 `faceCenter`。**保留**——握点到拍面中心差 0.6m，这个区分永远成立。

验证：77 项 ×3、sim 30/30、build 通过。**但模拟器里球拍是绕拍面法线转的——法线不变，拍面中心不动，等于没测到真路径。**

### (3) 23:20「放宽喂球约束：顶点在拍面附近」

**反馈**：不必每球都朝拍面中心喂，只要弹起后的最高点落在拍面附近一定范围、玩家够得到即可。

这是放宽约束，不是修 bug。原实现有两处「强迫症」：

1. `feedBounce` 精确控制「过拍面高度 = 拍面中心」，横向只留 ±3cm。
2. `liftOverNet` 在可行弧线里挑 `offCenter` 最小的，还按 0.1 细化一圈。

改动：新增 `FEED_APEX_DX/DY`（当时 0.16/0.14）、`FEED_APEX_BACK_MIN/MAX`、`FEED_APEX_LEAD`、`RETURN_OFF_TOL`；每球抽一次 `aimDx/aimDy`；`liftOverNet` 改为合格池随机挑；`feedBounce` 返回真 `apex`。

踩坑：

- **正反馈**：重瞄目标写成「拍面中心 + 本球偏移」，玩家跟着球挪半步 → 拍面移到球的位置 → 再按「拍面 + 偏移」算 → 球又被推一份 → 越推越远。改成「只修超出容差的部分」后收敛。
- `FEED_APEX_LEAD` 第一次估 2.15（错），实测 **2.40**。
- 「时差符号」测试偶发 `lastLag=null`（散布下这一球可能没接触）→ 该测试固定 `Math.random=0.5`。

### (4) 23:50「恢复自由挥拍」→ 撤销锚定

**关键澄清**：锚死拍面中心后无法正常挥拍，要求恢复自由挥拍；并明确「打不到」是指碰到后没有回弹、球从拍面中间穿过，属于碰撞判定问题，而非拍面没碰到球。

这是整个项目最重要的一次澄清：**症状是「碰到没回弹」，不是「没碰到」。**

撤销与重做：

- 删除 `HIT_ANCHOR` / `FACE_DRIFT_MAX` / `poseFromAnchor`；`syncRacket` 回归「握点 + 姿态」；`setRacketBase` 搬握点。
- `steerToRacket` 重写为**改方向不改速率**（`want = to/t`，`t = dist/speed` ⇒ `|want| ≡ speed`），三维一次修完，只在 `bounces >= 1` 后介入。
- `aimArrival` 删掉「拍面中心 120ms 位移外推」（那速度混着挥拍旋转，手腕一转 4 m/s，会把球瞄到半米外）。
- `rally.launch` 传**归一位姿**给 `liftOverNet`（位置固定在 `HIT_Z` + 击球高度，朝向保留）。直接传挥拍中的实时 pose → 候选全不合格 → 兜底弧线 → 偶发撞网（25 局 1 次）；归一后 25/25。
- `FEED_APEX_DX/DY` 0.16/0.14 → **0.12/0.10**（合成偏离 0.98 → 0.72）。
- `STEER_LEAD_S=0.55`、`STEER_VMAX=12`、`STEER_ACC=150`。

模拟器终于测到真路径：

- 转角从「绕拍面法线」改成**绕局部 x 轴**（拍面横轴），拍面中心扫出 0.3–1.1m。
- 挥拍时机：`tta = (HIT_Z - z)/vz` 落到 75ms 内就起势。整条弹道外推会被跟随改方向带偏。
- 走位：朝球**当前**横向（不做弹道外推），且限速 5.5 m/s。两个完美跟随系统会互相带偏。

验证：77 项 ×10 连跑零失败、sim 3 × 30/30、build 通过；`probe-swing` 显示跟随关时竖挥 30°/60°/90° 全部「未接触」，跟随开后全部「打中」。

**但没有真机验证。** 见 `AGENTS.md` 第 0 节。

## 4.13 2026-11-10 深夜 · 位姿慢漂确证与「不重定义正前方」的补偿

**现象与关键澄清**：真机（只跑 `dev:https`、未开视觉）补到三条读数：

1. 偏差**随时间慢慢变大**，约半分钟到一分钟歪到打不到球；按 `R` 可回正，回正后重新累积；
2. **只有反手位按 `R` 才回正**，正手位按 `R` 依然歪；
3. 回正之后就能打到球，重连之后也可以。

第 3 条推翻了 4.12 里「重连后打不到不是姿态漂移的后果」这句过强的断言。`R` 的实现是大屏清统计 + 发 `recal`，手机端只做 `yawZero = null`（下一帧重锁）和清连续性状态；**`ClockSync` / `lastImuSeq` / `SwingDetector` / `Rally` 一个都没动**。只重锁朝向基准就恢复命中 ⇒「打不到」的主因是位姿：alpha 慢漂让拍面法线绕竖直轴侧过去，`sweepFace` 的盘形判定判空，球从拍面位置穿过去。4.12 的时钟 / seq 残留是重连那次的**独立叠加项**，修好之后重连时 `start()` 里的 `yawZero = null` 顺带把姿态也回正，两条一起恢复。

第 2 条说明**旧 `recal` 的语义本身就是错的**：`yawZero = qYaw(当前绝对姿态)` 等于把「此刻手机朝哪」重新定义成正前方。而 `absolute = Ry(α)·Rx(β−90°)·Ry(γ)`，手机近竖直持握时 β≈90°、`Rx(0)` 退化成单位阵，`absolute ≈ Ry(α+γ)` —— **gamma 与 alpha 同轴**，正手 / 反手换握会让 `qYaw` 差出几十上百度，重锁结果必然依赖握位。所以「自动按 R」这条路直接否决：正手位只会更糟。

**改动**（只碰姿态输出，不碰判定 / 弹道 / 喂球 / 协议 / 时钟；`MAX_POSE_JUMP` 一行没动）：

- `src/core/attitude.ts`：新增 `worldYawDelta`（世界系增量四元数 `next·conj(prev)` 读出绕 Y 转角，避开 `qYaw` 的万向锁换分支）、`isYawGimbal`、`YawDriftObserver`。观测器按**相邻帧转角幅度**分离慢漂与真实动作：`< MAX_DRIFT_STEP = 0.05 rad`（≈2.9°/帧）才积分。真机慢漂约 1–2°/s，30–60Hz 下每帧 <0.1°；挥拍中段是十几到几十度，差两个数量级。**刻意不用「静止门控」**——挥拍那几百毫秒里 alpha 一样在漂，只积分静止帧会永久漏掉那部分。
（**11-17 修正**：这段的判据方向没错，但「按帧判」把阈值绑在了采样率上——20–25Hz 下
0.05 rad/帧 等于 58–72°/s，只有挥拍挡得住。见 4.34。）
- `src/controller/main.ts`：`advancePose` 里 `effZero = yawZero + (driftOn ? drift.radians : 0)`，`toOutputQuat(abs, effZero)`。只扣「传感器多转的量」，**不重定义正前方**，因此与握位无关。补偿开启时 `recal` 不再是重锁，而是「先 `yawZero += drift.radians` 固化已扣的补偿，再 `drift.reset()`」；关掉 HUD 开关时同理。**只 reset 不固化会让拍子在这一刻突然歪回累积的漂移量**——这是状态转换的坑，别简化掉。`start()` 新会话是 `yawZero = null` + `drift.reset()`，两者一起归零所以没问题。HUD 新增可点击的「漂移 ±x°」按钮做现场 A/B，含「万向锁」标记；扫码 URL 末尾追加 `&drift=1` 可直接以开启状态接入（二维码 URL 已带 `?room=XXXX`，不是再写一个 `?`）。**默认关**：照 `?vision=1` 的先例，未真机验证的能力不默认接管输出。
- `controller.html` / `src/style.css`：HUD 元素与按钮样式。
- `tests/core.test.cjs`：新增 8 条（当时共 **97 项**、15 个分组）。其中「竖直持握时 gamma 混进世界 Y 转角」是握位依赖的数学反证；「扣掉观测漂移后输出回到启动姿态」是「不重定义正前方」的端到端反证。

## 4.14 2026-11-11 · 快挥拍打不到 + 拍子疯狂抖：姿态跳变门限误伤真实旋转

**现象**（真机，只跑 `dev:https`、未开视觉）：挥拍速度一快就打不到球；打了一会儿之后球拍开始**疯狂抖动**。两条和 4.13 的 alpha 慢漂不同：慢漂是几十秒尺度、按 `R` 回正、偏差渐增；这条和「挥得多快 / 挥了多久」直接相关。

**根因**：两个坑嵌在 11-10 上午加的「跳变拒绝」里，都在 `controller/main.ts` 的 `advancePose`：

1. **判据只看角度、不看有没有真实运动**。`MAX_POSE_JUMP = 1.2 rad` 是按「方向事件 25–35Hz、挥拍 20 rad/s、相邻帧最多 0.8 rad」估的。但不少机型方向事件只有 20–25Hz，一次 20–35 rad/s 的挥拍相邻帧就是 **1.0–1.75 rad**，和门限重叠。于是真实快挥拍被当成「万向锁换欧拉解分支」，改用陀螺增量外推；而陀螺在挥拍峰值常被 2000°/s 量程削顶，积分出来的姿态会明显偏离手机。球到拍面那 100–200ms 用的是错姿态，`sweepFace` 判空 ⇒ **打不到**。
2. **比较基准冻结在跳变前**。`lastGoodAbs` 只在「采信绝对姿态」时更新，跳变帧不更新它。于是挥拍期间每一帧都在跟**挥拍前**的姿态比，整段挥拍乃至挥完之后都被判成跳变，卡在外推里，直到 `MAX_EXTRAP_MS = 500` 到期才强制重新接受绝对姿态 —— 这一刻又是一次大跳。大屏 `syncRacket` 在角速度大时把 τ 降到 3ms、几乎不平滑，这些跳被原样显示 ⇒ **疯狂抖动**。此外 `extrapMs += dtMs` 的两个入口（`onSample` 传真实间隔、`sendFrame` 写死 16.7）会把 500ms 兜底提前到约 250ms。

`scripts/probe-pose.cjs`（先跑 `npm test`）在纯计算层复刻旧判据并做 A/B，方向事件 25Hz、30 秒每 2.5s 一拍：

| 每帧转角 | 等效角速度 | 旧判据（挥完回原位） | 旧判据（挥完停在新朝向） | 新判据 |
|---|---|---|---|---|
| 0.4 / 0.8 rad | 10 / 20 rad/s | 0 外推帧 | 0 外推帧 | 0 |
| 1.2 rad | 30 rad/s | 51 帧 / 最长 280ms / 24 次切换 | 57 帧 / 520ms / 24 次 | 0 |
| 1.6 rad | 40 rad/s | 96 帧 / 520ms / 72 次 | 179 帧 / 520ms / 46 次 | 0 |

「切换次数」就是拍子在绝对姿态与陀螺外推之间来回跳的次数。30–60 秒里几十次大跳，正好对上「打了一会儿之后开始疯狂抖动」。

**改动**（只碰姿态连续性，不碰判定几何 / 弹道 / 喂球 / 协议 / 时钟 / 慢漂补偿的语义）：

- `src/core/attitude.ts`：新增纯计算 `PoseContinuityGate`（连同 `MAX_POSE_JUMP` / `MAX_EXTRAP_MS` 从 controller 搬进 core）。判据用**相邻两帧**的差，`prevRaw` **每帧都更新**，所以跳变只影响这一帧、不会冻结到超时；新增 `moving` —— 传感器角速度越过 `SWING_THRESHOLD` 时无条件采信绝对姿态。解分支跳变一般发生在静止 / 微动时，仍会被拦。另给 `YawDriftObserver` 加**非 Y 轴纯度判据**：增量四元数的 x/z 分量超过 0.01 就不积分，避免挥拍起收势的俯仰 / 横滚让 `effZero` 变成随机游走（补偿开启时会表现为拍子慢慢乱晃）。
- `src/controller/main.ts`：`advancePose` 只负责传 `moving` 与外推增量；`elapsed` 改用真实墙钟间隔（修掉双入口计时翻倍）；删掉 `lastGoodAbs` / `extrapMs` 两个局部状态；`recal` 与 `start()` 改调 `poseGate.reset()`。
- `tests/core.test.cjs`：新增 8 条（共 **105 项**、16 个分组），含「25Hz + 35rad/s 全程零外推」「跳变只拦一帧」两条直接反证。
- `scripts/probe-pose.cjs`：新增量化探针，固化修复前后的对照数字。

**明确没做**：没有调 `MAX_POSE_JUMP` 的数值（仍是 1.2 rad，调小会误伤真实挥拍）；没有把球追拍面 / 拍面锚定加回来；没有改大屏 `syncRacket` 的自适应平滑（修好输入后 targetQ 不再跳，改它会引入快挥拍滞后）；没有改慢漂补偿的默认关状态。

## 4.16 2026-11-12 · 对打模式：脚本回球机 + 独立服务

**需求**：在做 RL 之前先要一个脚本回球机，游戏分两种模式（对墙打 / 与回球机对打），分别启动不同的服务。墙打模式一行不改。

### (1) 为什么不换物理引擎

自研弹道积分器（半隐式欧拉、240Hz 定步长、子步轨迹回调）是为这台机器量身定的：球拍是**零厚度的椭圆盘**、不是刚体，任何通用引擎都没有对应 collider；击球判定要「线段 vs 椭圆盘」的精确求交，还需要反解「球要落在哪」时能**重放**同一套积分。换成 cannon / rapier 会得到「球拍要建成一个几何体」这个错误的抽象。对打新增的 `aimIntoCourt` 也是同一套积分的正用：粗扫 + 3 轮细化，一次求解约 0.4ms，不进 60Hz 主循环。「要不要换引擎」的结论与做 RL 无关——真要训练策略，这个积分器单核 1072–1401x 实时，够用。

### (2) 为什么必须是「对打」环境而不是复用墙打

墙打的后墙在 `z=-11.9`，网后 1.4 米。那个位置不是场地，是「球必须自己飞回来」这个前提逼出来的。要在后面站一个对手、要让球落在对方场内、要判「两次落地」，墙必须先关掉（`setWallActive`），而且对手侧要按球网镜像出完整半场（`OPP_HIT_Z = 2·NET_Z − HIT_Z`）。

### (3) 三个几何死结，全是实测撞出来的

1. **到面高度是硬约束**。玩家握点恒等于 `RACKET_POS[1]`=1.0，拍面中心只能在半径 0.6 的球壳上 ⇒ 最高 1.6m。第一版只约束落点，实测发球到面高度 **0.17m**，玩家一帧都接不到。给 `aimIntoCourt` 加 `arriveZ`/`arriveY` 之后才成立。
2. **到面高度的量测时机**。加了约束后求解器对任何目标都返回 null，因为试射在**第一次落地**就 break，而到面高度要在落地**之后**才测得到；改成「两个量都拿到才停」之后又漏了另一类合法球（球在落地前就穿过到面平面 = 玩家凌空打）。最终统一为「`land` 与 `planeY` 都拿到才停」。
3. **玩家的可及高度决定回球落点带**。球落得越靠近玩家，弹起来到击球面时就越低。要让它同时还有 1.3m 高，落点只能夹在 `z ≈ -6 … -1.5` 这一段。这条直接写进了 `ARRIVE_TARGET_Z_MAX` 与 `candidateTargets()`。

### (4) 回球机：不钉在底线

第一版把 `z` 钉在 `OPP_HIT_Z`。从底线到玩家拍面有 21.6 米，能让球「落在界内 + 到面 1.3m 高」的弹道几乎只剩月亮球。这不是求解器不行，是几何——真实球员遇到短球会往前迎。改成在全场找「最舒服的迎击点」（`pickIntercept`）之后，快球也有解，回合长度从 0.7 拍涨到 4.8 拍。

**竖直可及也必须放开**：回球机的握点给到 0.15–2.0（拍心 0.75–2.6），而玩家是 0.4–1.6。这不是放水，是对称性的必需——玩家打出来的球弹起顶点只有 1.0m 上下，拍面最低 1.22 的话它每一个球都够不着。修之前「够不着」几乎全部来自竖直方向，不是走位没跑到位。

### (5) 判分：第一落点定局

`onCollision` 原来的顺序是「先判出界、再判两次落地」。于是球合法落在对方场内、对手没接到、球继续滚出边线时，被判成**击球方出界**，得分反给了对手。`scripts/duel-sim.cjs` 的对打模拟把这个 bug 抓出来了。改成「已经合法弹过一次就不再改判」之后正常。

### (6) 前端：一份代码，两个入口

`src/play/app.ts` 是唯一实现，`main.ts` / `duel-main.ts` 各只有 `startPlay('wall')` / `startPlay('duel')` 两行。**没有复制成两份**——网络那一段（时钟同步、重连复位 `resetSession`、姿态连续性）是这个项目里最贵也最容易出错的代码，只能有一份。差异只有三处：`PlayScene` 的 mode（整场线条 + 对手球拍 vs 半场 + 练习墙）、规则对象、HUD 主数字（比分 vs 连拍）。

端口：5173/5174 墙打，5183/5184 对打。分端口不是洁癖——信令房间按房间号配对，共用端口时两个大屏窗口会互相抢手机。对打服务的 `/` 会被中间件改写到 `duel.html`，否则打开根地址会进到墙打。

### (7) 模拟脚本自己踩的坑（写在这里免得下次重踩）

- **探针必须关练习墙**。`advance` 的墙判据是「位置在墙平面**之后**」，从 `z=-21.3` 生成的球一出生就被抓到 `-11.9`。曾经据一张「没关墙」的网格图得出「只有 9–11 m/s 月亮球可用」的错误结论，那次调参全部作废。

## 4.17 2026-11-12 · 自动走位：只要挥拍，不用按键盘

### (1) 现场：为什么「够不到」

严格碰撞上线后拍面是真实的 30×38cm 椭圆，球心偏出 20cm 就打空。球的横向瞄准只发生在
**发球那一刻**（+ 落地重瞄那次 20cm 的微调），因为 4.5 撤销了「球追拍面」。于是形成
一个反直觉的结论：**站着别动几乎每球都接得到，中途按错方向跑开就够不到**。

`MOVE=off` 的实测先印证了前半句：五档力度 × 6 种子全绿，只 1 例漏接。既然球本来就来
找人，键盘走位在这套物理下**是负资产**——它最容易造成的结果是「玩家把自己从球的落点上
挪走了」。这条观察决定了功能形态：不是「加一个更强的走位」，而是「把玩家搬回球会经过
的位置」。

### (2) 只做左右，不做前后

前后（`z`）也能用：挪 z 会改「球到面时的高度」，理论上能接到更低/更高的球。但喂球和
回球机都把到面高度夹在拍面覆盖区间里（墙打瞄 `RACKET_POS[1]+FACE_CY`=1.6m，对打
`arriveY` 1.3–1.6m），这个轴上的缺口远小于横向；而自动前后走会让人在场上无意义地
进进退退，反而是负手感。先只解一维，模块形状留着（`planAutoMove` 返回 `eta`，将来
加 z 只多一个函数）。

### (3) 预测和回球机共用一份

`predictAtPlane` 原来住在 `machine.ts`，是回球机的私有工具。自动走位也要「球会从哪来」，
但两边必须给同一个答案：如果各自实现，会出现「机器算出来的点对得上、人算的差半米」这种
只在真机上才看得出的症状。所以把它提到 `physics.ts`，`machine.ts` 留一行转发导出，
`scripts/duel-sim.cjs` 一行没改。

一个容易忘的细节：**预测平面要用玩家当前的 `PLAYER.z`，不是常量 `HIT_Z`**。玩家按 W/S
前后走过之后击球面跟着走，写死常量会按旧平面算出一个偏掉的 x。

### (4) `stepAxis` 刻意不做指数收敛

「每秒最多 4.8m」+「差 5cm 以内不动」+「一步够得到就停在目标上」。不写指数收敛有两个理由：
指数收敛永远差最后一点点（球到面时还差 10cm 就是擦框）；死区不能省，否则玩家会贴着球的
正下方左右抖一帧一次。

### (5) 三路输入的优先级

> 11-13 之后只剩两路（视觉那条已删，见 4.21）：键盘 > 自动。下面这段是当时的记录。

视觉（`?vision=1`）> 键盘（`WASD`）> 自动。实现上就三条 `return`，没有状态机：视觉接管时
整帧返回；这一帧只要有一个方向键按下就走键盘、不碰自动；两者都没有才走自动。**不做
「按键后暂停 N 毫秒」的计时器**——松手瞬间接回来手感最直接。

### (6) 取证方式：给 `sim-e2e.cjs` 加 `MOVE` 开关，而不是另写一个脚本

`scripts/sim-e2e.cjs` 的走位原来是「朝球的当前横向位置跑」，本身就是个能到位的走位，
换成自动走位也是 30/30 —— 看不出差别。所以加了 `MOVE=naive|auto|off` 三档：

- `naive`（默认）历史行为，门禁按它判，**一行没改**；
- `auto` 走 `planAutoMove`，和 `app.ts` 同一份代码；
- `off` 站着不动。

`off` 的结论是「站着不动也能连打」（球瞄站位），于是真正的差别只能靠**主动制造失误**才
显出来：第 40 帧把玩家瞬移到 x=2.2，之后完全撒手。

| | 到面横向偏差中位 | 最差 | 进球心判定位 |
|---|---|---|---|
| 不动 | 0.07m | **1.60m** | 9/10 |
| 自动走位 | 0.01m | **0.05m** | 10/10 |

这条也正是写进单测的那条（`tests/core.test.cjs` 的「中途跑开 2.2m」）。

### (7) 单测：9 条，其中最值得留的是「判据自己做主」

`planAutoMove` 的早期版本靠 `predictAtPlane` 返回 `null` 来兜住「球不朝我飞」——看起来
也对，因为飞向墙的球在 3 秒窗口内穿不过击球面。但它兜不住「球就在身边横向飘」：那种球
`v[2]` 只有 0.4 m/s，照样能在 0.25 秒后穿过击球面，预测器给得出点，于是玩家会跟着一个
几乎没有前进速度的球跑。这条用例断言的是**预测器确实给得出点、而 `planAutoMove` 仍然
不追**，变异检验（把 `v[2] <= incomingVz` 改成 `if (false)`）立刻变红。

另外三条变异也验证过：去掉死区 →「死区内不动」红；去掉限速 →「一帧只挪 speed×dt」
和「左右对称」红。

## 4.18 2026-11-13 · 自动走位改成「拍面中心 + 二维」

### (1) 现场：两条反馈

4.17 的走位上线后真机试了一轮，反馈两条：

- 走位瞄的是「拍子竖直能碰到球」，但实际打球时拍子是横着的，应该按横着的来瞄；
- 只有左右走位还是够不到所有球，要加前后。

两条指向同一个被 4.17 刻意绕过的缺口：**走位的目标是握点，不是拍面中心**。

### (2) 根因：握点不是拍面中心

拍面中心在握点沿拍柄 0.6m 处（`pos + R(q)·(0, FACE_CY, 0)`）。4.17 的 `planAutoMove`
把球穿面时的 x 直接当成握点目标 x，这只在**拍柄竖直**时成立——那时中心在握点正上方，
x 与握点相同。握法一横，这根 0.6m 的杆子横过去，中心落在握点侧方半米，而判定半轴只有
0.24m。于是「人站对了、拍面在半米外」，表现就是「明明够得到却打空」。

4.17 当时不补偿，理由是「挥拍会把中心甩出 0.3–1.1m，拿实时中心当目标，玩家一挥拍人就
被拽走」（4.5 的老问题）。这个理由本身没错，但结论下错了：不能用**实时**中心，不代表
不能用**静态**中心。区别在于「挥拍甩出去的位移」和「握法造成的固定偏移」是两件事。

所以这一版的做法是：**只估计握法偏移，挥拍期间冻结**。

```ts
// 中心偏移 c = faceCenter(pose) - pose.pos，长度恒 0.6
blendCenterOffset(prevQ, q, dt, want, c, maxSpin = 0.6, tau = 0.4)
```

角速度 > 0.6 rad/s（34°/s）的帧整帧拒绝。取这个门槛的依据：静止持拍的传感器抖动是个位数
°/s，慢速调整握持 10–30°/s，而慢挥也有 100°/s 以上 —— 留一档余量，宁可少采几帧
（τ=0.4s 会补回来），也别把挥拍的甩动算进「握法」。实测这个判据的效果：换手后约 2 秒收敛，
挥拍中偏移完全不动。

### (3) 为什么必须加 z，而不是「顺便加」

站位的纵深决定「球到面时的高度」。同一个球，站前 30cm 就高 20cm 左右；而拍面竖直半轴只有
0.23m（`FACE_RY + BALL_R`）。所以高度差了，横向再准也是擦框。

4.17 不做 z 的理由是「喂球和回球机都把到面高度夹在拍面覆盖范围内」。这个理由只在**拍柄
竖直**时成立：那时中心高 1.6m，正好是喂球瞄准的高度。握法一横，中心掉到 1.0m，球还在
1.3m —— 差 0.3m，超出半轴，横向怎么走都没用。**所以「要不要做 z」和「要不要补偿 c」是
同一个问题的两面**，不能只解一半。

### (4) 选点：先筛来得及，再挑高度

沿弹道在我方可站区间每 10cm 采一个穿面点（`physics.sampleCrossings`），每个点换成握点
`(p.x - c.x, p.z - c.z)`，然后：

1. 横向超出站位范围就钳位并按半价计惩罚（球飘到边线外也要尽量靠近，不能干脆不追）；
2. 分轴估走到那儿要多久（横移 4.8 / 后退 3.6 m/s，真人倒退还更慢），超过球到面时间就淘汰；
3. 剩下的按 `|球高 - 拍面中心高|` 排序，加 `0.06×耗时` 的微弱惩罚让目标在两帧之间连续。

一个都来不及的时候**不回到中线**，挑「最赶得上」的那个继续追——球已经发出去了，站着看它
落地是更差的选择。

### (5) 纵深从 +1.35 放宽到 +2.0

第一版只把 z 加到 +1.35（底线外 0.15m），横握命中率只有 25%。查下来是：球在可站区间里
最低只降到 1.15m，而横握中心在 1.0m —— 退到头也差 0.15m。放宽到 +2.0（底线外 0.8m）后
球能降到 1.0m 附近，横握从 25% 到 42%。竖握不受影响（它本来就选靠前的位置）。

顺带一个反直觉的实测：**把目标高度抬高反而更差**。试过「wantY 钳到 1.3–1.75」「wantY+0.25」
「wantY 固定 1.45」，横握全部掉到 0–1/12。原因是几何是诚实的：拍面中心真的在 1.0m，球在
1.3m 就是接不到。想让横握接高球只能靠挥拍把拍子抬起来，站位帮不上。**不要为了「看起来
合理」去改目标高度**。

### (6) 实测（改前 vs 改后）

12 条真实来球（回球机求解器生成，三档到面高度 1.30/1.44/1.56 × 横向散布 -2.6…2.6），
球拍**静止不挥**，用真实 `sweepFace` 判这一球撞没撞上：

| 站位策略 | 竖着持拍 | 横着持拍 |
|---|---|---|
| 只走左右（4.17） | 8/12 | **0/12** |
| 左右 + 前后（4.18） | **11/12** | 5/12 |

横握改前是零 —— 拍面中心偏在握点侧方半米，永远不在球上。这条最能说明「瞄准中心」不是
优化项而是正确性问题。横握改后仍只有 42% 是物理上限：拍面中心 1.0m、球 1.3m 以上，
得靠挥拍抬起来。

### (7) 单测：+4 条，加的都是能复现反馈的断言

- **横握时握点要站到球的侧边 0.6m**：断言 `target + 0.6` 落在球心上，竖握作对照。
- **拍面中心低时要后退**：同一条球，横握的 `targetZ` 必须比竖握深 0.5m 以上；
- **弹道采样等距、时间递增、与精确穿面点吻合**（10cm 网格 vs `predictAtPlane`，时间差
  ≤ 一个物理帧）；
- **握法偏移只在没挥拍的帧采信**：静止 2 秒收敛到 ±2cm，30 rad/s 的挥拍帧整帧拒绝且
  偏移值一个字节都不许变。

`planAutoMove` 的签名从 `(ball, planeZ, cfg, homeX)` 改成 `(ball, { x, z, center }, cfg)`。
改动波及 `scripts/sim-e2e.cjs` 的 `MOVE=auto` 分支：那里**仍然只吃 x**，因为该脚本的挥拍
时机是按「球到 HIT_Z」算的，站位跟着 z 变会把时机判据一起改掉，A/B 就不可比了。

### (8) 性能

`planAutoMove` 单次 0.022ms（60fps 下 0.1% 单帧预算，近球 0.007ms）。采样器越过区间上界
即停，多数调用省掉一半以上步进。可以每帧算。

### (9) 验证与未验证

`npm run verify` 全绿：**132 项 ×3、sim 30/30（naive）、duel-sim 三档门禁、build**。
无头 Edge 看过墙打入口页：无异常，画面正常（场地、网、墙、拍子、球都在），底部键位提示
已更新。

**真机仍未验**。特别是有两件事只有真机能回答：

1. 真机的握法偏移是否和模拟里假设的一致（横 0.6 / 竖 0.6，中间值靠姿态算）；
2. 前后走位会不会让人觉得「被拖着走」。限速 3.6 m/s 和 5cm 死区是按体感拍的，没上过机。

## 4.19 2026-11-13 · 握点抬到 1.3m：横握的拍面终于和来球同高

### (1) 反馈

真机上「拍面高度不止 1 米，应该有 1.3 米左右」。这不是视觉问题：`RACKET_POS[1]` 是**握点**
（虎口）高度，横握时拍柄横过去、`faceCenter` 只加 0.6m 的杆长在竖直方向的分量（=0），
所以**横握的拍面中心就等于握点高度**。1.0 就是「球总在我腰上飞过去」的全部原因。

### (2) 改了什么

`court.ts` 的 `RACKET_POS` 从 `(0, 1.0, 0.3)` 改 `(0, 1.3, 0.3)`（胸口中线）。连带：

| 位置 | 之前 | 现在 |
|---|---|---|
| 横握拍面中心 | 1.0m | **1.3m** = 来球高度 |
| 竖握拍面中心 | 1.6m | **1.9m** |
| 墙打喂球目标（瞄当时拍面） | 自适应 1.0–1.9 | 自适应 1.3–1.9，代码没改 |
| 回球机到面高度带 | 1.3–1.6 写死 | `RACKET_POS[1] + 0…+0.3` |
| 机器发球到面高度带（`duel.ts`） | 1.22–1.6 写死 | 同一条带 |

喂球、落地重瞄、回球补偿全都瞄「当时拍面中心」，所以它们**一行没改**就自动跟着上移了——
这是 11-09 把「归一化位姿 + faceCenter」这套定下来之后第一次吃到红利。
`probe-feed.cjs` 实测：竖握到面 1.90m（vy≈1.9，仍在上升）、横握 1.30m，
落点离拍面 1.62–1.71m（还在设计区间 1.55–1.85 内）。

### (3) 到面高度带为什么不跟着整段上移

玩家能到的球壳从 1.0–1.6 变成 1.3–1.9，直觉是「球也该高 0.3m」。实测否掉了：

| `ARRIVE_Y` | 回球 L1 / L2 / L3 |
|---|---|
| **1.3–1.6（选它）** | **27 / 52 / 81** |
| 1.45–1.75 | 22 / 33 / 75 |
| 1.6–1.9 | 26 / 40 / 69 |

到面高度越高，从对手底线（21.6m 外）既要落界内、又要在到面时爬那么高的弹道越少，
回球机只能打月亮球，玩家反而更接不到。所以只取**握点 +0…+0.3**（= 拍面从水平到前倾 60°），
区间宽度保持 0.3m，不跟着放大。

### (4) 代价与它是不是真问题

拍面最低只能到握点高度 ⇒ **低球变难**。`duel-sim` 的 L2 从 59 掉到 52（L1 27、L3 79 基本不动）。
但这是**测试玩家模型**的限制：它对球的倾角固定 14°、只会屈膝到握点下 0.38m，够不到 1.3–1.6
的球就记一次「握点被夹」；真人遇到低球会把拍面压平（这正是游戏里手机姿态的用途）。
所以门禁保留「不回退」的判定，数字下降记录在此，不当回归处理。

### (5) 两条单测被这次改动打回原形

- `补偿瞄的是拍面本身`：触球点写死 `y=1.59`（那是握点 1.0 时的拍面）。改成 `face[1] - 0.01`。
- `回球补偿：竖直拍面…`：原来拿 `RACKET_POS` 那个真实握点当位姿、却要求回球回到 1.6m——
  等于「从腰高出手、回到头顶」，握点一抬高就必然撞墙 5.9m > `WALL_H` 5.2。
  改成按 `Rally.launch` 的真实做法**归一化位姿**（拍面中心平移到 `aimY = 触球高度`）。
  这条错误在 11-09 就埋下了，只是当时握点恰好等于 `RACKET_POS[1]` 才没暴露。

### (6) 验证

`npm test` **132 项**、`npm run sim` 30/30（漏接 0 / 撞网 0）、`npm run duel-sim` 三档门禁、
`npm run build` 全绿。**真机未验**：如果觉得「球整体变高了」，改 `ARRIVE_Y` 或握点，
别去改 `FEED_APEX_*`——那套散布是按判定半轴算的，和高度无关。

## 4.20 2026-11-13 · 握点变成第三个自由度：走位从二维升到三维

### (1) 反馈：三条，其实是两件事

4.19 上线后真机试了一轮，反馈三条：

- 离球太近，经常打不到；
- 网前的球完全移动不过去；
- 击球动力学不好：很多球「看着打上了但实际没打上」，有时打到了但球回弹很慢。

前两条是走位，第三条是触球质量。查下来**第三条是第一条的下游症状**——不是判定或出球公式的问题。

### (2) 用归一化判定坐标把「看着打上了」量化

先要一把尺子。`sweepFace` 的判据是球心到拍面椭圆盘的距离，所以把触球点换算成盘内归一化坐标
`(u, v, n)`（`u` 横向 / `v` 纵向 / `n` 法向，各除以对应半轴），`max(|u|,|v|,|n|) <= 1` 才算真进拍面。
写了个临时探针（`.tmp-bench/duel-probe.cjs`，未纳入版本库）逐球记录它，一档 42 球：

| 握法 | 真进拍面 |
|---|---|
| 斜握 14° | **2 / 42** |
| 竖握 | **0 / 42** |
| 横握 | 34 / 38 |

「看着打上了」的来源清楚了：球从拍面**下方 10–25cm** 掠过，`v ≈ -1.1`。

### (3) 根因：拍面中心被锁在一段球壳上

`faceCenter(pose) = pos + R(q)·(0, FACE_CY, 0)`，而 4.19 把握点 `y` 写死在 `RACKET_POS[1] = 1.3`。
于是拍面中心只能在这段球壳上：

| 握法 | `c.y` | 拍面中心高度 |
|---|---|---|
| 竖握 | 0.60 | **1.90m 固定** |
| 斜握 14° | 0.53 | **1.88m 固定** |
| 横握 | 0.00 | 1.30m 固定 |

回球机的到面高度带是 `[1.3, 1.6]`。竖握/斜握的拍面恒在 1.88–1.90m，**比球高 0.3–0.6m**——
几何上根本没进椭圆，怎么挥都没用。而 4.18 加 `z` 的思路是「站远一点让球掉下来」，可是：

- 顶多能把球降到 1.63m，还是够不着 1.88；
- 为了找「`|p.y - wantY|` 最小」的平面，选点循环会把玩家拖到底线外 2m（`planZ` 一直是 0.30，
  人却在 z=1.8）。这就是「离球太近打不到」的机制——**高度差不是站位能补的**。

### (4) 改法：`y` 是第三个自由度，不是补丁

`planAutoMove` 的返回值加 `targetY`，`AUTO_MOVE_DEFAULTS` 加 `speedY / minGripY / maxGripY`，
`app.ts` 的 `PLAYER` 加 `y`。三个轴各有自己的限速和钳位：

| 轴 | 范围 | 限速 | 含义 |
|---|---|---|---|
| `x` | ±3.9 | 4.8 m/s | 横向跑。原来 3.0，够不着小斜线 |
| `z` | HIT_Z−3.0 … HIT_Z+1.0 | 3.6 m/s | 纵深。前端放到网前 3m，后端只到底线内 |
| `y` | **0.70 … 1.65** | 9.0 m/s | 深屈膝 ⇄ 举拍 |

于是「球高了」的答案从「退到球掉下来」变成「把拍子沉下去」。选点循环里高度变成**硬约束**：
`overY > 0.01` 的平面直接淘汰（够不着就是够不着，不该靠代价函数软性折中），代价函数才是
`0.9×|姿态| + 0.7×|站位| + 1.2×横向超出 + 0.06×耗时`。

### (5) 网前球：两处都要改

短球的失败有两个独立原因，只修一个都还会漏：

1. 旧 `minZ = HIT_Z - 0.55`，人根本走不到网前；
2. **`sampleCrossings` 不知道「两次落地判死」**，会推出一条不存在的「二次弹起后飘到击球面」的
   弹道，规划器就把人放在终点等着。实测短球落在 z≈−8，弹一下在 z≈−1.4 就死（-22.05 起手扫 vy/vz，vz=13/vy=5.5 那一条：−8.01 → −1.40），那条弹道压根不存在。

第 2 条先写错过一次：初版判据是 `ourBounces >= 2`（只数「从现在起」），横握失败只从 35 降到 7。
原因是**来球往往已经弹过一次**，得从 `ball.bounces` 起算，并且判据要和 `rally`/`duel` 的
`bounces >= 2 && at[2] > NET_Z` 完全同源。改对之后横握 39/39。

### (6) A/B：改前 vs 改后

## 4.22 2026-11-14 凌晨 · 击球前抖一下 / 挥拍不是绕拍柄转 / 机位太远

第 1 条先取证再改，见 (2)；第 2 条是新加的一层几何，见 (3)；第 3 条只是机位，见 (4)。

### (2) 「击球前抖一下」：目标是每帧重选的，而且球一过就立刻回中

`scripts/probe-jitter.cjs`（复刻 `app.ts` 的 `updatePlayer`，逐帧记握点与目标）
把「球到面前 300ms」的握点位移拉出来看：**前后方向在一帧 6cm、下一帧 -6cm 地反向
2–7 次**（横握最严重，5.9 次/球）。单帧 6cm 的方波在屏幕上就是拍子在抽，而且
`setRacketBase` 平移相机，画面跟着一起晃。

两个来源，各自独立：

1. **规划器每帧重新选平面。** `sampleCrossings` 的候选网格锚在区间下界上，而下界是
   `max(球当前 z, 下界)` —— 网格跟着球往前滑，球飞一帧 6cm，所有候选平面整体平移
   6cm；相邻两格的代价只差千分之几，排序每帧翻一次，`targetZ` 就在 0.30 / 0.36 之间跳。
   `stepAxis` 把它当成「真的要挪」，按 `speedZ` 满速走 6cm 再走回来。
2. **`chasing` 翻 false 的那一刻目标瞬间回中。** 球越过拍面 → 目标变成回中点 →
   握点高度从「蹲着接低球」一跳回 1.3m。按 `speedY`=9 m/s 算是**单帧 15cm** 的竖直
   弹跳，正好落在挥拍最后那两帧上，读起来也是「击球时拍子抖一下」。

第一次修法是「把网格锚死成绝对坐标」。**错了，已回退**：网格跟着球滑是**响应性**
的来源（球当前所在的平面永远是候选），锚死之后最后一刻的横向偏差从 0.16m 抬到
0.29m，单测「中途跑开 2.2m」直接红。这条记在这里，免得下次又有人去「顺手修掉」。

真正的修法是**在目标和执行之间插一层保持器**（`TargetHold`，`core/auto-move.ts`）：

- 新目标离上一次不到 **0.10m** 就当没听见。10cm 比判定盘等效半轴（横 0.20 / 竖 0.24）
  小一半，落在里面本来就是「打得到，只是没那么甜」；
- 超过 10cm 才采纳（球换了落点/高度），一次跳过去，由 `stepAxis` 的速度上限拉成几帧；
- `chasing` 翻 false 之后先**原地保持 250ms**（够一次随挥收完），回位那一段的 y 用
  `homeSpeed`（3.2）而不是举拍的 9 m/s。

改完复测（同三个握法、165 球）：反向次数 **0.0 / 0.0 / 0.0**，单帧最大位移回到
0.11–0.13m（那是横移 4.8 m/s 的正常速度，不是抖动）。顺带把「中途跑开」那项的
最差横向偏差从 0.158m 压到 **0.076m** —— 保持器不只是防抖，它让人**站得住**。

### (3) 挥拍枢轴：给握点补一段它本来就该有的平移

见 `docs/algorithms.md` 3.10，这里只记取舍与踩过的坑。

- **不是反解骨架，是补一段平移。** 手机只给得到握点朝向。要让「轴」落在腰或肘上，
  唯一的手段是把握点自己也搬过去：`pos = P + R·(base − P)`，`P` 在腰与肘之间按手部
  角速度切换。转角趋零时它自动退化成 `base`，所以静止、走位、握法估计**一行都不用改**。
- **第一版把握点搬了 0.9m，直接漏接。** 用完整姿态增量去绕枢轴转，手腕自转也会
  把拍子甩出去；即使只用拍柄方向的最小弧，28 rad/s 那一档拍柄扫过 149°，腰的半径
  0.48m 乘出来就是半米。所以有两条夹子：`gain`（0.4，只缩转角）+ `maxShift`
  （0.18m，直接夹位移向量长度）。模拟器 A/B 见 `docs/algorithms.md` 3.10 的表：
  0.20 以内命中率和老行为一样（396 击球），0.35 以上才开始真漏。
- **为什么不做「拍面锚死在空间里」**：AGENTS.md 0.5 已经否过一次（拍子只转不平移）。
  这次的枢轴是「整支拍子绕身体走弧」，旋转和平移都有，只是平移被限了幅。
- **开关**：`G` 键 / `?rig=0`。真机 A/B 必须留着——位移会不会让人更容易打空，
  只有手能回答。

## 4.23 2026-11-14 深夜 · 走位瞄错了拍面 / 高度看不出来 / 抖动的最后一点

### (1) 三条反馈，一条根因链

真机第二轮（4.22 之后）：**挥拍「可以」**，抖动「没有之前严重，但有时还会」，另加两条：

1. 走位没控制好与球的**水平距离**——「好像是发球时根据球拍角度预估的距离，但拍子角度在变」；
2. 拍子**竖直高度**永远同一个高度，希望跟着来球上下 20cm 微调。

第 1 条是这一轮的主菜：它的根因和第 2 条、和「抖动的最后一点」都在同一条链上——
**走位瞄的那个「拍面中心」，是站着不动的拍面，不是挥下去那一刻的拍面。**

### (2) 挥手会把瞄准点搬走 40–60cm

拍面中心挂在握点沿拍柄 0.6m 处。`sim-e2e` 的挥拍波形（ω = peakW·sin(πu)，150ms）在
峰值 15 rad/s 时，球到面那一刻拍柄已经转过约 41°，`|R(41°)·c − c| = 2·0.6·sin(20.5°)`
≈ **0.42m**。判定盘等效半轴只有横 0.20 / 竖 0.24 —— 也就是说「瞄哪儿」和「打在哪儿」
差了一整个拍面还多。

老代码只在角速度 < 0.6 rad/s 的帧采信 `faceCenter`（4.5 留下的判据，防「一挥拍人被拽着
跑」），于是它估的是**握法**，不是**击球姿态**。

新探针 `scripts/probe-contact.cjs` 复刻整条链路（规划 → 保持器 → `stepAutoMove` → 挥拍
枢轴 → 偏移估计），挥拍是真的在转，量「击球那一刻真实拍面中心 − 瞄准点」：

| 握法 | 老行为 | 学了 `contactDelta` 之后 |
|---|---|---|
| 斜握 14° | 0.128m（几乎全在 z） | **0.040m** |
| 横握 | 0.373m（x 0.210 / z 0.308） | 0.03 量级（样本少，见下） |
| 竖握 | 0.218m（y 0.092 / z 0.197） | **0.028m** |

横握那一栏的「之后」样本不足：换握法会让来回球的散布跟着变，同一局里能比较的球不多。
这一格留待真机。

### (3) 偏移拆成两份，而且必须「同源」

- `restOffset`：实时 `faceCenter − 基座`，只吃角速度 < **1.2 rad/s** 的帧、τ=0.3s。
  原来是 0.6 rad/s / τ=0.4s。0.6 rad/s 只有 34°/s，**正常的手部微动都会被挡掉**，估出来的
  握法卡在开局那一次——这正是「发球时估一次，之后拍子角度变了也不跟着改」的直接原因。
  1.2 rad/s（69°/s）仍远低于真实挥拍（100–1700°/s），该挡的还挡得住。
- `contactDelta`：命中那一刻 `faceCenter − 基座` 再减掉 `restOffset`，即「挥拍比站着多扫
  出去的那一段」。每命中一球 EMA 0.45，逐帧 τ=0.45s 收敛（两拍之间不跳）。单轴夹 ±0.55m。

**踩得最深的一个坑：只改走位会把人推到边线。** 喂球（`Rally.aimArrival`）是瞄
`faceCenter(这一帧的姿态)`，走位瞄 `基座 + planOffset`。如果只把走位的偏移换成新的，
球仍被瞄向老位置，人走到新位置后拍面又偏了一段；下一球落地重瞄，球还是瞄「那一刻的拍面」，
于是**每球累积一次**偏移，人一路被推到 `maxX`。所以加了 `Rally.setFaceAimOffset(planOffset)`，
两边用同一份。这条写进了 AGENTS 0.8 的「不能碰」。

`planOffset` 初值是 `[0, FACE_CY, 0]`（竖直握），`contactSamples === 0` 时等于老行为——
**第一球一定还是老的**，打中一球才开始学。所以真机判断这一层至少要打三四个球。
要做 A/B 就 `?aim=rest`（关学习、球飞回老地方），它没绑键位：这是「这一局怎么打」的选择。

还有一个兜底（`noteMiss`）：**没命中就不学**，所以万一学歪了（换握法、换了挥拍幅度、
或者干脆没在挥）就永远出不来。连丢三球之后每球把 `contactWant` 缩 30%，等于往回退到
`restOffset`——老行为至少不会系统性偏半个拍面；打中一球就清零重来。

### (4) 高度：规划器一直在动，是执行层把它做成了「瞬间」

`targetY` 本来就在 0.70–1.65 之间随来球高度变（探针实测握点 0.94–1.62）。问题在速度：
`speedY`=9 m/s 是**一帧 15cm**，抬起来是一瞬间，读不出「在调整」；而且 `chasing` 一翻
false 就回 1.3m、回位用 `homeSpeed`，两球之间看到的一直是回位后的姿势 ⇒ 「永远同一个高度」。

改成两段（`stepAutoMove`）：

- 球还远（`eta > heightLead` = 0.45s）：目标只许偏离中立位 `±heightBand`（**20cm**），
  速度 `speedYSlow` = **1.8 m/s** —— 走完 20cm 约 110ms，肉眼能读出「跟着球抬起来」；
- 球越近，开闸权重 `w = (lead − eta)/lead` 把目标连续推向 `tg.y`，到面那一刻满行程、
  `speedY` = 6 m/s。

**不能硬切**：第一版是 `eta > lead` 就夹、否则放开，探针立刻在 `eta === lead` 那一帧看到
目标跳一次、人反向一次（y 反向 0.04 次/球）。改成连续开闸后回到 0。

顺带把高度死区单独拆出来（`deadbandY` 0.02，横移还是 0.05）：竖直半轴只有 0.24m，
5cm 死区等于先送掉四分之一余量。

### (5) 抖动的最后一点：相机是刚性跟随的

反向次数已经是 0（`probe-jitter` 三种握法 0.00 / 0.00 / 0.00），但「有时还会抖」是真的：
`setRacketBase` 把相机的 x/z **当帧**搬同样的距离。走位每帧的修正都直接变成整屏平动，
规划器偶尔改一次主意（4–8cm/帧）就是视野猛抽一下；近景机位把这件事放大了（相机离拍子
只有 2.2m）。

改成累积 + 追赶（`scene.camLag`，τ=0.12s）：总位移守恒（走多远跟多远），单帧突变摊成几帧。
残余不足 2mm 时一次搬完，避免永远差一点。切机位（`Z`）时清零，免得多搬一次。

### (6) 执行器抽到核心层

`stepAutoMove(cur, plan, tg, dt)` 从 `app.ts` 搬进 `core/auto-move.ts`：限速步进 + 边界夹取 +
高度两段全在里面。原因是 `probe-jitter` / `probe-contact` 各抄了一份——抄的那份一漂，
探针量到的就不是玩家身上的行为，而**这一轮的三个结论全靠这两个探针**。

### (7) 测试与验证

`tests/core.test.cjs` 新增 6 项（134 → **140 项**，21 → **22 个分组**）：

| 分组 | 项 | 内容 |
|---|---|---|
| 走位执行 | 6 | 球还远时一帧只挪 3cm（不是瞬移）；预位停在 ±20cm；球到面前才放开全行程；预位→对位**连续开闸**（y 随 eta 单调下探，且不越过目标）；球过去后回位用 `homeSpeed`；三轴各自限速 + 边界 |

`npm run verify` 全绿：**140 项 ×3、sim 30/30、duel-sim 三档门禁、build**。
无头 Edge 截图确认页面无控制台错误。

**真机未验**，三件事只有手能回答：

## 4.24 2026-11-14 深夜 · 真实赛制（分 → 局 → 盘）+ 发球

### (1) 需求

> 「可以将计分模式改成真实比赛的分-局-盘形式吗？一盘结束定胜负。每个人的发球局，
> 一分可以发两次球。轮到玩家发球时游戏自动发球（正上方垂直抛球），但需要玩家手动
> 挥拍发球，且需要发到正确的区。」

四件事：**真实赛制 / 一盘定胜负 / 每分两发 / 玩家发球是自动抛球 + 手动挥拍 + 必须进区**。

### (2) 拆成两个新模块，而不是往 `Duel` 里塞

`Duel` 已经 700 行。规则和几何再塞进去会变成「读不懂、也测不动」的一块，所以：

| 新文件 | 内容 | 为什么单独 |
|---|---|---|
| `core/match.ts` | 分 → 局 → 盘、平分/占先、发球区交替、抢七 1-2-2 | 纯状态机，**不碰球、不碰场地、不读时钟**。想换三盘两胜只改这一层 |
| `core/serve.ts` | 发球区 / 站位 / 抛球 / 拍面 → 落点 / 抛球接触 | 纯函数。`Duel`（判定）、`app.ts`（HUD 圈）、`scene.ts`（地面高亮）、单测用的是**同一份** |

`Duel` 只在「这一分归谁」定下来之后调一次 `match.awardPoint()`，照返回的 `PointOutcome`
决定播 `game` / `tiebreak` / `matchOver`。

**计分存原始计数（0,1,2,3,4…）而不是 0/15/30/40**：平分和占先是相对关系，存绝对值就得在
每一处判断前后关系；存计数只在显示时换算一次（`pointLabel`），判定只有「>=4 且净胜 2」。

### (3) 发球的三个「这条路走不通」

**(a) `sweepFace` 判不到竖直抛球。** 拍面碰撞是「球段穿过椭圆盘所在平面」，要求 `n0`、`n1`
异号。竖直抛球 + 竖直拍面时球是**沿着**平面走的，永远同号，一次都判不到。改成球形判定
`tossContact`（球到拍面中心最近距离 < 0.34m），既绕开退化，又正好符合「球在拍面上方一点点」
的实际情形。

**(b) 抛出那一帧就能发球。** 抛球出手点 1.95m，而发球站位上握点举到 1.62m、竖握时拍面中心
就在 2.22m——球抛出来就已经躺在判定球里了。于是加一条 `vy <= 0.5`：**只认下落段**。卡住之后
接触点在 2.2–2.6m 的下落段，距抛球约 0.42 秒，正好是真实发球的节奏。

**(c) 纵深不能取射线交点。** 直接拿拍面法线与地面的交点当落点，纵深由俯角唯一决定；从 2.25m
高、13m 外看，能落进区的俯角窗口只有 **7.2°–10.8°**（宽 3.6°）。那不是技术，是几何太窄。
改成**映射**：俯角 3° 打深、18° 打浅，整段 15° 都落在区里；左右**不夹**——瞄另一半区就是失误，
那才是「必须发到正确的区」这条规则的用处。

### (4) 门禁一开，暴露了三个真 bug

改完 `Duel` 先跑 `npm run duel-sim`，红得很难看：**78 分里没有一分打出过回合**，
两边都是「发球直接得分」。三个独立的原因：

**(a) 侧旋把球甩出 1.5m。** 模拟器的发球挥拍方向 `[0,14,-7]` 与拍面法线差了十几度，
`shotFromStroke` 切出来的侧旋让球在飞向对面击球面时横向漂 1.5m，正好飘出 `reachX`。
落点仍然判在发球区里（合法），但接发方够不到。→ 挥拍方向改成与拍面**平行**，零侧旋。

**(b) 「幽灵走廊」：`reachX` 有两个数。** `pickIntercept` 的过滤线是 `reachX + 0.6`，
而 `moveToward` 的夹取是 `±reachX`。3.0–3.6 之间于是成了一条只能看不能去的走廊；`gap` 又是
按**夹过的目标**算的，读出来是「我站好了」。平时看不出来——玩家回球的横向散布是 ±2.6，
几乎不进那条缝；**发球是斜对角的，落在区中心的球到击球面时已经飘到 ±3.4**，一上线就撞上。
→ 三处共用 `reachLimit()`，`gap` 改成量**拍心到球**的真实距离。

**(c) 机器发球是一条接不到的弹道。** `machineServe` 用 `aimIntoCourt` 的 `arriveY` 约束
（到面 1.3–1.6m）。实测 24 个落点**一次都解不出来**，于是每次都退到「只要落点进区」那一档，
发出来的球在拍面高度只剩 **0.4 米**。根子在几何：发球区到接发方击球面还要再飞 4.8–10.8 米，
平飞过去的球在 z≈−3 就二次落地了；只有抛高一点才带得动一整个第一弹的弧线。
→ 不再「解」，改成**扫**：固定 `vy`=5.0–6.0（顶点约 4.2m），只扫水平速度 12–18 m/s，
用真物理前向跑 39 条弹道，留「第一次落地在区内 + 到面 1.35–2.10m + 之前没有二次落地」的那条。

修完：L2 平均回合 0.0 → **2.9 拍**，最长 12 拍。

> 代价是机器会发一种顶点 4.2m 的月亮球。**这不是调参没调好**：想让它发得更冲，先得让玩家
> 能在更低的拍面高度接球（`docs/known-issues.md` 7.3 第 14 条）。

## 4.25 2026-11-15 凌晨 · 抛球太低 / 反手接不到 / 走位被夹在场内

### (1) 需求（真机反馈，三条）

> 1. 抛球太低了，无法完成上手发球。而且抛球相对球拍的位置不合理，很难把球发进区。
> 2. 反手没有正确处理拍面法向，导致反手无法接球。
> 3. 走位有时还是不太合理，导致接不到球。对于两侧落点比较刁钻的球，走位被约束在了
>    场内，更接不到球。应该允许走位到场外或网前。

### (2) 抛球：位置锚错了对象

真机那句「相对球拍的位置不合理」是钥匙。旧代码：

```ts
// startToss —— 从**拍面中心**抛
const fc = faceCenter(pose);
this.ball = makeBall([fc[0], TOSS_Y0, fc[2]], [0, TOSS_VY, 0]);
```

拍面中心挂在握点沿拍柄 0.6m 的杆子末端，所以它的位置完全由手机的**朝向**决定：

| 举拍的握法 | 拍面中心在哪 | 球抛到哪 |
|---|---|---|
| 屏幕朝前（拍柄竖直） | 握点正上方 2.22m | 头顶 |
| 屏幕朝天（拍柄朝前） | 握点正前方 1.62m | 胸前 0.6m 外 |
| 斜握 45° | 斜上 45° | 斜前方 |

同一句「抛球」抛到三个地方，玩家把拍子举到头顶时球不在那儿。而且顶点只有
1.95 + 3.9²/19.6 = **2.72m**，比竖直握的拍面（2.22）只高 0.5m——看起来不像抛球，
像把球往上递了一下，也没法做出「球从上方落下来、拍子迎上去」的上手发球。

**改法**：抛球点、击球区都锚在**握点**上，与手机怎么转无关。

- `SERVE_STRIKE_UP/FWD` = 上方 0.53m、前方 0.25m —— 额头前上方那一块；
- `TOSS_Y0` 1.95 → **2.05**（举拍时手的高度），`TOSS_VY` 3.9 → **5.2**：
  顶点 **3.43m**，比拍面高 1.2m，出手到可击球约 **0.95 秒**（真人约 1 秒）；
- `serveStrike(pose)`：拍面中心离锚点超过 `SERVE_ANCHOR_R`=0.35 就朝锚点收。
  竖握时中心本来就贴着锚点（原样返回，球仍打在拍线上），横握时中心离 0.63m →
  收进 0.35，判定球（0.42）才盖得住那颗抛在头顶的球；
- `SERVE_REACH` 0.34 → **0.42**：可击球窗口从 0.2 秒拉到 0.4 秒。

实测（`.tmp-probe-serve-e2e`）一次真实发球：**击球点 y=2.45m**（原来是 2.2 上下，
也就是「举到胸口上面一点」），落点 (−2.06, −13.65) 正好在右区里。

### (3) 发球进区：两个独立的障碍

**(a) 左右合法窗口只有 15.6°。** 从发球位看对角发球区：指向左边缘 −20.4°、右边缘 −4.8°。
按射线求交，拍面偏 8° 就出区——而玩家同时还要控俯角（3°–18°），手上一拧就出去了。
→ 新增 `YAW_GAIN`=0.65：偏角**相对区中心**压缩 0.65 倍再用。窗口 15.6° → **23°**，
中心仍然指向区中心（「指向区中心 = 绿」的直觉不变），转过头 17° 仍然出区
（「发错区 = 失误」这条规则还在，没有白送的进区）。

**(b) 屏幕朝天时，法线根本没有水平分量。** 举高手机时最自然的握法是屏幕朝上，
这时 `f ≈ (0,1,0)`，`atan2(f[0], -f[2])` 是一条纯噪声，`serveAim` 直接走
`far: true` 分支——红圈，怎么发都不进。
→ `aimAxis()`：法线不朝球场时，改从拍柄的两头里挑**朝网的那一头**当准星。
「拍面朝天 = 用拍框瞄」，`serveAim` 多了个可选的 `shaft` 参数。

### (4) 反手：判定从来没错，错在出球方向的符号

`sweepFace` 判的是「球心到**椭圆盘**的距离」，椭圆盘对法线正负号本来就不敏感——
所以反手**碰得到**球，只是碰完球飞回自己半场。问题在 `shotFromStroke`：

```ts
const alignment = dot(face, FORWARD);   // 反手拿到 ≈ −1
const clean = alignment > 0.15;         // false
// 注释写着「故意不改方向，让球照着拍面飞出去」
```

网球拍是**双面**的：正手打正面、反手打背面，几何上完全等价，球只看有没有碰到拍线。
设备只给一根 +z 法线，反手时手机翻了个面，这根法线就指着玩家身后。于是
`alignment ≈ −1` → 走「拍面完全背对」那条分支 → 球往后飞 → 判「没过网」。

**改法**：`racket.ts` 新增 `frontFace()`，只在**明确朝后**（`z > FACE_FLIP_Z`=0.12）
时翻面。三处生效：

1. `SwingDetector.buildStroke` 建拍时就翻好，`Stroke.face` 从此永远是「朝球场那一面」；
2. `shotFromStroke` 内部再翻一次（幂等）——纯函数不该依赖调用方先归一化；
3. HUD 的「拍面 右 x°」也用它，否则反手位会一直读到 180°，看着像握歪了。

副作用是「拍面没打开」的含义变了：原来是「背对球场」，现在是「拍框正对来球（侧着 90°）」。
这才是真实网球里打不出去的那种。原来那条单测（「拍面背对 → 球往后飞」）跟着改写成
「拍框侧着 → 球横飞」，另加一条「反手与正手出球逐位相同」。

### (5) 走位：站位不是落点

`maxX` 是 3.9，比单打边线（4.115）还往里 0.2m，注释写着「站在线上不算出界」——
但那说的是**落点**，不是站位。真实球员接边线球会跑出边线一两米再跑回来，
卡在场内就等于「边线球必失」：球从 x=4.6 经过时人贴在边线上够不到，判定盘半轴只有 0.2m。

| 常量 | 旧 | 新 | 依据 |
|---|---|---|---|
| `maxX` | 3.9 | **5.6** | 边线外 1.49m（跑到双打通道就停） |

### (1) 症状不是「抖」，是「判据的阈值和它要过滤的东西一样大」

用 A/B 对照确认是 `auto-move.ts` 引入的（把文件换回 HEAD 版本、重编、重跑，
反向次数回到 0）。逐帧 dump 之后一眼看穿：

```

 742   [-4.78, 4.20]    [1.301,-0.083]   [1.301,-0.083]   0.109 SWITCH

```

`TargetHold.holdR` 是 0.10，而 `sampleCrossings` 沿弹道按 **0.10m** 采点——
**相邻两格候选的距离正好等于阈值**。两个候选交替胜出时每次切换 0.101，
「刚好越过」，判据形同虚设：742 帧换过去、743 帧换回来，握点跟着反向一次。

这是个记账错误，不是调参问题：0.10 当年是按「判定盘是它的两倍」定的，没人算过
它和采样步长的关系。步长决定「相邻候选差多少」，阈值必须**严格大于**步长，
否则「相邻那一格」会被读成「新的决定」。

### (2) 改法：`holdR` 写成 `CROSS_STEP × 1.4`

```ts
export const CROSS_STEP = 0.1;        // 采样步长，导出是为了让约束看得见
const HOLD_R = CROSS_STEP * 1.4;      // 0.14
```

取 1.4 的理由：z 走一格 0.10，y 沿弹道跟着抬 0.03，合起来 `hypot(0.10, 0.03)` = 0.104，
1.4 倍留 4cm 余量；再往上（2 倍以上）就会开始把「真的换落点」也吞掉。
上限仍是判定盘半轴（横 0.20 / 竖 0.24），0.14 还在里面。

**没有**把握持器改成「阈值 vs 本帧步长的比例」：步长（5.4/60 = 9cm）本身就和
holdR 同量级，用比例等于把阈值交给跑速，跑速一动走位就换性格。也不改兜底代价的
权重——那两个方向相反的项是有意义的（高球要够得到、近距离要赶得上），
排序翻是它们的正常结果，该由保持器吸收。

### (3) 两个探针改接到对打的喂球上

用户的要求是「保住这两道门禁」，所以它们必须能跑，而且读数必须可信。

顺带修了一个判据定义问题：`y` 方向出现 0.10 次/球的反向。逐帧看是「蹲到 0.90 接低球
→ 球过去 → 停 250ms → 起身回 1.30」，中间隔十几帧零位移——那不是抖动，是起身。

**这不是放宽断言，是修判据的定义**：抖动的定义是「相邻帧来回走」。

**`probe-contact`（瞄准点误差）**：这一步比预想的深，走了三版。

第一版直接把来球换成 `Duel` 的。结果**竖握 / 横握 16 球 0 命中**。原因不是判定坏了：
回球机瞄的是固定高度带（`ARRIVE_Y` = 1.3–1.6m），不管你把拍面放在哪儿。这对真人
是对的（人自己会去够球），对**探针的固定挥拍**是致命的——同一个 `PEAKW` 挥所有球，
拍面中心在挥拍中段被甩出 0.3–0.4m，竖握/横握正好把球路扫开。量出来的会是「挥拍幅度
和来球高度不匹配」，不是 `contactDelta` 该补的那段误差。

第二版改成自己喂球：`aimIntoCourt` 把球送到**瞄准点**（`base + planOff`），
求解器和回球机同一个。这样 Δ 就是纯粹的「瞄准点 vs 真实拍面」。于是又撞上两件事：

- **落点可行域不是任意的**。`arriveY` 是硬约束，而「到面多高」由落点深度决定。

- **喂球会跟着玩家的漂移跑**。落点的 x 是「打哪儿」，不等于「穿面时在哪儿」；不管这个
  差，探针 40 秒能漂到 ±4.9m（场外），然后所有喂球都解不出来（竖握实测 2055 次解不出）。

| 触发 | 时机 | 丢多少 |
|---|---|---|
| 攒够 8 条 | `recordContact` 末尾 | 最多 7 球 |
| 停手 10 秒 | `setInterval` | 几球 |
| 关页 / 刷新 | `beforeunload` + `sendBeacon` | 0（浏览器保证送达） |

`sendBeacon` 是必须的：`fetch` 会随页面一起被取消，卸载路径上唯一可靠的就是它。
上限 64KB，正常最多 8 条约 3KB。

**文件名 = 页面打开时刻。** `20261115-161230.jsonl`（`contactRunId`）。刷新一次就是
新文件，所以「同一份文件里混进两次会话」不可能发生——那比丢数据更难查。服务端不做
时间戳、不做去重，只 append；幂等性靠客户端游标 `contactFlushed`（**只在成功后推进**）。

**降级。** 服务端不可用时（直接开 `dist/`、或 preview 没挂中间件）`K` 退回浏览器下载。
这条路径保留是为了「不猜环境」——宁可多一个出口。

### (3) 三处刻意的取舍

**没有用 File System Access API 写文件句柄。** 它确实能做到真正流式 append，但需要
用户手动选一次目录并授予持久权限，而 dev server 就在同一台机器上，一个 POST 就够。
用更简单的机制解决同一个问题。

**没有把 localStorage 当兜底。** 考虑过：`push` 时追加写 `localStorage`，刷新后恢复。
但既然已经有一个**同机的**服务端，磁盘就是比 localStorage 更好的存储——没有 5MB 上限、
不会被清缓存带走、导出不用额外步骤。两套兜底反而增加「到底哪份是准的」的疑问。

**自动落盘失败不抛、不打断打球。** `flushContacts` 里 catch 住，游标不推进，下一批
连同这批一起发。极端情况下可能重复写一次（服务端 append 不去重），但重复一行数据比
少一行数据好诊断——前者一眼看出来，后者永远是个谜。

## 4.29 2026-11-15 晚 · 定一条规则：发球不进校准器训练集

### (1) 需求

用户原话：**「加一条规则，发球不放在训练数据中。因为现在的发球抛球位置已经比较合适了，

理由值得原样记下来——它不是「暂时没做」，是**已经解决过的问题不再进数据集**：抛球点
与击球区在 4.25 已经重锚到握点、顶点抬到 3.43m，真机反馈位置合适。发球不需要校准，
所以它在训练集里只是噪声。

### (2) 查出来的现状：这条规则其实已经成立，只是没写在任何地方

发球走的是 `Duel.tickToss` 里**独立的 `tossContact` 判定**，不经过
`checkReceiverFace` / `enterContact` / `watchNearMiss`，所以**一条 `contact` 事件都
不会发**。26 条真机样本里 `meta.serve` 全为 `false`，`at[1]` 最大 1.66m（发球击球点
在 2.4m 左右）——数据本身也印证了没有发球样本混进来。

但这意味着 `serve` 是个**僵尸字段**，`usableForCalibration()` 里的 `!serve` 是永不
触发的防御。规则靠「发球恰好走了另一条路径」这个实现细节维系，任何一次「把发球并进
统一采集好攒更多数据」的改动都会静默破坏它，而且**破坏之后没有任何东西会响**。

### (3) 做法：把规则写在三处，并加一条会红的测试

- `ContactCapture.serve` / `ContactSample.meta.serve` 注释改成「当前恒为 false，以及
  为什么这是定下来的规则」；
- `tickToss` 顶部标明**它就是这条规则的实现点**，并写了「别为了多攒数据把它并进统一
  采集」和护栏测试的位置；
- `usableForCalibration()` 保留 `!serve`，注释说明它是「让规则在代码里可读、可测」，
  而不是依赖路径偶然性；
- 新增测试：构造发球相位、球从握点前上方落下、球到击球区时挥拍 —— 断言**这一发真的
  打出去了（有 `hit` 且 `serve: true`）**，同时 `contact` 事件数为 **0**。

测试里那条「真的打出去了」的断言是关键：只断言 `contact === 0` 的话，球没被打中也会
通过，等于什么都没测。

### (4) 踩到的一次「测了但没测到」：拆掉门限测试居然还是绿的

第一版注释把「发球不进采集」归因给 `checkReceiverFace` 开头那句

说明归因错了：`update()` 在 `phase === 'toss'` 时直接派给 `tickToss`，

注释已改成正确的那条链，并把「这一行挡的是 `contact` 阶段的重复判定」写清楚。这次
反向验证的价值就在于：**如果不做，注释会把后来人引到错误的代码位置**，而测试是绿的，
看不出任何问题——这正是 `docs/tuning.md` 6.3 那条「单测全绿、真机全漏」的同一个形状。

## 4.30 2026-11-15 深夜 · 样本补三个走位量：瞄准点、保持半径、死区

### (1) 为什么

26 条真机样本看完之后，最想回答的问题是「瞄准点和真实击球点差多少」，结果算不出来——
`meta` 里**没有记 `planOffset`**。上一轮讨论时说的是「它不能进特征」，实现的时候被
读成了「完全不记」，于是诊断那一半也一起丢了。

只有 `meta.offCenter` 可用，而它是判定层的三维距离，**已经混进了挥拍带来的那一份**，
拆不开。加上 `holdR`（0.14）和 `deadband`（0.05）这两个「按设计允许的静差」也没记，
所以即使拿到了残差，也没法判断「这 19cm 里有多少是设计、多少是真的偏」。

### (2) 加了什么

| 字段 | 位置 | 为什么 |
|---|---|---|
| `planOffset` | `meta` | 相遇**前**的瞄准点。用来算残差 |
| `holdR` | `meta` | 当时生效的保持半径。残差里「按设计不动」的那一截 |
| `deadband` | `meta` | 同上（x / z 轴） |
| `deadbandY` | `meta` | 竖直轴死区 0.02，**和 `deadband` 不是一个数**，只记一个的话减 y 会减多 |

`buildContactSample` 的输入接口把三项设成**必填**，不是可选：漏传会静默少一个字段，
而数据文件看起来完全正常——这正是最难查的那类错。TypeScript 现在会拦住新调用方。

`holdR` 通过 `TargetHold.radius` 读**实际生效值**，而不是在调用处引用 `HOLD_R` 常量：
构造时可以传别的值（探针里就有），引用常量记下来的就不是当时用的那个了。

### (3) 顺手把残差定死成一个函数

三个字段单独存在没有意义——每个人都会自己写一遍残差公式，而且算错的方式还不一样。
`aimResidual()` 的注释里给出了推导：走位把握点放在 `G = p − planOffset`，相遇时
`fc = G + rest + delta`，两式一减

```
fc − p = delta − (planOffset − rest)
```

**右边是残差，左边是拍面中心偏离瞄准点的量。** 所以这份残差可以直接和判定半轴
（横 0.20 / 竖 0.24）比较，不需要换算——`offCenter` 做不到这一点。

判据也写进去了：残差里有 `holdR` + `deadband` 是设计允许的静差，算「走位准不准」
要先减掉，否则会得出「走位一直偏 19cm」的错误结论。

### (4) 一处必须防的坑：`planOffset` 是每帧原地改的模块数组

`recordContact` 里先快照再 `learnContact`。顺序反过来，记到的就是「学完之后」的瞄准点，
残差凭空变小——**正好把要诊断的那个偏差自己抹掉**。

`buildContactSample` 里存的是 `cp()` 拷贝，一条测试专门钉住它。做了反向验证：把拷贝
改成存引用，测试**立刻变红**（156 通过 / 1 失败），改回来 158 全绿。这条如果不测，
文件会看起来完全正常，只是所有样本都显示最后一帧的瞄准点。

### (5) 旧数据怎么办

11-15 之前的样本没有这三个字段。`aimResidual()` 对缺 `planOffset` 的返回 `null`
而不是 0 —— 编一个 0 出来就等于说「这一拍瞄得完美」，比报错更有害。用
`data/contact/20261115-162137.jsonl`（26 条）实测：`aimResidual` 全部返回 `null`。

### (6) 验证

- `npm test`：**158 项**通过（新增 2 条：快照与分组、残差等于 `fc − p`）；
- `npm run duel-sim`：与改动前**逐字节一致**（只加字段，不碰判定）；
- `npm run build`、`tsc --noEmit`：通过；
- 旧文件 26 条实测不崩、缺字段返回 `null`。

**没验的**：真机。下次打球才能确认 `planOffset` 记的是「相遇前」而不是「学完后」——
具体看头几条的 `meta.planOffset` 是否还停在 `[0, 0.6, 0]` 附近，而不是第一球之后就跳到
`delta` 的量级。

## 4.31 2026-11-15 深夜 · 一次纯结构重构：模块边界、四元数、编译清单

## 4.32 2026-11-16 深夜 · 采集 schema 两处修正：`at` 挪进 meta、`driftDeg` 接上

起因是一次离线分析：拿两天 123 行真机样本（可用 111 条）问「能不能训校准器」。
结论是「能，但只有 4–5 个自由参数的线性模型能训」，而数据本身有三处会让人得出
错误结论。这一轮修掉其中两处纯代码的；第三处（跨天系数不稳）没法靠代码解决——
`rest.y → delta.y` 的系数在两天里是 **−1.30 与 +0.11**、符号相反，只能靠「留一天
不训、只拿它测」来判断，而那需要至少 3 天数据。

### (1) `at` 从 `feat` 挪进 `meta`：它和 `G` 相关 0.994

`feat.at` 记的是球的世界坐标，注释写的是「来球位置」——听起来是纯外部条件。实测：

| 量 | 值 |
|---|---|
| `feat.at.x` 与 `label.G.x` 的相关系数 | **0.994** |
| `|at − G|` 均值 / 中位 / 最大 | 0.565 / 0.571 / 0.888 m |
| 含 `at` 的留一 CV（z 轴 RMSE） | 0.102 |
| 不含 `at` 的留一 CV（z 轴 RMSE） | 0.117 |

球是打到身边才打得到的，所以球的位置几乎就是站位——把 `G` 换个名字又塞回了 X。
多出来那 13% 不是物理规律，是模型在拟合「上一版校准器的 `planOffset` 留下的系统性
痕迹」：一改校准器，`at` 的含义就跟着变。这正是 `core/contact-log.ts` 文件头禁止的
闭环自激。

做法：字段挪进 `meta`（漏接几何和 `offCenter` 的来龙去脉还要靠它还原，不能删），
新增 `FEATURE_KEYS` 白名单，配一条逐字对表的测试。**没有**改成 `at − G`：它同样
含 `G`，救不回来。真要「球在哪」这个信息，只能用相遇前就能拿到的东西（球机目标点、
弹道预测点），那是另一次特征工程。

### (2) `driftDeg` 终于有值了：手机 1Hz 上报，走 ctrl

`recorder.ts` 里那一行 `private readonly driftDeg: number | null = null` 从加这个
字段起就没接过线，而 README 承诺的「超阈值的整段丢弃」全指望它。于是 111 条样本
没有一条知道当时漂了多少度，被漂移污染的样本剔不掉。

- 协议：`CtrlMsg` 加 `{ t: 'drift', deg, comp }`。**不塞进定长包**——那要改
  `PACKET_BYTES` 再加一个兼容分支，而漂移是每秒变零点几度的慢变量，1Hz 的 JSON
  足够，代价只是几条 40 字节的控制报文。
- 语义：`deg` 随 `comp` 变。补偿关是「此刻姿态相对基准歪了多少」，补偿开是「已经
  替你扣掉了多少」。同一个数两种含义，所以样本里成对记 `driftDeg` / `driftComp`，
  混在一起算平均会得出没有意义的结论。
- 顺带修掉一处语义不一致：`recal`（按 `R`）在**补偿关**的分支原先不 `drift.reset()`，
  观测会跨重标定一直累加。后果有两个——读数不再是「相对当前基准」的偏差；以及
  之后中途打开补偿时，`yawZero += drift.radians` 会把重标定之前那段再扣一遍，而
  那部分已经被重锁抵消了。现在两条分支都清。**这条只影响「关 → 开」那一刻的数值，
  补偿关时的姿态输出逐帧不变。**
- 换段（`nextSession`）把握点置 `null` 而不是 0：新一段第一条报文到之前，手里那个
  数是上一段的累计值。

### (3) 验证与**没验的**

- `npm test`：**160 项通过**（原 158 + 新增 2 条：`feat` 白名单逐字对表、
  `driftDeg`/`driftComp` 成对记录）；
- `npm run build`（`tsc --noEmit` + `vite build`）：通过，`play-*.js` 仍 764 kB；
- 离线复核：把新 schema 的样本重新算了一遍分布，`delta` 各轴均值/方差与改前一致
  （只挪了字段位置，没动标签定义）。

**没验的**：浏览器与真机。1Hz 报文要等真机确认——打开页面打一球，`meta.driftDeg`
不应再是 `null`；手机不点「漂移」按钮时也该显示数字（补偿关时它是「歪了多少」）。
另外 `recal` 那条改动影响的是「关 → 开」切换，真机上应该看到：反手位按 `R` 回正后
再打开补偿，拍子不该再歪一下反弹。

## 4.33 2026-11-16 深夜 · 复核：两天的系数差异是 6σ，不是「n 太小」

4.32 留了个悬案：`rest.y → delta.y` 的系数在两天里是 −1.30 与 +0.11，当时说「可能是
握法不同，也可能只是第一天 n=21 的噪声，现有数据分不开」。补算标准误之后可以分开了。

| 批次 | n | `rest.y → delta.y` | `r(lag, delta.y)` | R²(y) |
|---|---|---|---|---|
| 11-15 16:21（s3–s4） | 21 | **−1.30 ± 0.17** | −0.13 | 0.83 |
| 11-16 22:14（s1–s5） | 90 | **−0.13 ± 0.09** | **−0.62** | 0.52 |

差值 1.17，合成标准误 0.19，约 **6σ**。样本内误差也不独立（同一段里拍与拍相关），
按 2 倍膨胀算仍有 3σ。两个可能的混淆项都排掉了：

- **共线性**：两天的 `rest` 分量相关几乎一样（`r(rest.x, rest.y)` = −0.47 / −0.45，
  `r(rest.y, rest.z)` = −0.10 / −0.30），不是某天矩阵病态导致系数虚高；
- **代码版本**：11-15 那批是 40c7101（23:24）之前采的，但那个提交只是把 `app.ts`
  里的 8 个模块级变量搬进 `PlayerRig`，`learnContact` 的公式（`k=0.45`、单轴 ±0.55
  夹）一字未改，标签定义也没动。

所以两天是**两个映射**：11-15 的 `delta.y` 主要由握法解释，11-16 主要由 `lag` 解释。

1. **别把两天并成一个训练集。** pooled 的 `rest.y` 系数 −0.32，对哪一天都不对
   （11-15 需要 −1.3，11-16 需要 −0.1），合并等于两边都欠拟合。
2. **固定模型跨天不成立**——这正是现行「每段 EMA 在线学」的设计依据，不是妥协。
   真要训，训的应该是**先验**（EMA 的初值 / 正则目标），不是固定预测器。
3. 11-15 那 21 条**不要删**：它是唯一的第二个「天」，是「换一天还行不行」这个

离线脚本加了 `--v1` 开关（默认仍只吃 schema v2）：`python .tmp-analyze-contact.py --v1`

## 4.34 2026-11-17 凌晨 · 漂移门限按角速度重做（旧门限等于 58–72°/s）

起因是 11-16 那批 248 条样本（`20261116-232136.jsonl`）的一个反常读数：`driftDeg`
中位 **90.5°**、p90 331°、max 674°，而**命中率在漂移分桶上完全平坦**——[0,10) 100%、
[10,30) 79%、[30,60) 81%、[60,120) 79%、>120° 77%，和 `offCenter` 的相关只有 −0.10。
姿态真歪掉 90° 是不可能还保持 79% 命中的，说明这个数不是「歪了多少」。

### 根因：阈值绑在了采样率上

```ts
const MAX_DRIFT_STEP = 0.05; // rad ≈ 2.9°/帧
```

注释写的是「真机慢漂约 1–2°/s，30–60Hz 采样下每帧不到 0.1°」——按**速率**算是对的，
但代码判的是**每帧角度**。方向事件实际是 20–25Hz，`0.05 rad/帧` 等于 **58–72°/s**：
只有挥拍（100–1700°/s）挡得住，抬手、转身、换握、走位调整全被积进「漂移」。
这是 4.13 那套判据的形态问题，不是数值没调好——同一个物理转动在 20Hz 和 60Hz 下
每帧角度差三倍，按帧判等于让阈值随设备/浏览器变。

数据侧的三个佐证：

| 检验 | 结果 |
|---|---|
| 样本间变化速率 | 中位 **12.7°/s**（陀螺零偏是 0.1–1°/s，差一到两个数量级） |
| 会话内同向变化占比 | 0.35（来回摆，不是单向爬升 → 跟着人的动作走） |
| 35 分钟补偿全关、基准只锁一次 | 命中率前半 80% / 后半 79%，**没有退化** |

### 改法

1. **按角速度判**。`update(abs, dtMs)` 的 `dt` 改成**必填**（漏传就是编译错——这个
   bug 的形态正是「按帧判」，不给默认值就是在结构上防复发）。门限 `MAX_DRIFT_RATE =
   0.1 rad/s`（5.7°/s）：真机慢漂 1–2°/s 要过，有意转手机 / 走位 ≥10°/s 要挡；
   手抖落在 2–5°/s 会过门，但符号来回变、长时间求和不增，顶不起读数。
   非 Y 轴分量的纯度判据一起改成速率（`MAX_DRIFT_OFF_RATE = 0.2 rad/s`）。
2. **断档帧不积分**：`dt > 250ms` 当作中间没采到（切后台 / 锁屏回来），那一帧的角差
   跨了未知运动，算速率没有意义。另设 4ms 下限，避免除以接近 0 的 dt。
3. **重置后立刻补报**。手机端把上报抽成 `reportDrift()`，在「按 R 重置后 / 切补偿后 /
   重连 `state=connected`」都立刻发一次，不再等 1Hz tick。大屏换段时会把本地读数置空，
   等 tick 就有最多 1 秒空窗，而那正好落在新一段的头几拍上——偏偏是这几拍最需要读数。
4. **重连不清零观测**，这是刻意的：`yawZero` 在重连时不重锁（重锁就是 4.13 否掉的
   「按当前姿态重新定义正前方」），所以 `acc` 相对基准是连续的。清掉它等于谎报 0。

### 验证与**没验的**

- `npm test`：**163 项通过**。新增 3 条直指这次的根因——30°/s 的有意转动在 20Hz 与
  60Hz 下都不该积分、同一物理慢漂在两种采样率下积出同样的角度、断档那一帧不积分；
  另有 4 条老用例（慢漂积分 / 纯度 / 扣进 yawZero / reset）从「0.4°/帧」改成带 `dt`
  的真实速率，否则它们编码的就是错的门限。
- `npm run build`：通过，`play-*.js` 764 kB 未变。
- **没验的是真机**。本次改动只在判据层，效果必须在手机上确认：
  1. 手机**放桌上静止 60s**，读数应 < 5°（旧门限下会走到几百度）；
  2. 拿在手里走两步、转个身，读数应基本不动（旧门限下会跟着跳）；
  3. 正常挥拍时读数不该出现阶跃（`skippedSteps` 会涨，`acc` 不该动）。
- **11-16 那 248 条样本的 `driftDeg` 全部作废**：它们是旧门限算出来的，既不能拿来
  验证新判据，也不能当剔除依据。其余字段（`delta` / `feat` / `planOffset`）不受影响。

## 4.35 2026-11-17 凌晨 · 漂移补偿改成 ZUPT：棘轮才是「往反手漂」的元凶

真机反馈：「打着打着球拍角度就会漂，而且总是往反手方向」。这一轮先查了「是谁在累积」，
找到的不是传感器噪声，而是 **4.34 那套判据自带的棘轮**。

### (1) 补偿关时，屏幕上的 yaw 就是手机 alpha 的变化量

`main.ts` 里只有两处会动朝向：`yawZero`（启动 / 按 `R` 时锁一次）和
`effZero = yawZero + (driftOn ? drift.radians : 0)`。补偿关时第二项恒为 0，输出是
`Ry(-yawZero) · abs` —— 左乘一个世界 Y 旋转只等于把 yaw 平移一个常数。实测
`d(yaw)/d(alpha) = 1.00`（各握位都是），所以**拍子转多少，就是手机 alpha 走了多少**。
大屏那侧 `smoothQ` 是向 `targetQ` 做的 slerp、姿态连续性门只拦单帧跳变，两者都不累积。

### (2) 补偿开时：慢回位被当成漂移吃掉（棘轮）

门限对真实动作是**双向**的：一拍快挥出去 40°（500°/s，被判据拒掉），然后四秒慢慢
回位（4°/s，低于 5.7°/s 门限，被当成漂移**积进去并扣掉**）。用两个实现跑同五个来回
（`.tmp-drift-ratchet.cjs --slow`，打印的是累计补偿量，与屏幕 yaw 反号）：

```
旧（4.34）：-40 → -80 → -120 → -160 → -200     每拍往里走 40°，永不回头
新（4.35）：  0 →   0 →    0 →    0 →    0     陀螺说在动，一帧都不进估计
```

每拍往里走一截、永不回头。**方向就是「你回来的那一侧」**——正手随挥收在身体左侧，
所以表现为往反手漂。这条和传感器漂不漂无关，是判据把真实动作当成了噪声。

### (3) 为什么「总是同一边」

- **零偏在竖直轴上的投影符号固定**：yaw 没有绝对参考（室内钢结构、音箱、手机壳磁铁
  会让磁力计被降权甚至不用），alpha 退化成陀螺积分，残差零偏 0.1–2°/s、符号由硬件
  决定，一分钟就是几度到几十度；
- **手腕旋前被握位放大**：同样 roll 1°，水平投影在 β=±20° 附近能放大到 **2.9 倍**
  （`.tmp-yaw-geometry.cjs` 的实测表），而人的旋前是单向的；
- **(2) 的棘轮**，方向恒为回位侧。

### (4) 为什么数据里没看见

11-16 那 34 分钟 224 条可用样本：拍面水平朝向均值 2°、sd 26°，逐段均值在 −19°…+41°
之间晃但无单调趋势；命中率前半 80% / 后半 79%。原因是**换段太密**（31 段、每段平均
7 拍），每次换段都重锁姿态基准，样本里最多只有 1 分钟的累积量，淹没在 ±26° 的挥拍
散布里。旧 `driftDeg` 中位 90.5° 是另一回事（那是「慢转角」被乱吃的结果，4.34 已说明）。

### (5) 改法：ZUPT（静止测零偏，运动外推）

`core/attitude.ts` 的 `YawDriftObserver` 推倒重写：

| | 旧（4.34） | 新（4.35） |
|---|---|---|
| 静止判据 | alpha 自己的变化率 < 5.7°/s | **陀螺 `\|gyro\| < 0.04 rad/s`（≈2.3°/s）** |
| 静止帧 | `acc += dy`（判据过了就积） | `acc += dy`（实测），顺手喂零偏 |
| 运动帧 | 不动 | `acc += bias * dt`（零偏外推） |
| 零偏 | 无 | 连续静止 ≥1.2s 才认第一次，之后按窗口长度加权细调 |
| 棘轮 | **会**（慢回位被吃） | **结构上不可能**：真实动作一帧都进不了估计 |

几个刻意的选择：

- **`update(abs, dtMs, gyroRate)` 三个参数都必填**。漏传 `gyroRate`（undefined）会
  走 `Number.isFinite` 为假的分支 → 一律按运动处理，即「不补偿」而不是「乱补」；
- **陀螺断线时传 `NaN`**（`gyroSource === 'none'`）。`currentGyro()` 在两条通道都断
  时返回 `[0,0,0]`，和「真的静止」长得一模一样——不显式区分就会把真实动作吃成漂移；
- **第一次零偏要 1.2s 的窗口**（`BIAS_TRUST_MS`），之后 400ms 就能细调。0.4s 窗口的
  端点噪声约 0.2°/s，拿去外推十分钟能积出上百度；
- `MAX_BIAS_RATE = 0.1 rad/s`（5.7°/s）夹住零偏量级，宁可少补也不能让它跑飞；
- **`advancePose` 只在新的一帧绝对姿态上推进观测器**（`abs !== lastDriftAbs`，对象身份
  比较）。它会同时被 60Hz 发包循环叫到，而方向事件只有 20–35Hz——同一帧重复喂进去，
  等于用「50ms 的变化 ÷ 16.7ms 的 dt」算速率，放大三倍：静止帧被误判成运动、静止窗口
  一直被打断，零偏永远到不了 1.2s。**漂得越快越先坏**，正好坏在最需要补偿的机器上。
- **重连 / 按 `R` / 切补偿开关只调 `resetAngle()`，保留零偏**：`yawZero` 已经把已经
  扣掉的量吸收了，累加要从 0 起；但零偏是陀螺的物理属性，和「正前方指哪」无关，
  丢了就得重新站 1.2s。只有新会话（`begin()`）才 `reset()` 连零偏一起清。

  **棘轮回归**（快挥 40° + 4°/s 慢回位 10s，只许涨零偏外推的 15°）、慢速真实转动

  其中「慢漂被积分」那条拆成了「静止学零偏 / 运动按零偏外推」两段。
- `npm run build`：通过，`play-*.js` 仍 764 kB；`duel-sim` 通过。

### (7) 没验的，以及它改变了什么

- **真机一条都没验**。改后的验收标准也换了（旧的那条「放桌上 60s 读数应 < 5°」按新
  语义是**错的**——桌上真漂 90° 时读数就该是 90°）：
  1. 手机放桌上 60s，屏幕上**球拍不该转**（读数会涨，那是在补偿）；
  2. HUD 上「漂移 +xx.x° y.y°/s」的第二个数应在静止几秒后出现，量级 0.0x–1°/s；
  3. 打十分钟，拍子的中线不该慢慢偏；按 `R` 之后读数归零、显示「待静止」；
  4. 卡顿 / 切后台回来不该出现 `NaN`、控制台无报错。
- **`driftDeg` 的语义变了**：从「累计的慢转角」变成「已经替你扣掉多少」，随时长单调
  增长。所以**任何 `|driftDeg| > X` 的剔除阈值都要作废**（包括之前的 20°）。看手机
  HUD 上的零偏（°/s）才是有意义的判断。`data/contact/README.md` 与分析脚本已同步。
- 仿真里「前 30s 没标定就开打」那 15° 说明：**开局要先站定 1–2 秒**，HUD 显示
  「待静止」时补偿还没生效。这不是缺陷，是「不知道就不猜」的代价。
