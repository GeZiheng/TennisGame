# 已知问题与设计脆弱点

> 原为 `AGENTS.md` 第 7 节，2026-11-09 拆分独立成篇。这些是**已知的、故意没改的**——不要误以为是新 bug。
>
> 例外：7.1 记录的是已解决症状的来龙去脉，以及重连场景下另一个根因的复现；当前待复验项见 `AGENTS.md` 第 0.3 / 0.4 节。

## 7.1 穿模症状（首次连接已解决，重连场景另案）

真机症状曾是「挥拍时球从拍面穿过」，2026-11-10 真机确认**首次连接**已消失。当时的缓解是「球追拍面」，但那套非物理跟随也已在同一天撤销（见 `docs/history.md` 4.10）。

11-10 晚复验发现**重新扫码接入后**该症状会再次出现，当时归为大屏跨连接残留的时钟偏移与包序号把挥拍事件挡在 ±150ms 窗口外（见 `docs/history.md` 4.12），已修复且本轮真机确认重连后能打到球。

**但「打不到球」的主因后来确证是第三层：位姿慢漂**。`R` 只重锁 `yawZero`、完全不碰时钟与包序号就能恢复命中，说明这条路径上「球从拍面穿过」是 alpha 慢漂让拍面法线绕竖直轴侧过去、`sweepFace` 盘形判定判空（见 `docs/history.md` 4.13）。11-11 又补到第四层：**挥拍速度一快就打不到、打一会儿拍子疯狂抖**，根因是姿态跳变门限把真实快挥拍踢进陀螺外推（见 `docs/history.md` 4.14），与慢漂、时钟都无关。排查「打不到」时按四条分开：**首次连接 / 运行中慢漂 / 快挥拍 / 重连**，不要再把主因归回判定几何或时钟。

## 7.3 设计上仍然脆弱的地方

1. **去掉跟随后，大角度挥拍会够不着**。拍面中心挂在 0.6m 杆末端，转 30° 就平移 0.31m，判定半轴只有 0.20m；落地重瞄横向只有 1.6 m/s（约 20cm）。这是刻意保留的物理代价，不是 bug。若真机上正常幅度的挥拍也频繁漏接，先看 `probe-swing.cjs` 与挥拍时机，别急着把跟随加回来。
2. **击球高度依赖姿态**。`serve` 用来球高度 = `clamp(faceCenter.y, 0.8, 1.9)`，玩家把手机举高/放低，来球高度会跟着变（握点 1.3m 时：横握 1.3m、竖握 1.9m —— 上限正好压在竖直握法上，再举高就不再跟着涨）。锚定方案取消后，这块又回到「跟着姿态走」。
3. **`liftOverNet` 的 `probe` 很贵**（一次回球 ~33 条候选 × 每条最多 1600 步）。目前只在击球时算一次，可以接受；如果以后要加「落点预览」之类的实时功能，需要缓存或降采样。
4. **`RacketTrack.at()` 是线性扫描**（最多 24 个元素）。当前 240Hz × 400ms 完全够用，不是瓶颈。
5. **`docs/motion-accuracy.md` 的握持标定还没做**。这是零成本、收益最大的一项：静止持拍取平均法线，与期望方向比对求安装角，出球时反向旋转补偿。若出现「球总往一边偏」，先看 HUD 的「拍面」读数。
6. **姿态门控曾把真实快挥拍误判成跳变（11-11 确证，代码层已修、真机待验）**。`MAX_POSE_JUMP=1.2 rad` 是按 25–35Hz / 20 rad/s 估的，但方向事件 20–25Hz + 20–35 rad/s 时相邻帧就有 1.0–1.75 rad；比较基准又冻结在跳变前，整段挥拍被踢进削顶的陀螺外推。真机表现就是「挥拍一快就打不到」+「打一会儿拍子疯狂抖」（每拍来回切一次姿态源）。已重构为 `PoseContinuityGate`：相邻帧差 + `moving` 判据 + 基准每帧更新，见 `docs/history.md` 4.14；`scripts/probe-pose.cjs` 量化了修复前后。**判据层已验证，浏览器与真机效果未验证**。
7. **（已关闭）视觉走位完全没真机验证 → 11-13 整条删除**。摄像头追色块那条通道（`?vision=1`）从上线起就没有真机跑通过：色相阈值、镜像方向、挥拍时躯干色块的波动都不是纯函数单测能覆盖的，`npm run verify` 全绿不代表可用。11-13 按用户要求整条删掉（`docs/history.md` 4.21），编号保留是为了不打破下面第 9 条对「第 8 条」的引用。

8. **绝对姿态的 yaw 没有持续锚定（11-10 深夜已确证，补偿已实现、真机待验）**。`yawZero` 只在启动 / `recal` 时锁一次，`deviceorientation` 的 alpha 缓慢漂移（室内磁场 / 系统融合重收敛）会让球拍绕竖直轴慢慢转；`toOutputQuat = Ry(-yawZero)·absolute`，alpha 漂 Δ 就是整体绕世界 Y 多转 Δ。真机读数「姿态 = 绝对姿态」排除了方向事件中断与外推累积，偏差渐增 + 按 `R` 回正后重新累积（约 30–60s 歪到打不到）确证了这一条。11-10 深夜已加 `YawDriftObserver` 按帧间转角幅度扣掉慢变分量，**默认关**，见 `docs/history.md` 4.13；门禁只覆盖纯计算，浏览器接入与真机效果未验证。

9. **欧拉角换解分支的中间地带没被门限覆盖**。`MAX_POSE_JUMP` 只拦 > 1.2 rad 的单帧跳变，但万向锁附近换解分支也可能只有 0.5–1 rad：这种幅度会被当成真实旋转采信，当时的 `lastGoodAbs` 随即写进新分支并固化，表现就是「某一拍之后突然差一个固定角度」。正常挥拍相邻帧可达 0.8 rad，所以**不能靠调小门限解决**，要做解分支识别。与第 8 条的判别方式互斥，见 `AGENTS.md` 0.4。「渐增而非突跳」的读数已把它从主因降级为次要候选；4.14 重构后基准每帧更新、跳变只拦一帧，这层的保护强度进一步降低（换取不再误伤快挥拍），HUD 的「万向锁」标记若在某个握位亮起，仍指向这一条。

10. **自动走位的第三维（握点升降）完全没真机验证**（11-13 加）。`speedY = 9 m/s`、`minGripY / maxGripY = 0.70 / 1.65`、`minZ = HIT_Z - 3.0` 三个数都是按几何和「比跑动快但不瞬移」拍的：自动屈膝/举拍可能让人晕（画面里人自己在上下起伏），网前 3m 的前迎可能过头（感觉「人一直往网里冲」）。门禁只证明它能打进球（L1 三握法 37–39/39、墙打三握法 100%），**证不了体感**。若真机觉得晃，先降 `speedY`；觉得冲，先收 `minZ` 到 `HIT_Z - 2.0`，两处都在 `AUTO_MOVE_DEFAULTS`，`docs/tuning.md` 5.5 有每条的取舍。

## 7.4 没有做的事

- 没有角色/手部渲染（只有球拍），所以「拍面中心被甩走」在视觉上没有参照物，只能靠球的位置判断。
- 没有真机自动化测试。所有真机结论都来自现场观察 + HUD 读数。
- 没有回放/录像功能。排查「刚才那一拍为什么没打到」只能靠 HUD 的六个瞬时值。
