# 已知问题与设计脆弱点

> 原为 `AGENTS.md` 第 7 节，2026-11-09 拆分独立成篇。这些是**已知的、故意没改的**——不要误以为是新 bug。
>
> 例外：7.1 记录的是已解决症状的来龙去脉，以及重连场景下另一个根因的复现；当前待复验项见 `AGENTS.md` 第 0.3 / 0.4 节。

## 7.1 穿模症状（首次连接已解决，重连场景另案）

真机症状曾是「挥拍时球从拍面穿过」，2026-11-10 真机确认**首次连接**已消失。当时的缓解是「球追拍面」，但那套非物理跟随也已在同一天撤销（见 `docs/history.md` 4.10）。

11-10 晚复验发现**重新扫码接入后**该症状会再次出现，当时归为大屏跨连接残留的时钟偏移与包序号把挥拍事件挡在 ±150ms 窗口外（见 `docs/history.md` 4.12），已修复且本轮真机确认重连后能打到球。

**但「打不到球」的主因后来确证是第三层：位姿慢漂**。`R` 只重锁 `yawZero`、完全不碰时钟与包序号就能恢复命中，说明这条路径上「球从拍面穿过」是 alpha 慢漂让拍面法线绕竖直轴侧过去、`sweepFace` 盘形判定判空（见 `docs/history.md` 4.13）。11-11 又补到第四层：**挥拍速度一快就打不到、打一会儿拍子疯狂抖**，根因是姿态跳变门限把真实快挥拍踢进陀螺外推（见 `docs/history.md` 4.14），与慢漂、时钟都无关。排查「打不到」时按四条分开：**首次连接 / 运行中慢漂 / 快挥拍 / 重连**，不要再把主因归回判定几何或时钟。

## 7.3 设计上仍然脆弱的地方

1. **去掉跟随后，大角度挥拍会够不着**。拍面中心挂在 0.6m 杆末端，转 30° 就平移 0.31m，判定半轴只有 0.20m。这是刻意保留的物理代价（11-10 撤销「球追拍面」时就定了），不是 bug。`node scripts/probe-contact.cjs` 量这段缺口：斜握 0.128m / 横握 0.303m / 竖握 0.406m（`MODE=contact` 学到位后降到 0.048 / 0.192 / 0.278）。若真机上正常幅度的挥拍也频繁漏接，先看探针读数和挥拍时机，**别急着把跟随加回来**——那是追踪弹。
2. **来球高度不再跟着你的拍面走（11-15 起）**。墙打时代喂球会瞄你此刻的拍面中心（`clamp(faceCenter.y, 0.8, 1.9)`），所以「举高手机 → 来球变高」。现在喂球的是回球机，它瞄固定高度带 1.3–1.6m，**不看你怎么持拍**。对你更公平（不会因为换个握法就接不到），但换来一条：竖握时拍面中心在 1.9m，来球在 1.3–1.6m，差的那 0.3m 得靠自动走位的握点升降去补（`docs/duel.md` 5.1）。
3. **`aimIntoCourt` 是搜索，不是公式**（猜速度 → 跑真实物理 → 修正，每次几十到上百次 `advance`）。回球机每次出球要试一整条候选落点阶梯，最坏情况是「几档全解不出来」。现在只在击球那一帧算一次，可以接受；如果以后要加「落点预览」之类的实时功能，需要缓存或降采样。
4. **`RacketTrack.at()` 是线性扫描**（最多 24 个元素）。当前 240Hz × 400ms 完全够用，不是瓶颈。
5. **`docs/motion-accuracy.md` 的握持标定还没做**。这是零成本、收益最大的一项：静止持拍取平均法线，与期望方向比对求安装角，出球时反向旋转补偿。若出现「球总往一边偏」，先看 HUD 的「拍面」读数。
6. **姿态门控曾把真实快挥拍误判成跳变（11-11 确证，代码层已修、真机待验）**。`MAX_POSE_JUMP=1.2 rad` 是按 25–35Hz / 20 rad/s 估的，但方向事件 20–25Hz + 20–35 rad/s 时相邻帧就有 1.0–1.75 rad；比较基准又冻结在跳变前，整段挥拍被踢进削顶的陀螺外推。真机表现就是「挥拍一快就打不到」+「打一会儿拍子疯狂抖」（每拍来回切一次姿态源）。已重构为 `PoseContinuityGate`：相邻帧差 + `moving` 判据 + 基准每帧更新，见 `docs/history.md` 4.14；`scripts/probe-pose.cjs` 量化了修复前后。**判据层已验证，浏览器与真机效果未验证**。
7. **（已关闭）视觉走位完全没真机验证 → 11-13 整条删除**。摄像头追色块那条通道（`?vision=1`）从上线起就没有真机跑通过：色相阈值、镜像方向、挥拍时躯干色块的波动都不是纯函数单测能覆盖的，`npm run verify` 全绿不代表可用。11-13 按用户要求整条删掉（`docs/history.md` 4.21），编号保留是为了不打破下面第 10 条对「第 8 条」的引用。

8. **绝对姿态的 yaw 没有持续锚定（11-10 深夜已确证，补偿已实现、真机待验）**。`yawZero` 只在启动 / `recal` 时锁一次，`deviceorientation` 的 alpha 缓慢漂移（室内磁场 / 系统融合重收敛）会让球拍绕竖直轴慢慢转；`toOutputQuat = Ry(-yawZero)·absolute`，alpha 漂 Δ 就是整体绕世界 Y 多转 Δ。真机读数「姿态 = 绝对姿态」排除了方向事件中断与外推累积，偏差渐增 + 按 `R` 回正后重新累积（约 30–60s 歪到打不到）确证了这一条。11-10 深夜已加 `YawDriftObserver` 按帧间转角幅度扣掉慢变分量，**默认关**，见 `docs/history.md` 4.13；门禁只覆盖纯计算，浏览器接入与真机效果未验证。

9. **挥拍枢轴的位移是真机上的未知数（11-14 新增）**。`core/swing-rig.ts` 会把握点在挥拍时
搬走最多 0.18m（绕腰/肘走弧），而「走位瞄的是挥拍前那个拍面中心」这件事没变。模拟器 A/B 里命中率
没变（`duel-sim` 里开关枢轴的命中率差在噪声内），但模拟器的挥拍是脚本化的正弦，真人的挥拍时机和
幅度散布大得多。如果真机上出现「枢轴开着更容易打空」，先按 `G` 关掉确认，再考虑把
`maxShift` 往下调（`docs/tuning.md` 5.6），不要去动判定半轴。

10. **欧拉角换解分支的中间地带没被门限覆盖**。`MAX_POSE_JUMP` 只拦 > 1.2 rad 的单帧跳变，但万向锁附近换解分支也可能只有 0.5–1 rad：这种幅度会被当成真实旋转采信，当时的 `lastGoodAbs` 随即写进新分支并固化，表现就是「某一拍之后突然差一个固定角度」。正常挥拍相邻帧可达 0.8 rad，所以**不能靠调小门限解决**，要做解分支识别。与第 8 条的判别方式互斥，见 `AGENTS.md` 0.4。「渐增而非突跳」的读数已把它从主因降级为次要候选；4.14 重构后基准每帧更新、跳变只拦一帧，这层的保护强度进一步降低（换取不再误伤快挥拍），HUD 的「万向锁」标记若在某个握位亮起，仍指向这一条。

10. **自动走位的第三维（握点升降）完全没真机验证**（11-13 加）。`speedY = 9 m/s`、`minGripY / maxGripY = 0.70 / 1.65`、`minZ = NET_Z + 4.0`（11-15 从 `HIT_Z - 3.0` 放到网前 4m）三个数都是按几何和「比跑动快但不瞬移」拍的：自动屈膝/举拍可能让人晕（画面里人自己在上下起伏），网前 3m 的前迎可能过头（感觉「人一直往网里冲」）。门禁只证明它能打进球（`npm run duel-sim` 的 L1/L2 回合数），**证不了体感**。若真机觉得晃，先降 `speedY`；觉得冲，先把 `minZ` 往回收（`NET_Z + 5.0` 起试），两处都在 `AUTO_MOVE_DEFAULTS`，`docs/tuning.md` 5.5 有每条的取舍。

11. **`contactDelta` 把正手和反手混成了一份（11-14 新增）**。偏移是按「命中那一刻的拍面姿态
减站着不动的姿态」学出来的，一次一个值；正手从右侧挥、反手从左侧挥，两者的 x 分量本来就
反号。玩家轮着用两边时，EMA 会收敛到中间那个「两边都不太对」的值。目前的赌注是：这套玩法
（手机当球拍、一个人对着回球机）绝大多数时候只用一边。若真机出现「一边准一边差」，下一步应该
按命中点的 x 正负分成两份（`hit.at[0]` 就在事件里），再各自 EMA。

12. **高度两段的三个数全是拍的（11-14 新增）**。`speedY=6`、`speedYSlow=1.8`、`heightBand=0.20`、
`heightLead=0.45` 没有一个来自真机：前两个是「一帧 10cm 有点跳 / 20cm 走 110ms 看得见」，
后两个直接来自用户那句「上下 20cm 左右」。门禁只证明「球到面时高度对得上」
（`npm run duel-sim` 的回合数与 `probe-contact` 的命中率），证不了「看起来像人在调整」。觉得像木偶就降 `heightBand`，
觉得球到面还在半路就加 `heightLead`（`docs/tuning.md` 5.5）。

13. **发球的几个数全是拍的（11-14 新增，11-15 重估过一轮）**。`TOSS_Y0=2.05`、`TOSS_VY=5.2`、
`SERVE_REACH=0.42`、`SERVE_ANCHOR_R=0.35`、`YAW_GAIN=0.65`，以及俯角映射的两端 3°/18°，
没有一个来自真机（11-15 那次只是被真机反馈「太低、发不进区」推着改了一版）：
   - 抛球高度和初速是按「顶点 3.43m、在举高的拍面上方 1.2m、出手到可击球 0.95 秒」算的，
     **「等 0.95 秒再挥」这个节奏感仍然没人验证过**——比原来长了一倍，可能显得慢；
   - `SERVE_REACH` 从 0.34 加到 0.42 是为了把可击球窗口从 0.2 秒拉到 0.4 秒，
     **发球该比接杀宽容多少，只有手能回答**；
   - 俯角只用了 15° 的行程映射进区，是为了绕开「合法窗口只有 3.6°」那条几何。
     如果真机觉得「怎么压都打不出短球」，先看这个映射，别去动 `serveBox`。

   回调顺序：手感不对时**先调 `TOSS_VY` 和俯角映射**（体感问题），`SERVE_REACH` 最后动
   ——它是判定半径，动它会把「挥到了没挥到」的边界一起挪掉。

14. **机器会发一种偏高偏慢的球（11-14 新增）**。为了让发球「接得到」，`Duel.solveServe`
   把竖直初速固定在 5.0–6.0 m/s，顶点约 4.2m，看起来像月亮球。这不是调参没调好：
   发球区到接发方击球面还要再飞 4.8–10.8 米，平飞过去的球在那之前就二次落地了
   （见 `docs/duel.md` 4.5）。**想让它发得更冲，先得让玩家能在更低的拍面高度接球**
   ——那要改的是判定盘和握点行程，不是这一条。

15. **两边发球局的难度不对称（11-14 新增）**。玩家发球是手动挥拍（打不进区就是失误），
   机器发球是一条被筛过的、保证接得到的弹道。`npm run duel-sim` 只保证「有球可打」，
   **没有测「两边发球局的胜率是不是平衡」**。真机上如果出现「一直在破发」或
   「谁也破不了发」，那是这个不对称，不是难度参数。

16. **发球的击球区是「握点锚点」，不是真拍面（11-15 新增）**。`serveStrike` 把拍面中心
   朝锚点收进 0.35m 以内，所以横握/斜握时**球可能从看得见的拍边外面飞出去却算命中**
   （最坏偏 0.6m）。这是「抛球点必须与握法无关」的代价，也是真机「打不到」的直接解药。
   判断方法：竖握（拍面中心本来就贴着锚点，偏移 0.07m）时视觉应该是对的；如果竖握也
   觉得球跑偏，先查 `SERVE_STRIKE_UP/FWD`，别去缩 `SERVE_ANCHOR_R`——缩了就回到打不着。

17. **发球左右是「压灵敏度」，不是严格几何（11-15 新增）**。`YAW_GAIN=0.65` 让合法窗口
   从 15.6° 变成 23°，代价是「拍面指向哪儿」和「球落在哪儿」不再一一对应（差 35%）。
   地面那圈红绿是唯一反馈，必须跟上手。若真机觉得「怎么偏都能进」，把 `YAW_GAIN` 往
   1.0 调；觉得「压不住」，往 0.55 调。**不要动 `serveBox`**——那是规则，不是手感。

18. **「拍面没打开」现在只由「拍框侧着」触发（11-15 新增）**。反手修好之后，
   `alignment` 不再有负值，`clean=false` 只剩「拍面与球场夹角 < 9°」。挥拍中段姿态必然
   经过这个角度，如果正好落在击球那一帧，会读到 `clean=false`——音效变闷、提示变
   「拍面没打开」，**球速和方向不受影响**（`shotFromStroke` 的 7:3 混合仍然照算）。
   真机上如果这条提示出现得莫名其妙，先看 HUD 的「拍面」读数是不是「朝上/朝下」。

19. **站位范围放宽之后的体感没验（11-15 新增）**。`maxX=5.6`（边线外 1.5m）与
   `minZ=NET_Z+4.0`（网前 4m）是按「真实球员会跑出去」和「再往前就是冲网」定的，但
   **跑出边线时相机会跟着走，视野里球网会偏**，这一点没人看过。觉得晕先把 `maxX` 收
   到 4.6；觉得边线球还是够不到，说明问题在跑速（`speed`）而不是范围。
20. **「保持阈值 > 采样步长」是一条隐式约束，代码里只能靠注释守（11-15 新增）**。
   `holdR` 现在写成 `CROSS_STEP * 1.4`，但只要有人单独调 `sampleCrossings` 的步长
   （或者给 `planAutoMove` 传自定义 `step`），两者就会重新脱钩，症状是「横握抖动」
   复发、单测不会红（除非把「相邻一格不许翻」那条也算上——它用的是同一份默认值）。
   真正的解法是让 `TargetHold` 从 plan 里读「这一帧的候选间距」，而不是吃常量；
   但 plan 现在不带这个信息，为一个 4cm 的余量加一个字段不划算，先记在这里。
21. **`probe-contact.cjs` 的喂球是探针自己造的，游戏里没有这个东西**（11-15 新增）。
   它把球喂到**瞄准点**上，才能问「球到瞄准点的那一刻，真实拍面在哪儿」；游戏里的
   回球机瞄的是固定高度带，两个点不一样。所以探针给的 Δ 是**几何量的上界参考**，
   不是「玩家实际接球时会差多少」——后者还叠着「来球高度带 vs 你握法」那一层
   （见上面第 2 条）。**别拿探针的命中率当游戏难度**，它只用来做 `MODE=rest` /
   `MODE=contact` 的 A/B。

## 7.4 没有做的事

- 没有角色/手部渲染（只有球拍），所以「拍面中心被甩走」在视觉上没有参照物，只能靠球的位置判断。
- 没有真机自动化测试。所有真机结论都来自现场观察 + HUD 读数。
- 没有回放/录像功能。排查「刚才那一拍为什么没打到」只能靠 HUD 的六个瞬时值。
- **没有「这一分是谁的发球局」的界面提示**（只有发球那一刻的一行字）。打了十几分之后
  很难只看记分牌知道该谁发球——真实转播里那个小球是必要的，这里没做。
