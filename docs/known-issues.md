## 7.1 穿模症状已解决（历史）

真机症状曾是「挥拍时球从拍面穿过」，2026-11-10 真机确认已消失。当时的缓解是「球追拍面」，但那套非物理跟随也已在同一天撤销（见 `docs/history.md` 4.10）。当前待复验的是撤销之后的命中率与姿态一致性，见 `AGENTS.md` 第 0.3 / 0.4 节。

## 7.3 设计上仍然脆弱的地方

1. **去掉跟随后，大角度挥拍会够不着**。拍面中心挂在 0.6m 杆末端，转 30° 就平移 0.31m，判定半轴只有 0.20m；落地重瞄横向只有 1.6 m/s（约 20cm）。这是刻意保留的物理代价，不是 bug。若真机上正常幅度的挥拍也频繁漏接，先看 `probe-swing.cjs` 与挥拍时机，别急着把跟随加回来。
2. **击球高度依赖姿态**。`serve` 用来球高度 = `clamp(faceCenter.y, 0.8, 1.9)`，玩家把手机举高/放低，来球高度会跟着变。锚定方案取消后，这块又回到「跟着姿态走」。
3. **`liftOverNet` 的 `probe` 很贵**（一次回球 ~33 条候选 × 每条最多 1600 步）。目前只在击球时算一次，可以接受；如果以后要加「落点预览」之类的实时功能，需要缓存或降采样。
4. **`RacketTrack.at()` 是线性扫描**（最多 24 个元素）。当前 240Hz × 400ms 完全够用，不是瓶颈。
5. **`docs/motion-accuracy.md` 的握持标定还没做**。这是零成本、收益最大的一项：静止持拍取平均法线，与期望方向比对求安装角，出球时反向旋转补偿。若出现「球总往一边偏」，先看 HUD 的「拍面」读数。
6. **姿态门控还没真机验证**。`MAX_POSE_JUMP=1.2 rad`、`MAX_EXTRAP_MS=500` 是按 25–35Hz 采样和 20 rad/s 挥拍估的。若快速但连续的转腕被误判成跳变，拍子会短时走外推；看手机端「姿态」三态读数和「姿态 Hz」判断。
7. **视觉走位完全没真机验证**。`?vision=1` 是默认关的实验通道：色相阈值、镜像方向、`range=1.2` 收窄后的命中率、挥拍时躯干色块的波动，都不是纯函数单测能覆盖的。`npm run verify` 全绿不代表它可用，见 `docs/vision.md` 第 5 节。

## 7.4 没有做的事

- 没有角色/手部渲染（只有球拍），所以「拍面中心被甩走」在视觉上没有参照物，只能靠球的位置判断。
- 没有真机自动化测试。所有真机结论都来自现场观察 + HUD 读数。
- 没有回放/录像功能。排查「刚才那一拍为什么没打到」只能靠 HUD 的六个瞬时值。
