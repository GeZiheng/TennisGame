# 对打模式 · 与脚本回球机

> 这一册只讲**对打**：规则、对手、几何约束、怎么调、门禁测了什么。
> 11-15 删掉对墙打之后，**对打是唯一的玩法**，所以这一册也是玩法主文档；
> 判定 / 弹道 / 走位的算法细节仍在 `docs/algorithms.md`，本册不重复。
> 最后更新：2026-11-15（删除对墙打模式；浏览器与真机未验）。

## 1. 运行

只有一个服务：

```bash
npm run dev            # HTTP :5183
npm run dev:https      # HTTPS :5184（真机必须走这条）
```

端口在 `vite.config.shared.ts` 里配（`vite.config.ts` / `vite.config.https.ts` 各只有三行）。
`index.html` 就是大屏，`/` 直接进对打——曾经还要一条中间件把 `/` 改写到 `duel.html`，
删掉墙打之后那个页面不存在了，改写规则一并去掉。

**手机端是 `controller.html`**，一直是同一个页面，手机不知道对面是谁。

## 2. 曾经是「两个类、一份前端」

对墙打（`Rally`）和对打（`Duel`）曾经并存，而且刻意**没有**合成一个带模式开关的类：
`Rally` 的阶段语义是「这一球会不会自己回来」，`Duel` 的是「这一分归谁」，
捏在一起会让两边的 `if` 互相污染。

复用的是判定那几件：`advance` 物理、`sweepFace` 判定、`shotFromStroke`、`RacketTrack`、
`SwingDetector`。不共享的是状态机、判分、喂球、发球。

前端倒一直是**一份**：`src/play/app.ts` 同时服务两种模式，模式差异只有场景、
规则对象、HUD 主数字三处。11-15 删掉墙打时正是靠这层切分：把 `Rally` 与墙打分支
剥掉，`app.ts` 里 `game` 从联合类型变成 `let game: Duel`，其余（网络、时钟同步、
重连复位、姿态连续性、渲染管线——这个项目里最贵的代码）一行没动。
经过见 `docs/history.md` 4.27。

## 3. 判分

### 3.1 一分归谁：只认落点

一度想按「球穿过击球面」判漏接，那样能立刻给反馈，但会误判：玩家打出一条飞向
底线的长球，球会先穿过对手的击球面、再落在界外——按击球面判就是「对手漏接，
玩家得分」，而实际上这球出界了，该玩家失分。

所以胜负只在三个时刻判：**落地、撞网、飞出范围**。代价是反馈晚半秒。

**第一落点定局**：球合法落在对方场内之后，弹第二下、或者滚出边线，都**不再改判**。
这条踩过——原来的实现先判出界再判两次落地，结果「落在界内、对手没接到、
球继续滚出边线」被判成击球方出界，得分反而给了对手。`scripts/duel-sim.cjs`
的对打模拟把这个 bug 抓出来了。

### 3.2 分 → 局 → 盘（一盘定胜负）

状态机在 `core/match.ts`，纯计算、不碰球也不读时钟。`Duel` 在「这一分归谁」定下来
之后调一次 `awardPoint()`，照返回的 `PointOutcome` 决定接着发球、换发球局、还是收摊。

| 层级 | 赢法 | 备注 |
|---|---|---|
| 分 | 0 / 15 / 30 / 40 | 40-40 是平分，之后必须**净胜两分**（领先一分显示 `AD`） |
| 局 | 先到 4 分且净胜 2 | 一局结束**换发球方** |
| 盘 | 先到 6 局且净胜 2 | 6-6 进**抢七**（先到 7 分且净胜 2） |

**一盘定胜负**，所以抢七的胜者直接赢下整盘。真实赛制里抢七只赢下这一盘，之后还要
打下一盘——这里没有「下一盘」，抢七赢了就是比赛结束。

抢七的发球轮转是 **1-2-2**：先发的人只发第 1 分，之后每人连发两分。所以
`serveServer()` 不能直接返回 `server` 字段——抢七期间 `server` 一直停在「本该发
下一局的人」，而实际发球的人每两分换一次。同理，抢七那一下 `awardPoint` 提前返回、
**没有翻 `server`**，先发的人必须是它的对手（`otherSide(server)`）。

**为什么用原始计数存分数**：平分和占先是**相对关系**，存绝对值（0..3）就不得不在
每一处判断前后关系；存原始计数只在显示时换算一次（`pointLabel`），判定只做
「>=4 且净胜 2」这一条，不会漏分支。

### 3.3 发球：两次机会 + 斜对角的发球区

每一分有两次发球机会。一发失误还有二发，二发再失误就是**双误**，这一分归接发方。

发球**必须落在斜对角的发球区里**，不是「界内就行」。判定和普通落点走同一个
`onCollision`，区别只是区间从整块半场收窄成 `serveBox()`，而且只在**球第一次落地**
时按发球区判（`servePending`），之后就是正常回合。

**发球区每分交替**：由「这一局已经打了几分」的奇偶决定，偶数 = 右区（deuce）、
奇数 = 左区（ad）。**失误不占分数**，所以一发失误之后二发站的是**同一侧**。

发球几何全部收在 `core/serve.ts`，只有一处定义 `serveBox` / `serveStandX`——
这一层最容易出的错是「左右搞反」：发球区是斜对角的，而两边都朝球网看，
所以世界的 x 符号是反的（玩家的右区是 `x>0`，机器的右区是 `x<0`）。

### 3.4 玩家发球：自动抛球，手动挥拍

轮到玩家发球时，`Duel` 先等他走到发球位（`setup`，最多等 1.6 秒），然后**自动把球
竖直抛起来**（`toss`），但**必须玩家自己挥拍**才打得出去。

**抛球点和击球区都锚在握点上，不锚拍面**（11-15 改）。原因值得记一笔：拍面中心
挂在握点沿拍柄 0.6m 的杆子末端，位置由**手机朝向**决定——竖握在头顶、横握在胸前
0.6m 外、斜握在斜前方。同一句「抛球」抛到三个地方，玩家把拍子举到头顶时球不在那儿，
于是既打不着也发不进区（真机反馈第 1 条）。

| 量 | 值 | 说明 |
|---|---|---|
| 抛球出手点 | 握点上方 0.43m（= 2.05m） | 举拍发球时手的高度 |
| 抛球点纵深 | 站位靠网 0.25m | 身体**前**上方，正头顶压不出去 |
| 抛球初速 | 5.2 m/s → 顶点 **3.43m** | 比举高的拍面（2.22m）高 1.2m，有真正的上升段 |
| 击球区锚点 | 握点上方 0.53m、前方 0.25m | 额头前上方那一块 |
| 击球区半径 | 0.42m | 球形判定，见下 |

- 抛球期间球只受重力，拍子得自己送到球上——球不会来找拍子；
- 没挥到，球落地就是一次失误（`fault('nohit')`）；抛球后 3.2 秒还没打出去也算失误；
- 发球那一拍**不用 `sweepFace`**，改成球形判定（`tossContact`）。原因见
  `core/serve.ts` 的注释：竖抛的球会**沿着**竖直拍面走，`n0/n1` 永远同号，
  平面穿越一次都判不到；
- 判定中心是 `serveStrike(pose)`：拍面中心离锚点超过 0.35m 就朝锚点收。竖握时中心
  本来就贴着锚点（原样用，球仍打在拍线上），横握时中心在侧前方 0.63m，收回来才盖得住；
- 而且**只认下落段**（`vy <= 0.5`）。出手点在锚点下方 0.1m，本来就在判定球里，
  不卡这一条，抛出那一帧随手一挥就把球打出去了。卡住之后接触点在 **2.45m** 左右
  的下落段（实测），距抛球约 0.95 秒，正好是真实发球的节奏。

**落点怎么定**（`serveAim`）：拍面的**水平偏角**决定左右、**俯角**决定区内深浅。

- 左右**不夹**，只压缩灵敏度（`YAW_GAIN`=0.65）。从发球位看，对角发球区按射线
  只张开 **15.6°**（偏 8° 就出区），压缩后合法窗口 **23°**，中心仍对准区中心；
  转过头仍然出区——「必须发到正确的区」这条规则不能白送；
- 纵深是**映射**不是求交：俯角 3° 打深（靠近发球线）、18° 打浅（靠近网），中间线性。
  直接拿射线与地面的交点当落点的话，从 2.5m 高、14m 外看，能落进区的俯角窗口只有
  **7.2°–10.8°**（宽 3.6°）——手机上比走钢丝还难，而那不是技术，只是几何太窄。
- **屏幕朝天时改看拍框**。举高手机最自然的握法是屏幕朝上，此时法线没有水平分量，
  按它算出来的偏角是一条噪声。`aimAxis()` 于是在法线不朝球场时，从拍柄两头里挑
  朝网的那一头当准星。

地面上的绿色块 = 这一分该发去的区，红/绿的圈 = 拍面此刻指向的落点（和判定用的是
同一个 `serveAim`，不是示意）。两者只在**发球这一刻**显示，相持中把地板染一块绿
会抢视觉。

## 4. 回球机（`core/machine.ts`）

### 4.1 它是「一台机器」，不是「一个假人」

不参与任何特殊判定：每帧产出一个 `RacketPose`，塞进和玩家同一套 `RacketTrack` /
`sweepFace` 里。球必须真的碰到它的拍面才算回球，它够不着一样会漏。
`Duel` 里没有 `if (side === 'machine')` 的判定分支——以后换成 RL 策略或另一个
真人，状态机一行都不用改。

**唯一的例外是身体尺寸**：玩家的握点基准是 `RACKET_POS[1]`=1.3，自动走位在
0.70–1.65 之间升降（屈膝 / 举拍），拍面中心挂在 `FACE_CY`=0.6 的杆子上，所以实际可及
0.70–2.25m；回球机是机器，拍臂能升能降，握点给到 0.15–2.0（拍心 0.75–2.6）。

这不是给它放水，是**对称性的必需**：玩家打出来的球弹起顶点只有 1.0m 上下
（`GROUND_REST`=0.76，落地时的竖直速度本来就不大），拍面最低只能到握点高度的话
它每一个球都够不着。实测放宽之前，「够不着」几乎全部来自竖直方向，不是走位没跑到位。

### 4.2 三层

1. **预测**（`pickIntercept`）：把球复制一份往前推 5 秒，只在**我方半场、
   不贴网、不退出挡板**的采样里挑「离理想击球高度最近 + 要跑得最少」的那个点。
   弹一次地重算一次——落地会明显改变速度方向，整条弹道外推会把那一拐算错
   （`duel-sim` 早期版本踩过同样的坑）。
   时间可行性用**当前站位**算，每帧重算，所以不会「一开始就判定够不着然后放弃」。
2. **走位**（`moveToward`）：限速、有反应延迟、有站位误差。**这三样不是打磨，
   是核心设计**：一个每次都精确到位的对手，比一个打不过的对手更出戏。
3. **回球**（`attemptReturn`）：选目标落点，用 `aimIntoCourt` 反解出球速度。

### 4.3 出球直接给速度、不走 `Stroke`

玩家的链路是「挥拍 → `shotFromStroke` → 出球」：方向 = 拍面法线×0.72 +
拍头速度×0.30。想从「我要球落在那儿」反解出拍面法线和拍头速度，是 2 个未知数
1 个方程——欠定。脚本对手不需要模拟挥拍手感，所以直接给速度、绕开 `Stroke`；
但**碰撞判定不绕过**。

### 4.4 站位不钉在底线

第一版把它的 `z` 钉在 `OPP_HIT_Z`。结果是整场比赛只有一种球：从底线到玩家拍面
有 21.6 米，能让球「落在界内、并且到面时还有 1.3–1.6 米高」的弹道几乎只剩
月亮球。那不是求解器不行，是几何——真实球员遇到短球会**往前迎**，迎上去之后
到玩家的距离变短，快球也有解。

现在纵深放开到 `[OPP_BASELINE_Z-0.8, NET_Z-1.6]`，即 `[-23.3, -12.1]`。

### 4.5 它怎么发球：扫一条「接得到」的弹道

发球不是从落点反解，而是**直接扫速度**（`Duel.solveServe`）。理由是一条被实测逼出来
的几何：

发球区在网和发球线之间（z −10.5…−4.5），接发方的击球面在 z=0.3——球落地之后还要
再飞 4.8–10.8 米才到拍面。用 `aimIntoCourt` 的 `arriveY` 约束去解，**24 个落点一次都
解不出来**（卡在 1.3–1.6 这一段），于是每次都退到「只要落点进区」那一档，发出来的球
在拍面高度只剩 **0.4 米**：玩家连球皮都碰不到，对手的每个发球局都是白送。

根子在几何：平飞过去的球落地后弹一下，在 z≈−3 就二次落地了（那时拍面还在 0.4m 高的
贴地滚）；只有**抛高一点**的发球才能带着一整个第一弹的弧线飞到拍面。所以固定
`vy`=5.0–6.0（顶点约 4.2m），只扫水平速度 12–18 m/s，落点取发球区靠内的那一段 ——
到面高度正好 1.5–1.8 米。

用「扫」而不是「解」，是因为弹起之后的高度没有解析式（恢复系数和旋转都在 `advance`
里）；用真物理前向跑一遍最省事也最准。一次发球最多 39 条 4 秒的弹道，一分才跑一次。

> 代价是机器的发球看起来偏高、偏慢（顶点 4.2m）。这是**为了让这一分能打起来**，
> 不是调参没调好。想让它发更冲的球，先得让玩家能在更低的拍面高度接球。

### 4.6 `reachX` 与「幽灵走廊」

`pickIntercept` 的过滤线曾经是 `|x| > reachX + 0.6`，而 `moveToward` 的夹取是
`±reachX`。于是 3.0–3.6 之间成了一条**幽灵走廊**：预测认为那些点可以去，站位却只能
到 3.0，`gap` 又是按夹过的目标算的（读出来是「我站好了」），结果球从 0.4 米外擦过去。

平时看不出来：玩家回球的横向散布是 ±2.6，几乎不进那条走廊。**发球一上线就暴露了**
——发球是斜对角的，落在发球区中心的球到接发方击球面时已经飘到 ±3.4。现在三处
（预测过滤、站位夹取、`moveToward`）共用 `reachLimit() = reachX + REACH_SLACK`，
`gap` 也改成量**拍心到球**的真实距离。

## 5. 几何约束（调参前必读）

这三条互相咬，改一个另外两个跟着动。

### 5.1 玩家能接 0.70–2.25m，但该送的是 1.3–1.6m

握点**基准** `y` 是 `RACKET_POS[1]`=1.3，但自动走位会把它在 0.70–1.65 之间升降
（屈膝 / 举拍，见 `docs/algorithms.md` 3.9），所以拍面中心实际可及 **0.70–2.25m**
（横握）到 **1.30–2.25m**（竖握）—— `ARRIVE_Y` 那一段完全在里面。

但**可及 ≠ 该送**：到面高度越高，21.6 米外的可行弹道越少，回球机只能打月亮球；太低又要把
拍面压平、判定盘跟着转成水平面。所以 `ARRIVE_Y` 仍取握点基准 +0…+0.3（= 拍面水平到前倾
60°），三个候选段的实测对比写在 `machine.ts` 那两个常量上方。

> 11-13 之前握点是被锁死的，这一节写的是「玩家能接 1.3–1.9m」。实测那句话对**横握**成立，
> 对斜握/竖握是错的：`c.y`=0.53–0.6 意味着拍面恒在 1.85–1.9m，1.3–1.6m 的来球全从下方
> 掠过（42 球只中 2 球）。现在靠 y 轴修掉了，`ARRIVE_Y` 不用跟着改。

玩家侧的横向走位默认是自动的（`core/auto-move.ts`，见 `docs/algorithms.md` 3.9）。
这一条是硬要求：机器瞄的是**落点**，不是你的拍面，球不会来找你。

所以 `machine.ts` 的 `ARRIVE_Y_MIN/MAX` = `RACKET_POS[1]` / `RACKET_POS[1]+0.3`（现为 1.3 / 1.6），`arriveTol` 收到 0.12
（默认 0.2 太松，差 20cm 就得靠压手腕去补）。

### 5.2 落点被夹在 `z ≈ -6 … -1.5`

球落得越靠近玩家，弹起来到击球面时就越低（落到脚边的球本来就是低球）。
要让它同时还有 1.3m 高，落点只能在这一段。`ARRIVE_TARGET_Z_MAX` = -1.5
就是这个上限；下限随站位变，见 `candidateTargets()`：`lo = posZ + 0.45·d`。

实测各深度的可打落点带（`.tmp-bench/aim-solve.cjs`）：

| 迎击点 z | 可打的目标落点 |
|---|---|
| -21.3 | -6.0 … -2.0 |
| -18 | -4.5 … -2.0 |
| -14 | -3.5 … -1.0 |

### 5.3 候选落点阶梯

迎得越靠前，能打的目标越靠前。所以 `attemptReturn` 不是只试一个目标，
而是走一条阶梯（想打的 → 中路的 → 保底的），第一个解出来就用。
全都不行才判 `solve`——那说明几何上真的没得打。

## 6. 三档难度

只有六个数字，**没有「随机失误」**——那会让失败原因不可归因，玩家学不到东西。

| | `reactMs` | `moveSpeed` | `reachX`（实际可及 `+0.6`） | `aimError` | `cornerProb` | `depth` |
|---|---|---|---|---|---|---|
| L1 | 380 | 2.6 | 2.6（3.2） | 0.34 / 0.26 | 0.15 | -6.0 … -4.4 |
| L2 | 300 | 3.6 | 3.0（3.6） | 0.22 / 0.18 | 0.40 | -5.6 … -3.0 |
| L3 | 240 | 4.6 | 3.2（3.8） | 0.14 / 0.12 | 0.65 | -5.0 … -2.0 |

`depthShallow`/`depthDeep` **越负 = 离玩家越远 = 越好接**（球落地之后还有更长的
路要爬到你手上）。所以 L1 打得更软、更靠前场。

`swingWindowMs`（200–240）故意取大：它不是难度参数，是「球碰到拍面时它还没
决定」的容错阀。难度靠反应和走位，不靠挥空。

## 7. 门禁：`npm run duel-sim`

`scripts/duel-sim.mjs` 把 core 编成 CommonJS 到 `.tmp-duel/`，再跑
`scripts/duel-sim.cjs`：**6 个种子 × 3 档 × 60 秒**，编译 + 跑完约 9 秒。

种子是硬编码的（`SEEDS = [11, 222, 3333, 44444, 555555, 6666666]`，同时在 sim 里
接管了 `Math.random`），而这条链路里没有任何 `Date` / `performance` 读取——时钟
全部由 sim 自己喂。所以**同样的代码必然给出同样的数字**，改参数前后可以直接对数。

玩家一侧是「近乎完美的脚本」：按预测到面点摆拍、到点就挥、出球走求解器；
轮到它发球时会站到发球位、等抛球过了最高点再挥（`serveFace` 把拍面指向发球区中心，
挥拍方向与拍面平行以消掉侧旋——有侧旋的话球到对面击球面时已被甩出 1.5m，
每一分都会变成「发球直接赢」）。
所以这里出现的失败基本都能归到回球机头上——那正是要测的东西。

```bash
npm run duel-sim                        # 三档全跑 + 门禁断言
npm run duel-sim -- --level 2 --seconds 60
npm run duel-sim -- --trace             # 打印每次击球的接触点/出球速度
npm run duel-sim -- --trace-m           # 打印回球机每 0.25s 的迎击决策
```

**断言只钉「塌了就是塌了」的几条**，不钉具体数字（回合长度会随瞄准策略变化）：

- 每一档：回球机能真的把球打回来（`machineHits > 0`）
- 每一档：够不着 / 挥空 / 解不出 少于成功回球
- 每一档：测试玩家自己求解失败不过半
- 每一档：**玩家的发球有四分之一以上被接回来** —— 4.24 那轮的教训（见 7.2）
- L2：平均回合 ≥ 2.5 拍
- 跑满三档时：L3 回球次数 > L1（难度梯度方向正确）

**不钉比分**：这个脚本里的玩家一定接到、一定打进界内，它赢多少分只反映它自己
多强，跟回球机好不好无关。

**单测是另一批**：`npm test` 里有 25 项专测对打（计分状态机、发球几何、发球判罚、
到面高度约束、`park` 不重播、第一落点定局……），跑法见 `docs/testing.md` 8.3 最后三行。
两者不重叠——sim 测「一整局还打得下去吗」，单测测「某条规则单独拿出来对不对」。

### 7.1 当前实测（2026-11-14）

6 个种子 × 60 秒合计：

| | 平均回合 | 最长 | 机器击球 | 接发球成功率 | 总得分 |
|---|---|---|---|---|---|
| L1 | 1.4 拍 | 6 | 54 | 60% | 53 |
| L2 | 2.9 拍 | 12 | 75 | 83% | 28 |
| L3 | 13.0 拍 | 30 | 97 | **100%** | 8 |

「接发球成功率」= 玩家发出去的球里，回球机真的接回来的比例。这一列也有难度梯度，
而且它比回合长度更能说明「发球是不是被当成一次正常的球」——如果它掉到 0，
比赛就退化成「谁发球谁得分」。

难度越高分数越少，是因为**同样时间里比赛的回合变长了**（L1 一分钟能打完 53 分，
L3 只打完 8 分），不是它变弱——它的回球次数是 L1 的将近两倍。

对比 11-12 那版（L1 1.9 / L2 4.2 / L3 8.6 拍）：L3 明显变长、L1 略微变短，这两处都
跟着 4.6 那条修正一起变了。**这些数字是「脚本玩家 + 现在的发球规则」下的，
不代表真人会打出同样长度的回合。**

### 7.2 一条差点漏出去的门禁

4.24 加完发球之后，`npm run duel-sim` 是**绿的**——`machineHits > 0`、`够不着 < 回球数`
这些断言全过。但实际数字是「平均回合 **0.0** 拍」：78 分里没有一分打出过回合，
两边都是发球直接得分。旧断言抓不到它，因为 `machineHits` 把**机器自己的发球**也算进去了。

所以补了一条 `接发球成功率 ≥ 25%`。这条的形状很典型：**统计量选错了，
一整类 bug 就会躲在一个全绿的指标后面**——和 4.16 那次「没关练习墙」是同一个教训。

## 8. 门禁覆盖不到的

- **浏览器 / 真机完全没验**。对打模式的渲染（整场线条、对手球拍、相机）、
  比分 HUD、发球区高亮、两条信令同时开着会不会抢房间，都只有代码层的保证。
- **发球的手感一条都没验**：自动抛球的高度合不合手、等球落下来再挥会不会觉得慢、
  俯角映射的深浅直觉对不对、地面那圈红绿跟不跟得上手。这几条只有真机能回答，
  而且**第一版大概率要重调** `TOSS_VY` / `SERVE_REACH` / 俯角映射的两端。
- 玩家一侧在门禁里是求解器，不是 `shotFromStroke`。真机上玩家打出来的球
  比这野得多（`SPEED_MIN`=18 起步、靠拍面朝向决定方向），可以预期**真机上一局
  的回合长度会明显短于 7.1 表里的数字**。这不是回球机退化。
- 玩家打不出「低球」这件事**已经不成立了**：自动走位的 y 轴能屈膝到握点 0.70m
  （拍面 0.70m，横握），比 4.19 那会儿强。剩下的天花板是**压平拍面**——判定盘会跟着
  转成水平面，那不是站位能解决的，见 5.1。
- **玩家侧自动走位没有进对打门禁**。`duel-sim.cjs` 的测试玩家自己就有一套更精确的
  走位（`predictAtPlane` + 握点按 `AUTO_MOVE_DEFAULTS` 的 0.70–1.65 升降），比真机准；
  真机的走位是 `core/auto-move.ts`（x/z/y 三维选点），路线更保守、有 0.05m 死区
  和分轴限速。所以 7.1 的回合长度在真机上会再短一截。
- **发球局/接发球局的胜率没有测**。门禁只保证「有球可打」，不保证两边发球局是平衡的
  ——机器发球偏高偏慢（4.5），玩家发球是手动挥拍，两边其实不在同一个难度上。
