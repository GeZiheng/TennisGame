# 对打模式 · 与脚本回球机

> 这一册只讲**对打**：规则、对手、几何约束、怎么调、门禁测了什么。
> 墙打的判定与喂球仍在 `docs/algorithms.md`；本册不重复。
> 最后更新：2026-11-12（代码层完成，浏览器与真机未验）。

---

## 1. 运行

两种模式是**两个独立的服务**，各自的信令互不干扰，可以同时开着两个窗口分别打：

```bash
npm run dev            # 对墙打 · HTTP :5173
npm run dev:duel       # 对打   · HTTP :5183
npm run dev:https      # 对墙打 · HTTPS :5174（真机必须走这条）
npm run dev:duel:https # 对打   · HTTPS :5184
```

端口表与配置工厂在 `vite.config.shared.ts`，四个 `vite.config*.ts` 各只有三行。
对打服务的 `/` 会被改写到 `duel.html`——否则打开根地址会进到墙打，
玩家会以为「对打没生效」。

**手机端是同一个 `controller.html`**，不用换。手机不知道对面是谁。

---

## 2. 为什么不是 `Rally` 加一个开关

`Rally` 的阶段语义是「这一球会不会自己回来」，`Duel` 的是「这一分归谁」。
捏在一起会让两边的 `if` 互相污染。所以是**两个类**：

| | 墙打 `Rally` | 对打 `Duel` |
|---|---|---|
| 复用的 | `advance` 物理、`sweepFace` 判定、`shotFromStroke`、`RacketTrack`、`SwingDetector` | 同左 |
| 不共享 | 状态机、判分、喂球（`feedBounce`/`aimArrival`） | 状态机、判分（落点/撞网/出界）、发球 |

前端反过来是**共用的**：`src/play/app.ts` 一份代码，`main.ts` / `duel-main.ts`
只是 `startPlay('wall')` / `startPlay('duel')` 两行。网络、时钟同步、重连复位、
姿态连续性、渲染管线都是这个项目里最贵的代码，只能有一份。

差异只有三处，都收在 `startPlay` 里：场景（`PlayScene` 的 mode）、规则对象、HUD 主数字（比分 vs 连拍）。

## 3. 判分只认落点

一度想按「球穿过击球面」判漏接，那样能立刻给反馈，但会误判：玩家打出一条飞向
底线的长球，球会先穿过对手的击球面、再落在界外——按击球面判就是「对手漏接，
玩家得分」，而实际上这球出界了，该玩家失分。

所以胜负只在三个时刻判：**落地、撞网、飞出范围**。代价是反馈晚半秒。

**第一落点定局**：球合法落在对方场内之后，弹第二下、或者滚出边线，都**不再改判**。
这条踩过——原来的实现先判出界再判两次落地，结果「落在界内、对手没接到、
球继续滚出边线」被判成击球方出界，得分反而给了对手。`scripts/duel-sim.cjs`
的对打模拟把这个 bug 抓出来了。

## 4. 回球机（`core/machine.ts`）

### 4.1 它是「一台机器」，不是「一个假人」

不参与任何特殊判定：每帧产出一个 `RacketPose`，塞进和玩家同一套 `RacketTrack` /
`sweepFace` 里。球必须真的碰到它的拍面才算回球，它够不着一样会漏。
`Duel` 里没有 `if (side === 'machine')` 的判定分支——以后换成 RL 策略或另一个
真人，状态机一行都不用改。

**唯一的例外是身体尺寸**：玩家握点恒等于 `RACKET_POS[1]`=1.3，拍面中心只能在
半径 `FACE_CY`=0.6 的球壳上（1.3–1.9m）；回球机是机器，拍臂能升能降，
握点给到 0.15–2.0（拍心 0.75–2.6）。

这不是给它放水，是**对称性的必需**：玩家打出来的球弹起顶点只有 1.0m 上下
（`GROUND_REST`=0.76，落地时的竖直速度本来就不大），拍面最低只能到握点高度的话
它每一个球都够不着。实测放宽之前，「够不着」几乎全部来自竖直方向，不是走位没跑到位。

### 4.2 三层

1. **预测**（`pickIntercept`）：把球复制一份往前推 5 秒，只在**我方半场、
   不贴网、不退出挡板**的采样里挑「离理想击球高度最近 + 要跑得最少」的那个点。
   弹一次地重算一次——落地会明显改变速度方向，整条弹道外推会把那一拐算错
   （墙打那边的 sim 踩过同样的坑）。
   时间可行性用**当前站位**算，每帧重算，所以不会「一开始就判定够不着然后放弃」。
2. **走位**（`moveToward`）：限速、有反应延迟、有站位误差。**这三样不是打磨，
   是核心设计**：一个每次都精确到位的对手，比一个打不过的对手更出戏。
3. **回球**（`attemptReturn`）：选目标落点，用 `aimIntoCourt` 反解出球速度。

### 4.3 出球直接给速度、不走 `Stroke`

玩家的链路是「挥拍 → `shotFromStroke` → 出球」：方向 = 拍面法线×0.72 +
拍头速度×0.30。想从「我要球落在那儿」反解出拍面法线和拍头速度，是 2 个未知数
1 个方程——欠定。脚本对手不需要模拟挥拍手感，所以直接给速度、绕开 `Stroke`；
但**碰撞判定不绕过**。

### 4.4 站位不钉在底线

第一版把它的 `z` 钉在 `OPP_HIT_Z`。结果是整场比赛只有一种球：从底线到玩家拍面
有 21.6 米，能让球「落在界内、并且到面时还有 1.3–1.6 米高」的弹道几乎只剩
月亮球。那不是求解器不行，是几何——真实球员遇到短球会**往前迎**，迎上去之后
到玩家的距离变短，快球也有解。

现在纵深放开到 `[OPP_BASELINE_Z-0.8, NET_Z-1.6]`，即 `[-23.3, -12.1]`。

## 5. 几何约束（调参前必读）

这三条互相咬，改一个另外两个跟着动。

### 5.1 玩家能接的高度是 1.3–1.9m，但该送的是 1.3–1.6m

握点 `y` 恒等于 `RACKET_POS[1]`=1.3（三路走位都只搬 x/z，`setRacketBase` 传进去的
一直是这个高度），拍面中心只能在半径 0.6 的球壳上 ⇒ **1.3–1.9m**。但**可及 ≠ 该送**：
到面高度越高，21.6 米外的可行弹道越少，回球机只能打月亮球；太低又要把拍面压平、
判定盘跟着转成水平面。所以 `ARRIVE_Y` 只取握点 +0…+0.3（= 拍面水平到前倾 60°），
三个候选段的实测对比写在 `machine.ts` 那两个常量上方。

玩家侧的横向走位默认是自动的（`core/auto-move.ts`，见 `docs/algorithms.md` 3.9）。
这一条在对打里比墙打更关键：机器瞄的是**落点**，不是你的拍面，球不会来找你。

所以 `machine.ts` 的 `ARRIVE_Y_MIN/MAX` = `RACKET_POS[1]` / `RACKET_POS[1]+0.3`（现为 1.3 / 1.6），`arriveTol` 收到 0.12
（默认 0.2 太松，差 20cm 就得靠压手腕去补）。

### 5.2 落点被夹在 `z ≈ -6 … -1.5`

球落得越靠近玩家，弹起来到击球面时就越低（落到脚边的球本来就是低球）。
要让它同时还有 1.3m 高，落点只能在这一段。`ARRIVE_TARGET_Z_MAX` = -1.5
就是这个上限；下限随站位变，见 `candidateTargets()`：`lo = posZ + 0.45·d`。

实测各深度的可打落点带（`.tmp-bench/aim-solve.cjs`）：

| 迎击点 z | 可打的目标落点 |
|---|---|
| -21.3 | -6.0 … -2.0 |
| -18 | -4.5 … -2.0 |
| -14 | -3.5 … -1.0 |

### 5.3 候选落点阶梯

迎得越靠前，能打的目标越靠前。所以 `attemptReturn` 不是只试一个目标，
而是走一条阶梯（想打的 → 中路的 → 保底的），第一个解出来就用。
全都不行才判 `solve`——那说明几何上真的没得打。

## 6. 三档难度

只有六个数字，**没有「随机失误」**——那会让失败原因不可归因，玩家学不到东西。

| | `reactMs` | `moveSpeed` | `reachX` | `aimError` | `cornerProb` | `depth` |
|---|---|---|---|---|---|---|
| L1 | 380 | 2.6 | 2.6 | 0.34 / 0.26 | 0.15 | -6.0 … -4.4 |
| L2 | 300 | 3.6 | 3.0 | 0.22 / 0.18 | 0.40 | -5.6 … -3.0 |
| L3 | 240 | 4.6 | 3.2 | 0.14 / 0.12 | 0.65 | -5.0 … -2.0 |

`depthShallow`/`depthDeep` **越负 = 离玩家越远 = 越好接**（球落地之后还有更长的
路要爬到你手上）。所以 L1 打得更软、更靠前场。

`swingWindowMs`（200–240）故意取大：它不是难度参数，是「球碰到拍面时它还没
决定」的容错阀。难度靠反应和走位，不靠挥空。

## 7. 门禁：`npm run duel-sim`

`scripts/duel-sim.mjs` 把 core 编成 CommonJS 到 `.tmp-duel/`，再跑
`scripts/duel-sim.cjs`：**6 个种子 × 3 档 × 60 秒**，编译 + 跑完约 9 秒。

种子是硬编码的（`SEEDS = [11, 222, 3333, 44444, 555555, 6666666]`，同时在 sim 里
接管了 `Math.random`），而这条链路里没有任何 `Date` / `performance` 读取——时钟
全部由 sim 自己喂。所以**同样的代码必然给出同样的数字**，改参数前后可以直接对数。

玩家一侧是「近乎完美的脚本」：按预测到面点摆拍、到点就挥、出球走求解器。
所以这里出现的失败基本都能归到回球机头上——那正是要测的东西。

```bash
npm run duel-sim                        # 三档全跑 + 门禁断言
npm run duel-sim -- --level 2 --seconds 60
npm run duel-sim -- --trace             # 打印每次击球的接触点/出球速度
npm run duel-sim -- --trace-m           # 打印回球机每 0.25s 的迎击决策
```

**断言只钉「塌了就是塌了」的几条**，不钉具体数字（回合长度会随瞄准策略变化）：

- 每一档：回球机能真的把球打回来（`machineHits > 0`）
- 每一档：够不着 / 挥空 / 解不出 少于成功回球
- 每一档：测试玩家自己求解失败不过半
- L2：平均回合 ≥ 2.5 拍
- 跑满三档时：L3 回球次数 > L1（难度梯度方向正确）

**不钉比分**：这个脚本里的玩家一定接到、一定打进界内，它赢多少分只反映它自己
多强，跟回球机好不好无关。

**单测是另一批**：`npm test` 里有 13 项专测对打（到面高度约束、`park` 不重播、
第一落点定局……），跑法见 `docs/testing.md` 8.3 最后三行。两者不重叠——sim 测
「一整局还打得下去吗」，单测测「某条规则单独拿出来对不对」。

### 7.1 当前实测（2026-11-12）

6 个种子合计：

| | 平均回合 | 最长 | 机器击球 | 机器失分 |
|---|---|---|---|---|
| L1 | 1.9 拍 | 7 | 27 | 39 |
| L2 | 4.2 拍 | 21 | 59 | 16 |
| L3 | 8.6 拍 | 35 | 80 | 12 |

「机器失分」= 玩家得分。难度越高分数越少，是因为**同样时间里比赛的回合变长了**
（L1 一分钟能打完 50 分，L3 只打完 18 分），不是它变弱——它的回球次数是 L1 的三倍。

## 8. 门禁覆盖不到的

- **浏览器 / 真机完全没验**。对打模式的渲染（整场线条、对手球拍、相机）、
  比分 HUD、两条信令同时开着会不会抢房间，都只有代码层的保证。
- 玩家一侧在门禁里是求解器，不是 `shotFromStroke`。真机上玩家打出来的球
  比这野得多（`SPEED_MIN`=18 起步、靠拍面朝向决定方向），可以预期**真机上一局
  的回合长度会明显短于 7.1 表里的数字**。这不是回球机退化。
- 玩家打不出「低球」。这是当前玩法设计的天花板，见 5.1——想解决要先给玩家
  一个「蹲」或「后退」的操作，那是另一轮的事。
- **玩家侧自动走位没有进对打门禁**。`duel-sim.cjs` 的测试玩家自己就有一套更精确的
  走位（`predictAtPlane` + 握点能上下动到 0.62–1.0），比真机强；真机的走位是
  `core/auto-move.ts`（拍面中心二维选点），路线更保守、有 0.05m 死区和限速。所以 7.1
  的回合长度在真机上会再短一截。
