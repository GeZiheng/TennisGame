# 姿态精度：误差从哪来，要不要加第二个传感器

> 这份文档回答两个问题：**「挥拍手感奇怪」是不是姿态精度不够**，以及**如果需要更准，加一个手臂传感器该怎么加**。
>
> 先说明数据来源：下面的量级来自代码里的实际参数（采样率、网络往返、平滑时间常数）和公开的传感器规格，**不是真机实测**。真机量化方法写在最后，建议先量一遍再动手。

---

## 0. 一句话结论

**传感器精度不是瓶颈。** 手机 `deviceorientation` 给的 β/γ（俯仰、横滚）有重力做参考，静态误差 1–2°，这个数字比拍面判定容差（2cm，相当于 2.6°）小得多。

真正让「手感不像自己的动作」的是另外三件事，按影响从大到小排：

| # | 问题 | 量级 | 出球方向误差 | 加传感器有用吗 |
|---|---|---|---|---|
| 1 | **握持安装角没标定**。手机屏幕平面和「你认为的拍面」之间差多少，系统不知道 | 5–20° | 放大 0.71 倍，10 米处偏 **0.6–2.5m** | 部分有用（能测手腕，但安装角仍要标定） |
| 2 | **姿态采样率在挥拍中段只有 4–5 个样本** | 25–35Hz | 相邻样本差 **28–38°**，取最近样本误差 ±14–19° | 没用 |
| 3 | **只测角速度，不测位置**。拍面只能绕握点画弧，伸拍够球做不到 | — | 击球点位置 | **有用，且只有它能解决** |

所以推荐顺序是 **1 → 2 → 3**，前两件都是纯软件，一天能做完；第三件才需要第二个传感器。

## 1. 现在的姿态链路

```
手机 deviceorientation（25–35Hz，系统融合好的绝对姿态）
   │  deviceEulerToWorldQuat(α, β, γ)
   ▼
toOutputQuat(abs, yawZero)          ← 只去掉绕世界 Y 的朝向，倾斜原样保留
   │
   ▼  60Hz 定时器发包（姿态值可能重复 2 次）
网络 20–60ms
   │
   ▼
大屏 setOrientation(q) → targetQ
   │  slerp，τ = 22ms（慢速）/ 10ms / 3ms（快速，等效 ω > 12 rad/s）
   ▼
syncRacket() → RacketPose{t, pos, q} → pushRacket（60Hz，带时间戳）
   │
   ▼
RacketTrack 按时刻 slerp 插值 → 240Hz 物理子步求交
```

链路本身是干净的：时间戳对齐、插值、子步扫掠都做了。误差不来自这里。

## 2. 六项误差，逐项拆

### 2.1 握持安装角（最大，且是系统性的）

系统把**手机的姿态**当成**拍面的姿态**：

```ts
// swing.ts
const face = vrot(q, [0, 0, 1]);   // 设备 +Z = 拍面法线
const grip = vrot(q, [0, 1, 0]);   // 设备 +Y = 拍柄
```

这个映射本身是对的（手机长边=拍柄、屏幕法线=拍面法线）。但**手机在手里的姿态和你脑子里的拍面并不重合**：

- 手机是扁的，握在掌心里必然有内外旋，常见 5–15°
- 不同人的握法差异更大（有的人屏幕朝前，有的人朝斜上）
- 挥拍时手腕还会再带 5–10° 的动态变化

而 `shotFromStroke` 里出球方向是 **72% 拍面法线 + 30% 拍头速度方向**，所以拍面偏 θ 度，球偏约 0.71θ：

| 握持偏角 | 出球偏角 | 10 米处横偏 |
|---|---|---|
| 5° | 3.5° | 0.62m |
| 10° | 7.1° | 1.24m |
| 15° | 10.6° | 1.87m |
| 20° | 14.2° | 2.52m |

（这张表可以直接复现：构造一个 `face = [sinθ, 0, -cosθ]` 的 Stroke，喂给 `shotFromStroke`。）

**10 米偏 1.2 米是什么体验**：球还在场内，但明显不是你想打的方向。玩家会归因成「手感奇怪」，而不是「握法偏了」——因为屏幕上没有任何东西告诉他偏了多少。

### 2.2 yaw 漂移与磁跳变

`abs` 的 α（绕重力的朝向）是个弱项：

- **Android**：α 参考磁北，室内有钢筋、音箱、手机壳磁铁 → 跳变 5–15°，且是**突然跳**
- **iOS**：α 的参考是任意起点，系统靠陀螺积分维护 → 慢漂，约 1–3°/分钟

现在是「第一次拿到姿态时把 α 记为 0」（`yawZero`），之后 α 的变化原样透传。所以 Android 上磁跳变会让球拍**自己转一下**，这个很致命——玩家会明确感到「拍子抽风了」。

### 2.3 姿态采样率（第二大的问题）

这是最容易被忽略、但对「挥拍瞬间」影响最大的一项。

挥拍中段角速度 12–20 rad/s（`SWING_THRESHOLD` 是 3，`CHARGE_FULL_W` 是 19）。按 30Hz 算：

```
相邻样本间隔        33ms
15 rad/s 转过      0.50 rad = 28.6°
20 rad/s 转过      0.67 rad = 38.2°
```

而 `buildStroke` 用的是 `peakSample`——也就是**恰好那一个采样**的姿态。峰值落在两个样本之间时，姿态误差最大 ±14–19°。

这和 2.1 是**独立叠加**的：一个人的总误差可能是「握持偏 10° + 采样偏 12°」。

注意：大屏端的 `RacketTrack` 插值不会改善这一点。插值只能在两个已知样本之间画最短弧，源数据只有 30Hz，插不出中间的信息。

**但角速度传感器的采样率通常是 60Hz**（`devicemotion` 的 `rotationRate`）。所以这里有一个纯软件的解法：见 3.2。

### 2.4 网络延迟

**不影响精度**。挥拍事件带的是手机时刻的峰值（`stroke.t`），姿态历史带时间戳，`RacketTrack.at(t)` 按时刻插值。时钟同步（`ClockSync`）把两边时基对齐了。

它影响的是**延迟感**：挥完到球飞出，中间有「网络往返一半 + 峰值回落结算 16–33ms」。这条链路已经被 `liveStroke` 抢跑和 `CONTACT_HOLD_MS = 100ms` 覆盖掉了。

### 2.5 平滑滤波的相位滞后

`syncRacket` 里 τ 是自适应的：12 rad/s 以上降到 3ms，几乎不平滑。所以快速挥拍这一段基本没有额外滞后。慢速时 22ms 的滞后反而有好处（压掉手抖）。

这一项已经处理得比较到位，不是主要矛盾。

### 2.6 只有姿态、没有位置

`RacketPose.pos` 永远是 `RACKET_POS`（握点固定在胸口前方），拍面中心 = `pos + q·(0, 0.6, 0)`。

也就是说：**球拍在空间里只能绕一个固定点旋转，不能平移。**

真实挥拍里，「够不着」和「够得着」有一半是靠伸拍（肩、肘、腕的平移）解决的。现在这部分完全由键盘走位代偿——所以玩家会觉得「我明明伸手就到了，游戏里却要按 A/D 跑过去」。

这是唯一一项**必须靠额外传感器**才能解决的（加速度计二次积分算位移在几十毫秒尺度上漂得离谱，不可用）。

## 3. 不加硬件能做什么

### 3.1 握持标定（半天，解决 2.1）

思路：让玩家做一个**已知的标准动作**，把「手机 → 球拍」的固定安装旋转解出来。

实现要点：

1. 大屏上放一个「校准」按钮，触发 `recal`（协议里已有这条消息，手机端也已有处理分支）。
2. 校准流程不是「静止 2 秒」就完事——那样只会把当前的错误握法记成基准。必须**给视觉反馈**：屏幕上把球拍摆到「标准姿态」（竖直、拍面正对球场），玩家转动手机直到手里的角度和屏幕上的一致。
3. 确认时手机端记录 `qRef`，算出安装偏移：

```ts
// 期望姿态已知（IDLE_POSE），实际姿态是 qRef
const qMount = qMul(IDLE_POSE_Q, qConj(qRef));
// 之后每帧
out = qMul(qMount, qAbs);
```

4. 存 `localStorage`，下次开局直接复用（同一台手机、同一个人的握法不会天天变）。

**为什么不能只靠「相对启动姿态」**：现在的 `yawZero` 只归零朝向，倾斜是绝对的。而握持偏差主要在倾斜上（内外旋），归零朝向管不到。

**代价**：校准之后，屏幕上的球拍会和你手里手机的角度差一个固定值。这是**正确的**——真实球拍的拍面和手机之间本来就有安装角，屏幕上应该显示真实球拍，不是显示手机。

### 3.2 陀螺仪插值：把姿态从 30Hz 提到 60Hz（一天，解决 2.3）

`devicemotion` 的 `rotationRate` 通常 60Hz，而 `deviceorientation` 只有 25–35Hz。做一个极简互补滤波：

```
每次 rotationRate（60Hz）:  q ← integrate(q, ω - bias, dt)      // 高频推进
每次 deviceorientation（30Hz）: q ← slerp(q, qAbs, α)            // 低频校正，α ≈ 0.3
```

- 高频推进补上了「两个绝对姿态之间那 33ms」的信息，挥拍峰值处的姿态误差从 ±14° 降到 ±7°
- 绝对姿态做校正，抑制积分漂移
- α 不能太大：`deviceorientation` 本身有系统融合延迟（20–50ms），校正太猛会把那个滞后引进输出

`core/imu.ts` 里已经有 `ImuTracker`（纯积分 + 静止冻结 + 零偏估计），加一层「绝对姿态校正」就成型了。要在真机上对比 `poseHz` 和实际跟手程度。

### 3.3 yaw 抗磁跳变（半天，解决 2.2）

把 α 拆成两部分用：

- **倾斜（pitch/roll）用 `deviceorientation` 的 β/γ**：重力参考，不会漂，也不受磁干扰
- **朝向（yaw）用 `rotationRate` 积分**：不含磁力计，没有跳变；缺点是零偏漂移

实现上是先用 `qYaw(qAbs)` 分离朝向、只取倾斜部分 `qTilt`，yaw 单独用陀螺积分，最后 `q = yawQuat(yaw) · qTilt`。

取舍：磁跳变是「突然转 30°」，玩家立刻能察觉；陀螺漂移是「一分钟漂几度」，不容易注意，而且每球断球时可以静默重新对齐。**对网球这个场景，漂移比跳变好接受得多。**

风险：如果设备 `rotationRate` 不可用（代码里已有 `useDiff` 兜底判断），就得退回现在的方案。

## 4. 加第二个传感器：能解决什么、怎么做

### 4.1 它能解决的只有一件事（但这件事很大）

前面六项里，**只有 2.6（位置）必须靠硬件**。而 2.6 恰恰是「够球」体验的核心：

现在的模型是「拍面绕握点旋转」，玩家伸拍、上前一步的身体动作全部丢失，只能靠 WASD 平移整个站位——这是键盘游戏的模型，不是体感游戏的模型。

有了第二段（小臂），就能估算拍面中心的三维位置：

```
肘部（固定，或由肩推算）
   └─ 小臂：长 L1 ≈ 0.26m，方向由「手臂传感器」给出
        └─ 腕
             └─ 球拍：长 L2 = FACE_CY = 0.6m，方向由「手机」给出
                  └─ 拍面中心
```

`p_face = p_elbow + R_arm · [0, L1, 0] + R_racket · [0, L2, 0]`

同时它还能**间接改善 2.1**：手腕相对小臂的弯折角是测出来的，而不是猜的。

但它**对 2.3（采样率）毫无帮助**——两个传感器都是 30Hz，误差还是那么大。所以别指望「加了传感器手感就顺了」，顺不顺是采样率和延迟的事。

### 4.2 硬件选择

| 方案 | 成本 | 采样率 | 优点 | 缺点 |
|---|---|---|---|---|
| **第二部手机**（复用现有 controller 页面，`?role=arm`） | 0（手边就有） | 25–60Hz | 零成本、协议复用、能立刻验证值不值得做 | 重、绑在手臂上晃、要充两台电 |
| **BLE IMU**（WT901、MetaMotionR、BNO085 模块） | 200–800 元 | 100–200Hz | 轻、快、可贴在小臂上 | 要写 BLE 解析、要做磁校准、只支持部分浏览器（Web Bluetooth 在 iOS Safari 上不可用） |
| **手表**（Apple Watch / Wear OS） | 已有 | 50–100Hz | 轻 | 各平台 API 完全不同，网页端基本拿不到原始 IMU |

**建议先用第二部手机验证。** 如果「有了位置」确实让体验质变，再考虑专用 IMU；如果加完发现手感只好了 10%，那这笔钱就省下来了。

### 4.3 佩戴与标定

- 位置：**小臂中段偏肘**，手机长边沿小臂方向。绑在腕上会和球拍段重叠，信息冗余。
- 朝向：屏幕朝外（远离手臂），这样设备 +Y = 小臂方向、+Z = 小臂外侧法线。
- 标定（每次开局一次，10 秒）：
  1. 站直，小臂水平前伸，球拍竖直（标准准备姿势）
  2. 两个设备各记录一次绝对姿态
  3. 由几何约束解出两个安装偏移：`qMountArm`、`qMountRacket`
  4. 同时得到「小臂方向 = 世界 -Z」的参考，用来算肘部初始位置

### 4.4 协议与时钟

现有 `Link` 是 1:1 的（一个 room 两个 peer）。加第二路有两条路：

1. **复用现有链路，多加一路 peer**：房间号后面加后缀（`room-arm`），大屏开第二个 `Link`。改动最小，但两路各自做时钟同步，两套 `ClockSync` 会各自漂 1–3ms——对 240Hz 物理（4.17ms/步）来说可以接受。
2. **手臂设备把数据发给手机，手机合并后一包发出**：时钟只有一套，对齐最干净；但多一跳蓝牙/WiFi，延迟 +10–30ms，且手机要做转发。

**推荐 1**，因为延迟比 3ms 的时钟误差重要得多。

数据量：手臂只需要姿态 + 角速度，一帧 16 字节，30Hz → 不到 1KB/s，可以忽略。

### 4.5 判定的改动（这是真正的工作量）

有了位置之后，`sweepFace` 不能再假设拍面中心固定在 `RACKET_POS`：

```ts
// 现在
pos: [racketX, RACKET_POS[1], HIT_Z]   // 由键盘给

// 之后
pos: p_face                            // 由两段刚体算出来，每帧不同
```

连带要改：

- `RacketPose.pos` 每帧变化 → `RacketTrack` 也要插值位置（现在只插值姿态）
- 「漏接」的判定线（`BEHIND_PAD`）要跟着真实位置走
- 喂球的目标点（`feedBounce` 的 `targetZ/targetY`）要跟着真实拍面走
- 回球补偿 `liftOverNet` 的目标同样
- 走位（`WASD`）的语义要重新定义：是移动整个身体（含肩），还是微调？前者会和「伸拍」重复

**工作量估计**：协议 + 标定 2–3 天，两段刚体与位置融合 2 天，判定与喂球重构 3–4 天，真机调参 2–3 天。合计 2 周左右，而且中间每一步都要真机验证——这是它最大的成本，不是代码本身。

## 5. 建议的顺序

| 步骤 | 内容 | 工期 | 预期收益 |
|---|---|---|---|
| 1 | **先量**：HUD 显示实时「拍面偏角」，静止持拍时看这个数是不是接近 0 | 2 小时 | 判断 2.1 到底有多大 |
| 2 | 握持标定（3.1） | 半天 | 消掉最大的一项 |
| 3 | 陀螺插值 60Hz（3.2） | 一天 | 挥拍瞬间误差减半 |
| 4 | yaw 改用陀螺积分（3.3） | 半天 | 消掉 Android 磁跳变 |
| 5 | 再量一次，此时手感应该已经「像自己的动作」了 | — | — |
| 6 | 如果还想要「伸拍够球」，再上第二传感器 | 2 周 | 质变，但贵 |

**第 1 步最重要。** 在不知道「拍面偏角」实际是多少度之前，任何优化都是在猜。如果静止时显示 3°，那 2.1 根本不是问题，应该直接跳到 3.2；如果显示 18°，那前面的分析就成立。

## 6. 怎么自己量

真机上按顺序看三个数：

1. **手机端仪表区的「姿态」采样率**（`poseHz`）。低于 25Hz 说明这台机器的 `deviceorientation` 很稀，2.3 会很明显。
2. **手机端仪表区的「角速度」来源**。显示 `rotationRate` = 60Hz 通道可用，可以做 3.2；显示 `diff` = 只能靠姿态差分，60Hz 插值做的也是 25Hz 的信息，收益有限。
3. **大屏 HUD 的「拍面偏角」**（待实现）。静止持拍、拍面朝球场时，这个数就是 2.1 的量级。

把这三个数发我，就能确定该先做哪一项。
