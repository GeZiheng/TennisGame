# 网球体感 · P1 对墙打

手机当球拍，大屏对着练习墙打。手机只负责**姿态**和**挥拍**，球的物理、碰撞、音效全在大屏算。

当前进度：P0（链路 + 姿态）已验收，P1（挥拍 → 弹道 → 击球 → 对墙打）已跑通，五种力度档位端到端模拟零漏接。

---

## 怎么跑起来

### 第一次

```bash
npm install
npm run dev:https
```

`dev:https` 会先生成本地 CA 和服务器证书（`.cert/`），再起 HTTPS 服务。终端会打印这样的信息：

```
服务器证书仍然有效（IP 未变：192.168.x.x）

  ➜  Local:   https://localhost:5174/
  ➜  Network: https://172.x.x.x:5174/    vEthernet (WSL)
  ➜  Network: https://192.168.x.x:5174/  以太网
```

> **地址不止一个。** 装了 WSL / Docker / VMware 的机器会多出 `172.x`、`10.x` 的虚拟网卡，手机连那些地址一定打不开。**认准后面写着「以太网」「WLAN」「Wi-Fi」的那一条**——上面例子里是以 `192.168` 开头的那一条。

不用自己判断：`make-cert.mjs` 会单独打印一行「手机访问 → https://192.168.x.x:5174/」，大屏二维码里的地址也是同一套逻辑筛出来的（排除了 loopback / vethernet / vmware / docker / wsl，并按 `192.168` > `10` > `172` 排序）。**直接扫码最省事。**

### 每次开打

1. **大屏**（电脑 / 接电视的笔记本）打开 `https://localhost:5174/`
   证书警告点「继续」——红的也不影响玩，想变绿见下面「把红锁变绿锁」
2. **手机连同一个 Wi-Fi**（建议 5GHz），扫大屏中间的二维码
3. 手机上如果提示证书不受信任，选「继续访问」；点「开始挥拍」，**把手机横过来当拍柄握**
4. 大屏左上角出现「连拍」，就可以打了

> **两端必须是同一个服务进程。** 信令房间在内存里，大屏开在 5173、手机连到 5174 是配不上的。用 HTTPS 就两端都用 5174。

二维码里编的是 `https://192.168.x.x:5174/controller.html`，不是 localhost。手机扫不开时，也可以手动把大屏上那串地址敲进去（面板里有「复制」按钮）。

### 不想掏手机，只想看看画面

```bash
npm run dev          # HTTP，5173，不需要证书
```

浏览器打开 `http://localhost:5173/`，然后按 **`M`** 启动本地模拟控制器——它会生成假数据喂进同一条链路（不经过网络），可以先看手感、看 HUD、看特效。

### 全部命令

| 命令 | 作用 |
|---|---|
| `npm run dev:https` | 真机测试用的主命令（HTTPS + 5174 + 自动签证书） |
| `npm run dev` | 纯本地看画面（HTTP + 5173） |
| `npm run build` | 类型检查 + 打包 |
| `npm test` | 核心逻辑单测（77 项，不需要浏览器） |
| `npm run sim` | 端到端模拟：假数据跑完整对拉，验证手感参数 |
| `npm run cert` | 只重新签证书（局域网 IP 变了时用） |
| `npm run trust` | 把根证书装进系统受信任库 |
| `npm run test:signal` | 信令房间配对冒烟测试（需先 `npm run dev`） |

## 怎么打

| 动作 | 效果 |
|---|---|
| 拍面朝球场往前挥 | 球向前飞，**拍面朝哪球往哪飞** |
| 向上刷球 | 出上旋，球过网后会往下扎 |
| 向下切球 | 出下旋 |
| 挥得越快 | 球越快（18–32 m/s），音效和特效也更重 |
| 拍面完全背对球场 | 球会往后飞——这不是 bug，打不出去就是打不出去 |

**连拍只在球过网那一刻 +1**，撞网或漏接归零。

### 喂球是「落在你前面、弹起来再过来」

每一球从对面发出后，会落在**你拍面前方 1.55–1.85 米**的位置，弹起来再过来。目标不是「精确送到拍面中心」，而是**弹起后的最高点落在拍面附近一定范围**：横向 ±12cm、高度 ±10cm、前后 0.55–0.85m（`FEED_APEX_DX/DY/BACK_*`）。

用弹地球而不是直接送过来，有三个原因：

1. **真实网球绝大多数来球都是弹地之后的。** 球在空中飞十米直扑脸前，本身就是现实里不会发生的事。
2. **落点是视觉节拍器。** 球第一次落地 = 计时开始，之后球的高度单调可预测。挥拍时机可以靠看落点学出来；直送过来的球没有这个锚点，玩家只能等球飞到脸前再反应——而拍面只有 30×38cm，那基本就是猜。
3. **落点把「球速」和「来球高度」解耦了。** 直接送的时候，想让球慢就得压平（然后撞网），想让它高就得吊起来（然后够不到）。落地之后，弹起的竖直速度由入射角决定，水平速度由落点距离决定，两者可以分开调。

**落点为什么不能再近了。** 这条是抛体运动卡的，不是参数没调：球弹起后要爬升到拍面高度（1.0–1.9m），竖直速度必须先有 `sqrt(2g·h)` ≈ 4.4–6.1 m/s，爬升时间 0.45–0.62 秒；而弹起后的水平速度由入射速度决定（约 3.5–5.0 m/s，改不动——再慢球就飞不到十米外的落点了）。两者相乘，**最高点必然落在弹起点前方 2.3–2.45 米**（`FEED_APEX_LEAD`，这是实测值，别凭直觉估）。

所以落点只能取在「顶点之前一点」：1.55m 时球到拍面还在缓升（+1.3 m/s），顶点落在拍面后面 0.55–0.85m，视觉上是「球往上送到你手上」；再近到 1.2m 就变成 3.2 m/s 的急升，球从拍子上方蹿过去，反而更难打。实测见 `scripts/probe-feed-scan2.cjs`。

| 落点距拍面 | 到拍面时的竖直速度 | 顶点位置 | 手感 |
|---|---|---|---|
| 1.2m | +3.2 m/s，急升 | 拍面后 1.1m | 球往上蹿，容易从拍面上方过去 |
| **1.55–1.85m** | **+1.3 ~ +2.0 m/s，缓升** | **拍面后 0.55–0.85m** | 球「送到手上」，落点也够近 |
| 2.2m | ≈ 0，顶点正好在拍面 | 拍面上 | 最稳、最好打，但落点看着远 |
| 3.0m | −3.8 m/s，下落中 | 拍面前 1.1m | 像掉下来，窗口只有 0.06 秒 |

**高度和横向也跟着拍面走，但只保证落在「附近」。** 来球高度 = 拍面中心高度（静止握法下是 `RACKET_POS[1] + FACE_CY` = 1.6m）± 10cm，横向在拍面中心 ±12cm 内随机，前后再散 0.55–0.85m——每球都会差十几厘米。

这两个数不是随便取的：判定椭圆的等效半轴是横向 0.203 / 竖直 0.243。散布之所以取 0.12 / 0.10 而不是贴着半轴，是因为横向和竖直会**同时**偏——两轴都取满时合成偏离是 `sqrt((0.16/0.203)² + (0.14/0.243)²) ≈ 0.98`，几乎贴着盘边，再叠上「球到面时拍面还在动」的跟随误差就会偶发判空。0.12 / 0.10 合成后约 0.72，留三成余量，实测甜区读数落在 0.45–0.75：明显散开，但一定在盘内。

为什么不要「精确送中心」：每球都吸在同一个点上，玩家两拍之后就不用看球在哪侧了，接球退化成打地鼠。

**球在最后半秒跟着拍面走。** 这是整套设计里最关键的一条，原因见下面「挥拍时球拍真的会转」那节——球拍是绕握点转的杆子，一挥拍拍面中心就扫出去半米，球如果还照着挥拍前的位置飞，就会从拍面里穿过去。

所以分两段处理：

1. **我方半场落地那一刻重瞄**（`aimAfterBounce`）：落点是整条弹道上唯一不会被察觉的修正点，球本来就要在这里剧烈改向。用和游戏内完全相同的物理试算，把球送到「此刻拍面中心 + 本球散布」。
2. **最后 0.55 秒持续跟随**（`Rally.steerToRacket`）：改球的**方向**而不改速率——直接求「t 秒后到达目标点」的速度 `to/t`，因为 t 就是用剩余距离除以当前速率算出来的，这个期望速度的模长正好等于速率。横向、竖直、纵向一次修完，球被轻轻带向拍面，不会忽快忽慢。上限 12 m/s、加速度 150 m/s²，够跟上一次正手挥拍里拍面中心 0.6–1.1m 的位移。

跟随只在**弹起之后**（`ball.bounces >= 1`）介入：落地之前改方向会挪动落点本身，那就把「落点 = 视觉节拍器」毁了。

**顺带修掉了一个结构性死结。** 旧方案要求球一口气飞到拍面、中途不许落地。你退到后场时飞行距离 12 米以上、初速只有 10.5，球必然中途落地；而求解器把「提前落地」当成「仰角还不够」，一路加到上限，于是每一球都变成从墙顶飞过的月亮球——这正是「发球普遍较高、退到后场够不到」这一反馈的由来。弹地球不存在这个问题：落地是设计的一部分。

求解方式也值得记一笔：未知量两个（`vy`、`vz`），约束两个（落点、到达高度）。不用二维搜索，而是参数化成一个东西——**发球到落地的飞行时间 `t`**。`t` 定了、落点定了，速度就定了；而「弹起后到拍面的高度」对 `t` 严格单调，直接二分。一次求解约 60 次模拟，几毫秒。


### 一个必须知道的规律：越用力，拍面要越平

同样的仰角，挥得越快球飞得越高越远——真实网球就是这样。全力抽击还保持 20° 仰角，球回来时会在 2.35m 的击球上限之上，你只会看到「够不着」。

模拟里仰角从 20° 压到 6°，才能做到满力 36 拍零漏接。所以：

- 球总是从头顶飞过去 → **压低拍面**
- 球总是撞网 → **抬高拍面**

## 面板怎么读

### 左上角：连拍 HUD

大字是当前连拍，下面一行是最好成绩、上一拍球速、上旋/下旋类型。橙色的那行字是击球反馈（比如「挥晚了」）。

### 左下角：链路面板

上半是**击球诊断**，打不到球、或者觉得手感黏时看这六个数：

```
挥拍 12 · 到面 12 · 时差 晚 43ms · 甜区 34% · 出球 0ms · 拍面 右6°
```

| 现象 | 结论 |
|---|---|
| **挥拍 = 0** | 角速度没上来。看手机端「角速度」标记是不是「姿态差分」 |
| 挥拍 > 0，**到面 = 0** | 球压根没碰到拍面，物理或阶段卡住了 |
| 时差 **超过 ±150ms** | 挥早了或晚了。人反应 250ms 起，先看看是不是网络抖动 |
| **甜区 = 没碰到** | 球从拍子旁边飞过去了。多半是球来时你正好在走位，按 `A` / `D` 迎上去 |
| 甜区 **> 85%** | 打到了，但擦着拍框。还能回去，只是出球方向会歪 |
| **出球 > 40ms** | 球在拍面上停太久，手感会「黏」。正常应该是个位数 |
| **拍面 偏 8° 以上** | 球会往那边偏（放大 0.71 倍，10 米差 1.2m）。不是判定的问题，是握法 |

「甜区」是球打在拍面上的位置：0% 是正中心，100% 是拍框内沿。
这个数就是「严格碰撞」在工作——如果你换了拍面角度或者走错方向，
它会立刻变差甚至变成「没碰到」。

「拍面」是**球拍法线当前指向**相对「正对球场」的偏角，正数偏右、负数偏左；
拍面接近水平时会直接显示「朝上」或「朝下」。**静止持拍、拍面朝球场时应该显示「正」。**
如果一直是 10–15°，那不是传感器不准（β/γ 有重力参考，误差 1–2°），
而是手机在手里的内外旋没和你的「拍面」对上——详见 `docs/motion-accuracy.md`。

「时差」和「出球」是两件事，别混：时差是**挥拍时机准不准**（决定判不判得上），出球是**判上之后球多久才动**（决定手感顺不顺）。时差 0、出球 120ms 的体验依然是「明明打到了，球被吸住一下才弹走」。

下半是链路指标：

| 指标 | 含义 | 及格线 |
|---|---|---|
| **端到端 p50** | 从手机传感器采到这一帧姿态，到它被大屏处理完 | < 50ms 无感；> 90ms 会觉得拍子有惯性 |
| **网络 p50** | 只算 Wi-Fi + 排队这一段 | < 25ms 很好；> 50ms 先治网络 |
| **抖动** | 最差的 5% 比中位数糟多少 | < 30ms |
| **峰值角速度** | 手机陀螺仪有没有被甩到量程外 | < 2000°/s 最好 |

**「端到端」减去「网络」，就是手机那一段**（采样等待 + 发包排队）。差值大说明锅在采样率，不在 Wi-Fi——去手机页面看「姿态 xx Hz」。差值小说明网络是主因。

底部曲线是最近 120 个包的单向延迟，**红色虚线是 100ms**。超过它，玩家会归因为「我打空了」而不是「网络卡了」。

抖动那栏：**< 30ms** 环境健康；**30–80ms** 能玩但会偶发打空，换 5GHz 再测；**> 80ms** 先别调手感，先查网络。

> 数值全是 `—` 说明时钟同步没成功：两端都得刷新页面（手机端不回 pong 的话，单向延迟算不出来）。

### 手机端顶部

三个数字，从左到右是姿态来源（绝对姿态 / 陀螺仪）、**发包率**、**姿态采样率**。

发包率 60–75Hz 是正常的（60Hz 定时器 + 挥拍起势时的补发）。真正决定「球拍跟不跟手」的是**姿态采样率**：低于 45Hz 会标黄，说明这台机器的 `deviceorientation` 只有 25–35Hz——屏幕上的球拍其实是 30fps 的动画，和网络快慢无关。

## 调参入口

所有手感常量都在 **`src/core/court.ts`** 一个文件里，改完 `npm run sim` 就能看到影响：

| 常量 | 现在 | 调它会怎样 |
|---|---|---|
| `SWING_THRESHOLD` | 3.0 rad/s | 往下调更容易触发。你习惯轻挥就调到 2.4 |
| `SPEED_MIN` / `SPEED_MAX` | 18 / 32 | 球速区间。**18 是物理底线**：低于它球从墙上弹回来会擦网或在中场趴下（实测 13–16 全挂），想更慢只能改墙弹性或墙距 |
| `SPEED_GAIN` | 2.4 | 挥拍速度到球速的放大倍数 |
| `HIT_WINDOW_MS` | 150 | 击球时间窗。玩家普遍喊「我明明挥到了」就加大 |
| `FACE_RX` / `FACE_RY` | 0.15 / 0.19 | 拍面半宽/半长。**这两个直接决定可击球面积**，改大 = 变简单 |
| `FACE_MARGIN` | 0.02 | 拍面判定容差。补的是「判定用的拍面比玩家手里的晚 20–60ms」那段位移，给 2cm 让擦框也算命中 |
| `FACE_CY` | 0.6 | 握点到拍面中心的距离（杆长），决定球拍视觉长度 |
| `STEER_LEAD_S` | 0.55 | 来球在最后多少秒开始跟着拍面走。调大会让球路更早拐弯，落点也就不再是节拍器 |
| `STEER_VMAX` / `STEER_ACC` | 12 / 150 | 跟随的修正速度上限（m/s）与加速度上限（m/s²）。**别往下调**：低于 8 就跟不上挥拍，会重现「球从拍子里穿过去」 |
| `FEED_APEX_DX` / `FEED_APEX_DY` | 0.12 / 0.10 | 来球顶点在拍面中心周围的横向/高度散布。两轴会同时偏，合成后必须留在判定半轴（0.203 / 0.243）以内，调到 0.16 / 0.14 就会偶发判空 |
| `FEED_APEX_BACK_MIN/MAX` | 0.55 / 0.85 | 顶点落在拍面**之后**多远。和落点绑死：落点 = `FEED_APEX_LEAD` − back。调大 = 落点变近、球更「往上送」 |
| `FEED_APEX_LEAD` | 2.4 | 顶点在落点前方多远（抛体运动决定，实测值）。**别凭直觉估**，改完用 `probe-feed-scan2.cjs` 重测 |
| `RETURN_OFF_TOL` | 0.55 | 回球落点允许偏离拍面中心的比例（1.0 = 盘边）。调大 = 回球更散、更自然；调到 0.9 以上会出现「回球擦着框回来」 |
| `RACKET_POS` | (0, 1.0, 0.3) | 参考握法（手机竖直）下的**握点**位置。拍面中心在它正上方 `FACE_CY`，所以静止时拍面高 1.6m |
| `WALL_Z` / `WALL_H` | -11.9 / 5.2 | 练习墙的位置和高度 |
| `SWING_MAX_MS` | 450 | 超过这个时长判为「转」不是「挥」 |

`npm run sim` 会跑五档力度（5.5 / 8 / 12 / 18 / 28 rad/s）× 6 个随机种子，输出每档每种的识别次数、击球数、漏接、撞网、连拍。**改完参数第一件事就是跑它**——比真机试快得多。跑多个种子是因为「补偿器选中高吊弧线 → 回球在脚前弹起 → reach」这类漏接只在特定发球扰动的耦合下出现，单种子跑过不代表没问题。

## 手机连不上 / 没反应

### 手机说「这个浏览器没有 DeviceMotion」

球拍端页面底部有环境自检，照着它判断：

| 显示 | 含义 | 怎么办 |
|---|---|---|
| 带「微信 / QQ / 钉钉」 | 在 App 内置浏览器里打开的。WebView 不下发运动传感器，**换 HTTPS 也没用** | 右上角 `⋯`（Android 是 `⋮`）→「在浏览器打开」 |
| `安全上下文 ✗` | 地址是 `http://`，被浏览器静默拦截 | 改用 `npm run dev:https`，扫新二维码 |
| 两个都是 ✓ 但点开还是报错 | 权限被拒，或页面不在前台 | 刷新重新授权；iOS 检查设置里 Safari 的「运动与方向访问」 |

微信这个坑最常踩：默认用微信扫码，页面就停在微信的 WebView 里。iOS 微信甚至不会把 `DeviceMotionEvent` 暴露给网页。

### 为什么手机非要 HTTPS

`http://192.168.x.x` 不是安全上下文，Chrome 和 Safari 都会**静默拦截**运动传感器：不报错，而是干脆不给数据。localhost 例外，所以电脑上看不出来，一上手机就废。

### 手机能连上、能挥拍，但打不到球

先看左下角那四个数（见上面「面板怎么读」）。如果「挥拍」是 0，看手机端仪表区的「角速度」标记：

- 亮起「姿态差分」= 这台机器的 `rotationRate` 不可用，已经自动走姿态差分的兜底（能正常玩，只是峰值略软）
- 一直是 `rotationRate` 但挥拍数不动 = 角速度确实没上来

如果是下面这两种，都不是故障，是打法：

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 球粘在拍面上，过一会儿才掉下去 | 挥拍时机差得远（差 200ms 以上），冻结等不到事件 | 看 HUD 的「时差」，往前或往后半个节拍 |
| 球从拍子上方整整齐齐飞过去 | 拍面仰角太大，越用力越明显 | 压低拍面（见「越用力，拍面要越平」） |
| 球从身子旁边过去 | 真的没站对，或者发球之后连续走了两米以上（盯人每秒只改 1.2 m/s） | 停下等这一球 —— 下一球会重新瞄你 |
| 球擦着拍框掉下来，没弹回 | 没挥拍，或者挥晚/挥早了 200ms 以上 | 看 HUD 的「时差」；这一球已经判漏接了，等下一球 |

「到面高度」也能直接读数：超过 2.0m 说明来球偏高，下一拍提前压平拍面。

### 如果连不上

点对点直连失败通常是这三个原因，按顺序排查：

1. **路由器开了 AP 隔离**（访客网络几乎都开），两台设备互相不可见
2. **手机连的是访客 Wi-Fi / 蜂窝网络**，和大屏不在同一个子网
3. Chrome 的 mDNS 候选地址在部分路由器上不生效

换到 5GHz 主网络、关掉 AP 隔离，基本能解决。

### 如果球拍的方向整体转了 90°/180°

只有一个旋钮：`src/core/attitude.ts` 里的 `EARTH_TO_WORLD`。它把「地球系（Z 朝上）」翻到「three 世界系（Y 朝上）」，现在是 `Rx(-90°)`。方向整体反了就改成 `Rx(+90°)`，然后 `npm test` 里那几项姿态测试会立刻告诉你哪一项对不上。

## 把红锁变绿锁（可选）

默认是自签名证书，浏览器只认信任链，所以显示「不安全」。现在改成自己当一个 CA：

```bash
npm run cert     # 生成本地根证书 + 用它签发服务器证书（dev:https 会自动跑）
npm run trust    # 把根证书装进当前用户的受信任根证书库
```

装完**完全重启浏览器**（不是刷新），电脑端就没有红锁了。

手机要单独装一次（根证书在电脑上，不在手机上）：

1. 手机浏览器打开 `https://192.168.x.x:5174/ca.crt` 下载
2. **iOS**：设置 → 已下载描述文件 → 安装；然后 设置 → 通用 → 关于本机 → 证书信任设置 → 打开对「Tennis P0 Local CA」的**完全信任**
3. **Android**：设置 → 安全 → 加密与凭据 → 安装证书 → CA 证书 → 选刚下载的文件

撤销：`certmgr.msc` → 受信任的根证书颁发机构 → 找到「Tennis P0 Local CA」删除；手机上删掉对应描述文件即可。

> 这个根证书只签发 `localhost` / `127.0.0.1` / 你的局域网 IP，私钥在 `.cert/ca-key.pem`（已在 `.gitignore` 里）。不要拷到别的机器上。

装不了证书也有替代方案：**mkcert**（`mkcert -install`）或者**内网穿透**（`cloudflared tunnel --url http://localhost:5174`，拿到真实域名和真实证书，手机零配置）。

## 球拍为什么和手机对得上

**球拍本地轴 = 手机硬件轴。** 拍柄沿手机长边（+Y），拍面法线垂直屏幕（+Z）。所以想让拍面像正手那样立起来，把手机屏幕转向侧面就对了。

姿态用 `deviceorientation` 的 alpha/beta/gamma（操作系统已经融合好的绝对姿态）算四元数，倾斜**完全照搬**手机，只有**朝向**（绕世界竖直轴）扣掉启动瞬间的初值——因为 alpha 的参考系各平台不一致，直接用会让球拍凭空扭向某个方向。

两个踩过的坑：

1. **屏幕旋转补偿是错的，已经删掉。** 设备坐标系焊死在硬件上：x 沿屏幕短边、y 沿长边、z 垂直屏幕向外，手机横过来握它也不变。按 `screen.orientation.angle` 补一个旋转，结果是横握时球拍整体歪 90°。
2. **只积分陀螺仪，起始倾斜是错的。** 陀螺仪只给角速度，积分出来是「相对启动瞬间的增量」，没有重力参考。你横着举手，球拍却立着，而且越挥越偏。

数学在 `src/core/attitude.ts`，不依赖 DOM 和 three.js，有单测钉住。

## 为什么挥拍检测不做轨迹积分

手机陀螺仪在挥拍峰值处经常被 2000°/s 量程削顶。一旦削顶，积分出来的轨迹就是错的；但「这里有个峰」这个事实永远可靠。所以只做峰值检测 + 特征分类，拍头速度用刚体公式 `v = ω × r` 从峰值反推。

**检测器是「迟滞 + 峰值保持」，不是三点比较。** 这点很关键：大屏 60Hz 发包，但 `deviceorientation` 常常只有 30Hz，走姿态差分时同一个角速度值会被连发 2–4 次，序列里出现平台段。三点检测要求 `w[i]` 严格大于左右邻居，在平台段上恒不成立，整次挥拍会被静默丢弃——曾经表现为「球到面 43 次，挥拍只记到 1 次」。

现在的判据：越过门槛进入 armed → 跟踪这一路的最大值 → 回落到峰值 75% 结算 → 超过 450ms 没回落判为「转」。

## 击球判定：严格碰撞

球拍不是装饰。**球心轨迹与拍面椭圆盘求交**，交点在椭圆内才算打中。

几个实现上绕不开的细节：

**必须做线段求交，不能做点判定。** 球在 240Hz 子步里走 8–17cm，而拍面只有一张纸的厚度可忽略。「球当前在不在椭圆里」在高速球上会系统性漏判——球在两帧之间穿过去，两端都不在椭圆内。所以在这一小步的线段上取几个候选点（穿过平面的位置、面内离中心最近的位置、两端点），挑垂距在球半径以内、且落在椭圆里的那个。代价只是几次乘法。

**判据是「球心到拍面圆盘的距离 ≤ 球半径」，不是「球心穿过拍面平面」。** 差别只在掠射时出现：球路几乎平行于拍面，球心可能永远不穿过平面，但球体已经压到拍线上了。按「必须穿过平面」判会漏，而漏掉的那 16ms 在屏幕上就是「球从拍子中间穿过去」——玩家不会认为自己角度不对，只会认为碰撞坏了。真网球这时是擦框，也是要弹一下的。

**位姿要按时刻插值。** 拍面位姿来自渲染循环（60Hz），物理跑 240Hz。一个子步里拍面最多转 25°，直接用上一帧的姿态会把命中点算到几厘米之外。用的是时间戳 + slerp，不是帧序号——rAF 并不是严格的 60Hz。

**时间窗退到辅助位置。** ±150ms 现在只回答「这一下算不算你挥的」：球可能正好撞上静止的拍子，那不该算一次击球。真正的判定由几何完成。

**冻结从 190ms 缩到 60ms 又放回 100ms。** 严格碰撞之后，绝大多数命中都是「正在挥」被抢跑直接取走的，不需要等；但 60ms 还是太短——挥拍事件的路途时间是「峰值回落结算 16–33ms + 网络 20–60ms」，峰值正好落在接触点上的那一挥最晚 90ms 才到，60ms 会把它误判成漏接，玩家看到的就是「球粘在拍面上然后掉下去」。100ms 覆盖整条链路的抖动。

**冻结期结束还没等到挥拍，球要「擦框掉下去」，不能原速穿过拍面。** 这一点以前不重要（球是从远处直送过来的，撞到拍面的概率低），现在喂球瞄着拍面中心，**每一球都会正正打在拍子上**——所以「没挥拍」这个结局必须演对。原来是把速度还原、让球继续飞，屏幕上读起来就是「球从拍子里穿过去了」，玩家的结论必然是「碰撞坏了」。现在给它一个说得通的结局：横向速度削到一成、往侧前方掉下去。看到的是「蹭到了框，没打实」，和 HUD 那句「漏接」对得上。

### 挥拍时球拍真的会转（所以球要跟着拍面走）

这是「站着不动能打到，一挥拍球就从拍子里穿过去」的根因。

手机只给得出**角度**，给不出手的位置。所以球拍天生只能写成「握点固定、绕握点旋转」——而拍面中心挂在握点末端 `FACE_CY`（0.6m）处。手机转 30°，拍面中心平移 31 厘米；转 90° 是 85 厘米。整个拍面才 30 厘米宽。

**这个几何事实不能改。** 一度试过把拍面中心锚死在空间里（旋转只改朝向），判定确实稳了，但屏幕上拍子除了转一点平移都没有——那根本不是挥拍，自由挥拍被彻底破坏。所以位置必须留给握点。

那问题就落到球这边：**球在最后半秒跟着拍面走**（`Rally.steerToRacket`）。球飞了十米，最后三米本来就是进击球准备的一段，轻微修正看不出来；一旦跟住，挥到哪里球就在哪里，`sweepFace` 的判定自然成立。

能不能跟上，取决于两个数（`scripts/probe-swing.cjs` 实测）：

| 挥拍转角 | 拍面中心扫出 | 跟随关（老做法） | 跟随开（现在） |
|---|---|---|---|
| 30° | 0.31m | 0.37m 未接触 | 打中 |
| 60° | 0.60m | 0.63m 未接触 | 打中 |
| 90° | 0.85m | 0.86m 未接触 | 打中 |
| 120° | 1.04m | 1.02m 未接触 | 打中 |

（「距离」= 球穿过击球面那一刻，球心到拍面中心的三维距离；判定半轴约 0.20m。）

**回球补偿要用「归一位姿」，不能直接用挥拍中的位姿。** 补偿器（`liftOverNet`）会验证「回球腿能不能真的穿过拍面」，而挥到一半时拍面中心被甩在半米外——拿它当目标，所有候选弧线都不合格，池子空了退回兜底，实测偶发撞网。所以回球判定用 `HIT_Z` 平面 + 击球高度，只保留**朝向**（斜拍面能不能兜住球是真实约束，11-04 那个 bug 就是靠它抓住的）。

### 走位：球会找你，但你要站对地方

手机只给姿态，球拍**只能转、不能自己挪**。拍面椭圆就 30×38cm，所以位置必须由键盘给（`WASD`）：

- 移动只平移站位和相机，不碰姿态。两者必须分开：姿态来自手机（绝对朝向），位置来自键盘（相对速度），混在一起手感会打架。
- 横向、前后都能动（`x` ±3m、`z` 从网前 0.55m 到来球线后 1.35m）。

**但球是往你身上发的，不是你追球。** 早期版本球从场地正中发、落点铺开 ±1.3m，走开两米就永远够不着，而且屏幕上没有「你站歪了」的参照——早期现象是「静止时能打到、一移动就打不到」。现在发球点跟着拍面走（见上面关于喂球的那节），而且**飞行途中还会轻微盯人、落地那一瞬再重瞄一次**，所以哪怕你是球发出去之后才挪的步，球也会跟着换落点。走位的作用变成**微调**：站着能打到，挪半步打得顺。

代价是拍面真的只有 30×38cm：球心偏出 25cm 就打空（`npm test` 里有这条几何反证）。球会找你，但不会替你挥那一下。

### 连带修掉的三处

**回球补偿的判定从「竖平面高度窗口」换成拍面盘形。** 这是真机上「打到了却不回弹」的根因。旧判据问的是「球穿过 `z=targetZ` 竖平面时，高度在不在拍面中心 ±12cm」——拍面一倾斜这个模型就错了：倾斜的拍面是**斜的盘**，上升中的球穿过盘平面的点比穿过竖平面低 15cm。于是补偿器选中「过竖平面 1.6m」的弧线，实际从拍面下沿下面两厘米掠过去。现在用**和游戏内同一套 `sweepFace`** 逐个物理子步验证回球能不能真的穿过拍面，并且只在撞墙高度不超过可见墙面（5.2m）的弧线里挑——更高的「撞墙」是物理在一面不存在的墙上弹了一下，回球会从天上砸下来在脚前大力弹起，正是要避免的那类球。

**但传进去的位姿要「归一」。** 不能直接用挥拍中的实时位姿：那时拍面中心被甩在半米外，补偿器要「让回球穿过一个飞在半空的拍面」，所有候选都不合格，池子空了退回兜底弧线，实测偶发撞网。所以位置固定为「击球平面 `HIT_Z` + 击球高度」，只保留**朝向**——斜拍面能不能兜住球是真实约束。

**而且不再挑「最居中」的那条。** 以前会在合格弧线里选 `offCenter` 最小的、还按 0.1 步长细化一圈，于是每一拍都回到甜区正中央——玩家两拍之后就不用看球在左边还是右边了。现在所有落点偏离在 55% 半径以内（`RETURN_OFF_TOL`）的弧线都是合格解，**随机挑一条**：回球会有十几厘米的自然漂移，但每一条都经过同一套几何验证，绝不会有「够不着」的那种解。随机挑的前提是「都合格」，所以这不是放宽判定，是去掉不必要的强迫症。

**仰角扫描起点从 `max(v[1], 0)` 改成 0。** 原来「只许抬高、不许压低」，前提是「压低一定下网」。但球撞的是墙，压平之后撞墙更低、回来也更低，照样过网。这个下限卡死过一整档：全力挥的出射仰角本身就有 6 m/s，33 次试探全部失败，补偿原样返回——看起来像没生效，其实是根本没得选。

## 球拍模型：换资产不换判定

拍子是 `public/models/racket.glb`（源文件留在 `assets/`，1372 三角面、无贴图、
自带 16×18 拍线）。判定**仍然是一块椭圆盘**，模型只负责好看，一根线都不参与碰撞。

模型导出的坐标约定和游戏里的球拍组完全一致——pivot 在柄底中心、拍头沿 +Y、
拍面法线 +Z、单位米——所以朝向一个都不用调，只差尺寸。

**尺寸必须对，因为判定盘的位置是写死的。** 模型是真实比例（拍框外沿半宽 12.8cm、
拍面中心在柄底上方 51.5cm），而判定是 `FACE_RX` 15cm / `FACE_RY` 19cm / 中心
`FACE_CY` 60cm——本来给的就比真实拍面大一圈。直接摆进去，视觉拍面会比判定盘低
8.5cm：球从拍面下沿掠过时判「没打到」，可看起来明明碰到了，比尺寸差一点更伤人。

所以 `scene.ts` 的 `loadRacketModel()` 按两个轴分别缩放：

| 轴 | 系数 | 对齐到 |
|---|---|---|
| x | `FACE_RX / 0.128` ≈ 1.172 | 拍框外沿正好等于椭圆的 x 半径 |
| y | `FACE_CY / 0.515` ≈ 1.165 | 拍面中心正好落在 `FACE_CY` |

x 这一条是精确的，不是凑数：`sweepFace` 的判据是「球心落在 `FACE_RX + 球半径`
的椭圆内」，也就是球贴着框外沿就算命中——视觉框边落在 `FACE_RX` 上，两者严丝合缝。
正投影比对过：框外沿 ±0.150 对判定 ±0.15，拍头顶 0.797 对判定上沿 0.790，柄底 0。

非均匀缩放把框管截面压扁 0.6%（2.4cm 的管子差 1.5mm），看不出来；整支拍子
68.5cm → 79.7cm，和原来程序化那支（80.3cm）几乎一样，所以换拍之后观感不跳。

**换模型只改两个数**：`GLB_FRAME_HALF_X` 和 `GLB_FACE_CY`，换成新模型的拍框外沿
半宽与拍面中心高度（Blender 里量，或 `node -e` 读 glb 的 accessors 包围盒）。
**不要**去动 `FACE_*`——那三个数动的是判定、喂球和所有测试。

两个兜底：模型加载失败（路径错、文件被删）会自动退回程序化球拍，游戏照常能玩；
拍面那层 5% 白的薄膜不归模型管，挂在球拍组上，换模型不会丢。

`npm test` 覆盖的几条关键断言值得留意：

- **平台段输入仍能识别挥拍**：同一个值连发 3 次，必须刚好出 1 拍
- **上旋必须比平击落得早**：专门钉死马格努斯的叉乘顺序（写成 `ω × v` 方向就反了）
- **高速球不穿墙**：240Hz 定步长下 42 m/s 的球每步只走 17cm
- **整局对拉零漏接**，且过网次数与击球次数 1:1（连拍不能重复计数）
- **一步跨过整个拍面也不漏**：起点和终点都在椭圆外，仍必须命中——这条钉死了「为什么必须做线段求交」
- **球顺着拍面掠过去也算接触**：球路几乎平行于拍面时球心不穿平面，但球体已经压到拍线上了；按「穿过平面」判会漏，屏幕上就是穿模
- **挥拍时拍面中心会绕握点扫出去**：转 60° 必须扫出 0.45m 以上——这条钉住「球拍要能真的挥」，谁再把拍面中心锚死就会红
- **球拍一直在转也必须打得中**：±70° 连续摆动 10 秒，必须至少命中一次——钉住「球跟着拍面走」这条跟随链路
- **挥拍过程中球拍一直在转，球也必须打得中**：连续 ±70° 摆动的整局模拟（不挥时球粘拍、挥了就出球）
- **补偿瞄的是拍面本身**：倾斜 18° 的拍面下，回球必须真的穿过拍面盘（用同一套 `sweepFace` 验证），且撞墙不超过可见墙面——这条钉的是「打到了却不回弹」那个真机 bug
- **拍面只有 30×38cm**：同一条水平飞过的球，球心偏 15cm 中、偏 25cm 打空——反证尺寸是真的在限制范围，不是摆设
- **站到边上不动也能连续打**：`x=0 / ±2 / −2.5` 三个站位都必须零漏接（喂球跟着拍面走的回归测试）
- **来球必须先落地一次**：落点在拍面前 1.3–2.4m、击球高度贴合拍面中心 30cm 以内——钉住「弹地喂球」，防止哪天又被改回直送（直送在后场必然变成月亮球）
- **球发出去之后才挪步也接得到**：发球 0.35 秒后横移 1.2 米（比三个拍面还宽），球必须自己换落点送到新站位上——这条钉的是「落地重瞄 + 飞行途中盯人」，也是「落点太远够不到」的回归防线
- **没挥拍时球是擦框掉下去，不是穿过拍面**：喂球瞄着拍面中心，所以「没挥」这个结局每球都会演一次，演错了就会被当成碰撞 bug

时钟同步那组也值得留意：偏移量的符号一旦写反，延迟会变成负数或者大得离谱，而且不会有任何报错——只会让你误以为网络有问题。

## 设计取舍（改之前先读）

**为什么用 WebRTC 而不是 WebSocket。** WebSocket 是 TCP，一次丢包会让后续所有包排队等重传，Wi-Fi 抖一下就是几百毫秒卡顿。传感器数据用 `ordered: false, maxRetransmits: 0`，丢一帧无所谓。

**为什么不用蓝牙。** iOS Safari 不支持 Web Bluetooth，手机本身也不能当 BLE 外设广播；就算能，BLE 实测基线 8–16ms，比局域网 Wi-Fi 的 2–8ms 还慢。

**为什么球的物理在大屏算，不在手机算。** 手机只发姿态和角速度（60 字节/包，约 10kbps），物理和碰撞都在大屏本地跑，避免两端各自模拟导致轨迹对不上。

**为什么连拍在击球那一刻不加、要等过网。** 反过来的话数字会比画面慢半秒，玩家会以为没算上；但如果在击球瞬间就加，撞网那一下连拍会先涨再归零，看着很怪。
